# Р4.09 — Паттерн 9. Shared artifacts

**Статус:** Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

**Уровень:** Middle–Senior/Tech Lead. **Время:** 30–45 минут, предварительная оценка без пилота.

**Предварительные знания:** Р4.02, Р4.05.

**Результат обучения:** Передавать результат вместе с версией, происхождением и границей доказательности.

## 1. Инженерная проблема и определения

Shared artifact — устойчивый результат, который передаётся между стадиями, людьми, агентами или CI: spec, patch, decision record, test report. Общая папка не определяет договорённость о формате, свежести или владельце.

Важно различать immutable handoff и изменяемую общую память. Во втором случае появляются конкурентные записи и конфликты.

Связанные первоисточники и границы их применения: [SRC-418](references.md#src-418). Рабочие модели курса явно отделены от документированных функций продуктов.

## 2. Архитектура и механизм

Минимальный envelope описывает тип, schema version, producer, parent task/run, source commit, время, sensitivity и правило замены. Consumer валидирует не только наличие файла, но и связь с нужным состоянием. GitHub workflow artifacts — конкретный пример хранения и передачи файлов между jobs, а не универсальный протокол агентной памяти.

```text
producer → immutable artifact + lineage → validate → consumer
                              ↓
                     superseded при новом входе
```

Имена `latest.json` без указателя версии удобны, но создают риск чтения не того результата.

## 3. Авторская практическая демонстрация

Reviewer Workbench получает test report, созданный до изменения authorization. В файле написано passed, но source commit не совпадает с текущим patch. Приёмка должна отклонить перенос evidence.

```json
{
  "schema_version": 1,
  "kind": "verification-report",
  "task_id": "CLOSE-01",
  "source_commit": "<exact-commit>",
  "status": "not-executed",
  "checks": []
}
```

Это учебный JSON, не стандарт GitHub или SDK. Значение not-executed честно отражает отсутствие запуска. В реальной реализации checksum, подпись и ACL выбираются по threat model. При публикации нового report старый не перезаписывается бесследно: сохраняется lineage и причина supersession.

**Среда и статус:** Engineering Workbench — кандидат сквозного проекта; здесь использованы синтетические входы. Схемы, псевдокод и JSON иллюстрируют договорённости. Продукты, агентные процессы, команды и приложение в рамках урока не запускались. Ожидаемые свойства не являются фактическими результатами.

## 4. Production, отказы и сопровождение

Для mutable артефактов нужен single writer, optimistic version check или согласованный merge. Secret-bearing logs очищаются до передачи, задаются retention и права. В monorepo schema должна быть совместима с потребителями; её незаметное изменение может сломать соседние workflow. Хранилище evidence само становится эксплуатационной зависимостью.

В существующем проекте фиксируют исходный commit и совместимость потребителей; в команде — владельца решения и reviewer. Автоматические tests/CI дают evidence в охваченном scope, а человеческий review оценивает намерение и исключения. Полная стоимость включает обучение, настройку, usage, задержку, review, rework и дальнейшие обновления. Secrets и чувствительные payload не помещают в открытые artifacts. Условия остановки и восстановления выбирают до расширения полномочий.

## 5. Trade-offs и альтернативы

| Подход | Когда уместен | Освоение, внедрение и сопровождение / цена компромисса |
|---|---|---|
| Чат/устный handoff | Короткая синхронная работа | Мало setup, трудно восстановить provenance |
| Versioned файлы | Контракты и reviewable history | Прозрачно, нужен контроль ссылок и конфликтов |
| Artifact store | Много runs/jobs | ACL и retention удобнее, выше инфраструктурная цена |

Сравнение качественное, без результатов benchmark. Проверяемость оценивают по связи критериев с независимыми checks; безопасность — по реальным границам действий и bypass paths. Перед выбором сопоставляют цену внедрения и поддержки с ценой ручного baseline. Большая автономность и больше артефактов не получают преимущества автоматически.

## 6. Проверка знаний с объяснёнными ответами

### 1. Что делает artifact общим?

Он передаётся через определённую границу нескольким потребителям с известным смыслом, schema и ownership. Наличие общей папки этого не задаёт.

### 2. Почему неизменяемая передача проще?

Она сохраняет историю и исключает незаметное перезаписывание. Новая версия явно заменяет старую через lineage.

### 3. Как обработать конкурентные записи?

Выделить отдельных writers, одного владельца merge или optimistic version check. Последняя запись не должна молча побеждать без согласованной семантики.

### 4. Что важно для безопасности artifact?

Права доступа, минимизация содержимого, provenance, retention и удаление секретов. Даже test log может содержать чувствительные payload.

### 5. Зачем указывать commit и run?

Они связывают evidence с конкретным состоянием. Без них старый отчёт легко принять за проверку нового patch.
