# Р4.17 — Методология 3. OpenSpec

**Статус:** Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

**Уровень:** Middle–Senior/Tech Lead. **Время:** 30–45 минут, предварительная оценка без пилота.

**Предварительные знания:** Р4.15, Р3.07.

**Результат обучения:** Различать текущую спецификацию и предлагаемое изменение; проверять reconciliation после реализации, а не считать архив evidence корректности.

## 1. Инженерная проблема и определения

OpenSpec — открытый проект Fission-AI для spec-driven development с AI coding assistants. В отличие от универсального термина SDD, это конкретный toolkit со своей структурой и эволюцией. Урок анализирует публичный README на дату проверки; команды и integrations требуют версии перед исполнением.

Связанные первоисточники и границы их применения: [SRC-404](references.md#src-404). Рабочие модели курса явно отделены от документированных функций продуктов.

## 2. Архитектура и механизм

Полезно различать действующий контракт системы и пакет предлагаемого изменения. Изменение описывает новую intent, затрагиваемые требования, план и задачи; после реализации и проверки оно архивируется по правилам проекта, а актуальные specs согласуются с новым состоянием.

```text
текущие specs → change package → implement/check → archive/reconcile
                    ↑                    ↓
                    уточнение при новом решении
```

Архивация — операция жизненного цикла артефакта. Она не означает, что код прошёл все проверки или что reviewer согласовал риск.

## 3. Авторская практическая демонстрация

В Workbench существует правило закрытия только исполнителем. Change добавляет роль администратора. В пакете нужно показать изменённый критерий и неизменяемые свойства: прежний tenant scope, отказ чужому пользователю, повтор и audit consistency.

```text
change intent: расширить actor set для CLOSE-01
delta: разрешить administrator в своей tenant boundary
preserve: C2 state policy, C3 idempotency, C4 audit
verification: role matrix + regression cases
```

После реализации reviewer проверяет, что новые specs действительно отражают решение. Если change архивирован, но current spec осталась старой, обнаружен drift. Если текущий код расходится со spec по другой причине, не следует незаметно включать это расхождение в scope изменения.

Структура здесь концептуальная; точные generated directories и commands берутся из pinned release. CLI не запускался, archive и code reconciliation не наблюдались в рабочем приложении.

**Среда и статус:** Engineering Workbench — кандидат сквозного проекта; здесь использованы синтетические входы. Схемы, псевдокод и JSON иллюстрируют договорённости. Продукты, агентные процессы, команды и приложение в рамках урока не запускались. Ожидаемые свойства не являются фактическими результатами.

## 4. Production, отказы и сопровождение

Для brownfield полезен ограниченный change вместо переописания всей системы, но сначала нужна карта действующих контрактов. Общие specs в monorepo требуют owner и review затронутых команд. Следите за установочными scripts, обновлениями и различиями host integrations; project README не является независимой оценкой качества.

В существующем проекте фиксируют исходный commit и совместимость потребителей; в команде — владельца решения и reviewer. Автоматические tests/CI дают evidence в охваченном scope, а человеческий review оценивает намерение и исключения. Полная стоимость включает обучение, настройку, usage, задержку, review, rework и дальнейшие обновления. Secrets и чувствительные payload не помещают в открытые artifacts. Условия остановки и восстановления выбирают до расширения полномочий.

## 5. Trade-offs и альтернативы

| Подход | Когда уместен | Освоение, внедрение и сопровождение / цена компромисса |
|---|---|---|
| Issue + patch | Малый fix | Минимум документов, выше риск потерять контекст решения |
| Change package OpenSpec | Эволюция формализованных specs | Явный delta/архив; нужно поддерживать current contract |
| Длинная feature spec | Большая новая функция | Глубже design, дороже пересмотр для малой правки |

Сравнение качественное, без результатов benchmark. Проверяемость оценивают по связи критериев с независимыми checks; безопасность — по реальным границам действий и bypass paths. Перед выбором сопоставляют цену внедрения и поддержки с ценой ручного baseline. Большая автономность и больше артефактов не получают преимущества автоматически.

## 6. Проверка знаний с объяснёнными ответами

### 1. Что такое delta спецификации?

Описание добавляемого, изменяемого или удаляемого поведения в рамках change. Оно должно быть согласовано с актуальным контрактом после завершения.

### 2. Что означает архивирование change?

Этап управления записью изменения и историей по выбранному workflow. Точный sync/архивный механизм проверяют для версии; он не доказывает корректность кода.

### 3. Почему reconciliation требует работы?

Пропущенное обновление оставляет current specs устаревшими. Нужны owner и смысловая проверка, а не только перемещение файлов.

### 4. Почему не копировать команды main бессрочно?

Ветка и интерфейсы меняются. Для воспроизводимого tutorial фиксируют release/commit и поддерживаемый host.

### 5. Исполнялся ли OpenSpec в уроке?

Нет. Рассмотрены публичные документы; установочные действия и workflow не выполнялись, фактических runtime результатов нет.

## 7. Итоги и следующий шаг

Различать текущую спецификацию и предлагаемое изменение; проверять reconciliation после реализации, а не считать архив evidence корректности.
