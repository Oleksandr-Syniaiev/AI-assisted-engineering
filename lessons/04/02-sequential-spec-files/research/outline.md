# План урока Р4.02: Паттерн 4. Спецификации из X последовательных файлов (детерминированные стадии)

**Статус: Research / Outline. Урок не написан.**

## Результат обучения
Читатель объясняет границы концепции, связывает её с проверяемым инженерным workflow, разбирает production failure mode и обосновывает выбор альтернативы по evidence.

## Предпосылки и переходы
- Prerequisites: Р4.01, Р4.04.
- Curriculum ID, название и исходный порядок сохранены.
- Предыдущие темы: see prerequisite links; следующий мостик: После договорённой последовательности следующий урок строит bounded runtime loop.

## План разделов урока
1. Результат обучения, prerequisites, терминология и scope.
2. Production problem and motivation: Название не указывает, какое значение X или обязательный набор файлов предполагается. Спецификации, планы и задачи могут быть разделены на артефакты со стадийными входами/выходами; это process pattern курса, не универсальная формула. «Детерминированность» может относиться к порядку/gates, но не гарантирует детерминированный текст LLM или корректность.
3. Теория/механизм: На каждой стадии задать owner, input version, question it resolves, output schema, exit criterion, allowed side effects и путь возврата. Связь должен хранить явные IDs/links. Gate может быть автоматическим schema/check или человеческим approval. Изменение upstream intent инвалидирует зависимые решения и требует повторной проверки.
4. Mermaid diagram для data/state flow, owners и enforcement boundaries.
5. Практическая авторская demonstration: Смоделировать изменение требования: propose → spec → design/plan → tasks → implementation/checks. На середине scope меняется; показать invalidation, delta и возврат на владельца артефакта. Число файлов не задавать до источника X; исследовательский walkthrough не исполнен.
6. Production engineering: Для brownfield минимизировать артефакты и сохранить актуальные system constraints; добавить историю и контроль доступа. Gates влияют на lead time; автоматические генераторы могут плодить дубли. Контроль rollout/rollback относится к system design, не к документационному файлу.
7. Alternatives matrix with applicability, learning curve, implementation, maintenance, safety, verification and total cost.
8. Пять сценарных вопросов с объяснёнными ответами.
9. Выводы, известные ограничения и связь со следующей темой.

## Практическая демонстрация и evidence
- Вход: сквозной кандидат Engineering Workbench; конкретный scaffold/harness/version to be fixed before drafting.
- Показать happy path и один конфликт/отказ/negative case.
- Ожидаемый результат сформулировать как критерий, не как фактический вывод.
- Фактическое исполнение включать лишь при запуске в описанной среде с версией и необрезанным evidence.
- Проверка должна быть независима от авторского/agent-generated artifact, где возможно.
- Research package не включает команды, которые здесь запускались; некоторые официальные примеры продуктов можно процитировать после повторной проверки.

## Вопросы проверки знаний
### 1. Какое значение X задано curriculum?

Не указано. Не выводить X из примера Spec Kit/OpenSpec/Kiro и не объявлять их файлами автора паттерна. [SRC-402](sources.md#src-402), [SRC-403](sources.md#src-403)
### 2. Что можно назвать детерминированным?

Порядок переходов, схемы и контрольные условия, если их исполняет определённый код. Генеративный результат и корректность не становятся детерминированными автоматически. [SRC-402](sources.md#src-402), [SRC-403](sources.md#src-403)
### 3. Что должно произойти при изменении требования?

Определить зависимые артефакты, пересмотреть их и повторить соответствующие gates/tests; иначе возникает drift. [SRC-402](sources.md#src-402), [SRC-403](sources.md#src-403)
### 4. Когда полезны отдельные файлы?

Когда стадии имеют разных владельцев/reviewers, долговременную ценность или самостоятельное применение; не ради формального числа. [SRC-402](sources.md#src-402), [SRC-403](sources.md#src-403)
### 5. Как сравнить X-file workflow?

Зафиксировать единый кейс, проверить число ручных переходов, пропуски, время, rework и sync burden; сравнение без baseline не доказывает выгоду. [SRC-402](sources.md#src-402), [SRC-403](sources.md#src-403)

## Common misconceptions
- Термин curriculum не гарантирует стандартизованное определение или установленное авторство.
- Официальная capability matrix не является независимым сравнением качества.
- Документация, generated artifact и самооценка модели не заменяют run-time evidence.
- Security policy нельзя обеспечить одним prompt; tool boundaries и CI permissions важны.
- Качественная матрица не является измерением производительности/TCO.

## Практическая форма
Использовать только авторскую разобранную демонстрацию; не назначать самостоятельную работу, домашнее задание, сдачу или обязательный артефакт читателя. Вопросы снабдить полными ответами.

## Блокирующее уточнение
Подтвердить у автора curriculum X, список файлов, смыслы gates, возобновления/отката и происхождение выражения «детерминированные стадии».
