# Р4.02 — Паттерн 4. Спецификации из X последовательных файлов (детерминированные стадии)

**Статус:** Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

**Уровень:** Middle–Senior/Tech Lead. **Время:** 30–45 минут, предварительная оценка без пилота.

**Предварительные знания:** Р4.01, Р4.04.

**Результат обучения:** Проектировать стадии через вход, выход, gate и возврат; не отождествлять порядок файлов с корректностью.

## 1. Инженерная проблема и определения

Последовательные файлы помогают разделить вопросы: что требуется, как реализовать и как разбить работу. Но X в curriculum не определён. Здесь X — число нужных артефактов конкретного процесса; универсальный список или магическое количество не вводится.

Детерминированным может быть порядок переходов и проверка schema. Вывод LLM и правильность design от этого детерминированными не становятся.

Связанные первоисточники и границы их применения: [SRC-401](references.md#src-401) · [SRC-403](references.md#src-403). Рабочие модели курса явно отделены от документированных функций продуктов.

## 2. Архитектура и механизм

У каждой стадии есть версия входа, owner, вопрос, выход и exit criterion. После изменения требования downstream-артефакты получают статус требующих пересмотра. Gate может проверять ID и ссылки автоматически или ожидать решение человека; эти виды evidence различаются.

```text
intent → spec → design/plan → tasks → implementation → checks
            ↑                 ↓
            review при изменении upstream-решения
```

Прогресс стадии не равен завершению функции: tasks могут быть выполнены, а итоговый API не пройти acceptance. Поэтому нужны и локальные gates, и общая приёмка.

## 3. Авторская практическая демонстрация

Сначала Workbench закрывает заявки только исполнителем. На стадии tasks появляется решение разрешить администратора. Простая генерация следующего файла продолжит устаревший план.

Правильный разбор: зафиксировать новый decision; обновить ROLE-01 и negative cases; пересмотреть authorization design; отметить зависимые tasks; затем продолжить реализацию. Выполненные ранее независимые задачи можно сохранить, а не пересоздавать всё механически.

```text
artifact: tasks-v2
depends_on: spec-v3, design-v2
state: needs-review
reason: изменился список допустимых actors
```

Формат здесь учебный, не manifest конкретного продукта. Ожидаемый результат — обнаруженное устаревание до кодирования, а не автоматически подтверждённая совместимость.

**Среда и статус:** Engineering Workbench — кандидат сквозного проекта; здесь использованы синтетические входы. Схемы, псевдокод и JSON иллюстрируют договорённости. Продукты, агентные процессы, команды и приложение в рамках урока не запускались. Ожидаемые свойства не являются фактическими результатами.

## 4. Production, отказы и сопровождение

В brownfield избыточное разбиение может дублировать существующие ADR и API docs. Связи лучше вести идентификаторами и версиями, назначив владельца возврата. Если gate просто проверяет наличие непустого файла, процесс легко создаёт видимость дисциплины без смыслового контроля.

В существующем проекте фиксируют исходный commit и совместимость потребителей; в команде — владельца решения и reviewer. Автоматические tests/CI дают evidence в охваченном scope, а человеческий review оценивает намерение и исключения. Полная стоимость включает обучение, настройку, usage, задержку, review, rework и дальнейшие обновления. Secrets и чувствительные payload не помещают в открытые artifacts. Условия остановки и восстановления выбирают до расширения полномочий.

## 5. Trade-offs и альтернативы

| Подход | Когда уместен | Освоение, внедрение и сопровождение / цена компромисса |
|---|---|---|
| Один контракт | Небольшое изменение | Просто поддерживать; сложные вопросы смешиваются |
| Несколько стадийных файлов | Командная функция | Явные зависимости; нужно управлять invalidation |
| Workflow engine | Много повторяющихся изменений | Дороже внедрение; переходы и recovery можно формализовать |

Сравнение качественное, без результатов benchmark. Проверяемость оценивают по связи критериев с независимыми checks; безопасность — по реальным границам действий и bypass paths. Перед выбором сопоставляют цену внедрения и поддержки с ценой ручного baseline. Большая автономность и больше артефактов не получают преимущества автоматически.

## 6. Проверка знаний с объяснёнными ответами

### 1. Какое значение X указано в curriculum?

Значение не задано. Число файлов выбирают по потребностям процесса и не объявляют составом неизвестной авторской модели.

### 2. Что здесь может быть детерминированным?

Порядок переходов и автоматические условия gate. Генерация текста и правильность решения не получают такой гарантии автоматически.

### 3. Что делать при изменении upstream-требования?

Найти зависимые artifacts, пересмотреть их и повторить соответствующие checks. Продолжение по старому plan создаёт drift.

### 4. Когда полезно разделение файлов?

Когда этапы решают разные вопросы, имеют разных owners или самостоятельную ценность. Разделение только ради числа повышает поддержку без ясной выгоды.

### 5. Как проверить пользу стадийного процесса?

На одном baseline сравнить пропуски, время, ручные переходы, review и rework. Результат единичного случая нельзя обобщать на все команды.

## 7. Итоги и следующий шаг

Проектировать стадии через вход, выход, gate и возврат; не отождествлять порядок файлов с корректностью.
