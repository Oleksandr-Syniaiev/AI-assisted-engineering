Р4.06 — Паттерн 7. Hooks: lifecycle vs git-style

Статус: Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

Уровень: Middle–Senior/Tech Lead. Время: 30–45 минут, предварительная оценка без пилота.

Предварительные знания: Р4.03, Р4.07.

Результат обучения: Выбирать hook по событию и границе действия, отдельно проверяя block, timeout и bypass.

1. Инженерная проблема и определения

Слово hook обозначает реакцию на событие, но события у разных систем различаются. Agent lifecycle hook может реагировать на tool invocation или сессию; Git hook — на commit или receive. Они имеют разные payload, cwd, права, timeout и возможность блокировки.

Нельзя перенести script между ними только переименованием файла.

Связанные первоисточники и границы их применения: SRC-414 · SRC-415. Рабочие модели курса явно отделены от документированных функций продуктов.

2. Архитектура и механизм

Для каждого hook задайте trigger, input schema, исполняемый код, output/решение, обработку ошибки и observability. Выясните, выполняется ли он синхронно и может ли остановить действие. Preview-интерфейс агента требует проверки версии. Git документирует собственные события и обход pre-commit через --no-verify.

runtime event → hook adapter → validation → allow/deny/error
Git event     → Git hook     → exit status по семантике Git

Неблокирующий post-event log полезен для диагностики, но не предотвращает уже состоявшийся side effect.

3. Авторская практическая демонстрация

Для Workbench сравним два намерения. Первое — проверить сообщение commit; этому подходит commit-msg. Второе — запретить tool запись вне разрешённого каталога; Git hook не видит все shell/file действия и недостаточен.

Контракт agent hook:
вход: имя действия, target, identity и args
проверка: target в allowlist, credentials подходят scope
выход: deny с причиной либо allow
сбой/timeout: политика для чувствительной записи — fail closed

Это псевдоконтракт без выдуманной JSON-schema конкретного клиента. Для истинного enforcement ещё проверяют, нельзя ли вызвать ту же операцию другим tool. Политика отказа выбирается по риску, а не предполагается одинаковой во всех продуктах.

Среда и статус: Engineering Workbench — кандидат сквозного проекта; здесь использованы синтетические входы. Схемы, псевдокод и JSON иллюстрируют договорённости. Продукты, агентные процессы, команды и приложение в рамках урока не запускались. Ожидаемые свойства не являются фактическими результатами.

4. Production, отказы и сопровождение

Hook — исполняемый dependency: review code, права, network, секреты и update path. Рабочая директория может отличаться от ожидаемой, а input содержать недоверенный текст. Не вставляйте его в shell как код. Локальные hooks дополняйте серверными проверками и защищёнными CI gates, если правило должно действовать для всей команды.

В существующем проекте фиксируют исходный commit и совместимость потребителей; в команде — владельца решения и reviewer. Автоматические tests/CI дают evidence в охваченном scope, а человеческий review оценивает намерение и исключения. Полная стоимость включает обучение, настройку, usage, задержку, review, rework и дальнейшие обновления. Secrets и чувствительные payload не помещают в открытые artifacts. Условия остановки и восстановления выбирают до расширения полномочий.

5. Trade-offs и альтернативы

ПодходКогда уместенОсвоение, внедрение и сопровождение / цена компромисса
Agent lifecycle hookКонтроль runtime событийHarness-specific; нужны тесты failure semantics
Git hookСобытия GitЛокальный feedback, возможен обход
CI/server policyОбщий допуск merge/deployСильнее командный контроль, более поздняя обратная связь

Сравнение качественное, без результатов benchmark. Проверяемость оценивают по связи критериев с независимыми checks; безопасность — по реальным границам действий и bypass paths. Перед выбором сопоставляют цену внедрения и поддержки с ценой ручного baseline. Большая автономность и больше артефактов не получают преимущества автоматически.

6. Проверка знаний с объяснёнными ответами

1. Чем различаются lifecycle и Git events?

Первый набор принадлежит агентному runtime, второй — операциям репозитория Git. Payload, место исполнения и реакция на ошибку различаются.

2. Достаточно ли локального hook для обязательного gate?

Нет: hook может отсутствовать или быть обойдён. Командное правило требует контроля на доверенном пути CI или сервера.

3. Что проверять у hook?

Обнаружение, вход, cwd, выход, timeout, ошибки, права и альтернативные пути обхода. Успех только обычного сценария не показывает отказное поведение.

4. Почему hook является supply-chain риском?

Он исполняет код с правами своей среды. Поэтому установку стороннего hook рассматривают как подключение исполняемой зависимости, а не просто текста.

5. Одинаковы ли конфигурации hooks у всех клиентов?

Нет. Перед переносом нужно сверить события, schema и возможности блокировки конкретного host/version.

7. Итоги и следующий шаг

Выбирать hook по событию и границе действия, отдельно проверяя block, timeout и bypass.
