# Р4.19 — Методология 5. specs.md

**Статус:** Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

**Уровень:** Middle–Senior/Tech Lead. **Время:** 30–45 минут, предварительная оценка без пилота.

**Предварительные знания:** Р4.15, Р3.07; confirm project identity.

**Результат обучения:** Идентифицировать проект и выбранный flow, сравнивать одинаковый scope и не подменять документацию испытанием.

## 1. Инженерная проблема и определения

Имя specs.md неоднозначно. Публичный кандидат из research — репозиторий fabriqaai/specs.md, описывающий framework с несколькими flows. Совпадение названия не доказывает авторский замысел curriculum; исходный identity-вопрос остаётся открытым.

Далее рассматривается именно этот repo, без объявления его единственной реализацией термина. Исторические claims об ускорении не переносятся в курс как измерения.

Связанные первоисточники и границы их применения: [SRC-406](references.md#src-406). Рабочие модели курса явно отделены от документированных функций продуктов.

## 2. Архитектура и механизм

README разделяет Ideation, Simple, FIRE и AI-DLC. Это разные scope процесса, а не четыре автоматически совместимых режима выполнения. Simple ориентирован на генерацию спецификаций; более полные flows добавляют state, execution и traceability по описанию автора.

```text
выбор flow → его artifacts/state → host integration → review → output
```

Перед trial нужно понять, какие файлы создаются в repo, где хранятся standards, как выбираются agents и что происходит при переключении flow. Эти свойства проверяют в disposable project на закреплённой версии.

## 3. Авторская практическая демонстрация

Для Workbench простая генерация spec может подготовить CLOSE-01..04, но не даёт execution evidence. Если выбран расширенный flow, добавляются этапы планирования, запуска и walkthrough. Их надо сравнить по одинаковым критериям, а не по числу папок.

```text
Simple evaluation: получен ли согласованный contract?
Execution-flow evaluation: получен ли contract + принятый patch + checks?
Общее: actors, state, повтор, audit и независимый oracle.
```

Если сравнивать полный execution-flow с Simple по количеству реализованного кода, единица сравнения изначально несправедлива. Сначала выравнивают scope, затем добавляют недостающие стадии одинаковым способом.

Команды installer из README в урок не превращаются в проверенный tutorial. Npx, расширения и framework не запускались; portability и writes установщика не проверены.

**Среда и статус:** Engineering Workbench — кандидат сквозного проекта; здесь использованы синтетические входы. Схемы, псевдокод и JSON иллюстрируют договорённости. Продукты, агентные процессы, команды и приложение в рамках урока не запускались. Ожидаемые свойства не являются фактическими результатами.

## 4. Production, отказы и сопровождение

Проверьте license, зависимости, install scripts, внешнюю сеть, generated instructions, telemetry и update channel. Для monorepo важны boundaries общего state и владельцы standards. Утверждение автора о brownfield support — повод выбрать испытание, а не доказанный результат на вашем legacy.

В существующем проекте фиксируют исходный commit и совместимость потребителей; в команде — владельца решения и reviewer. Автоматические tests/CI дают evidence в охваченном scope, а человеческий review оценивает намерение и исключения. Полная стоимость включает обучение, настройку, usage, задержку, review, rework и дальнейшие обновления. Secrets и чувствительные payload не помещают в открытые artifacts. Условия остановки и восстановления выбирают до расширения полномочий.

## 5. Trade-offs и альтернативы

| Подход | Когда уместен | Освоение, внедрение и сопровождение / цена компромисса |
|---|---|---|
| Simple spec generation | Только формулирование контракта | Меньше ceremony; execution остаётся вне scope |
| Полный flow выбранного framework | Повторяемый delivery process | Больше artifacts и поддержка state |
| Собственный playbook | Особые ограничения команды | Ясный контроль, собственная цена сопровождения |

Сравнение качественное, без результатов benchmark. Проверяемость оценивают по связи критериев с независимыми checks; безопасность — по реальным границам действий и bypass paths. Перед выбором сопоставляют цену внедрения и поддержки с ценой ручного baseline. Большая автономность и больше артефактов не получают преимущества автоматически.

## 6. Проверка знаний с объяснёнными ответами

### 1. Какой проект выбран кандидатом specs.md?

fabriqaai/specs.md. Его repo существует, но название curriculum само по себе не подтверждает, что автор имел в виду именно этот проект.

### 2. Чем различаются flows в README?

Они имеют разный scope: ideation, генерация specs, адаптивное исполнение и более полный AI-DLC. Это taxonomy автора, а не независимый рейтинг.

### 3. Проверена ли переносимость между hosts?

Нет. Список поддержки в README описывает заявление проекта; для доказательства нужны реальные trials на выбранных версиях.

### 4. Что подтверждает опубликованная install-команда?

Наличие документированного пути установки. Она не доказывает, какие files/network effects будут в конкретной среде без проверки.

### 5. Как оценивать обещанные возможности?

Закрепить версию и общий набор задач; описать успехи, ошибки, ручную работу, безопасность и поддержку отдельно. Не сравнивать flows разного scope как равные.
