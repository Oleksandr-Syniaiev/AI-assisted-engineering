# Р4.16 — Методология 2. GitHub Spec Kit

**Статус:** Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

**Уровень:** Middle–Senior/Tech Lead. **Время:** 30–45 минут, предварительная оценка без пилота.

**Предварительные знания:** Р4.15, Р3.07.

**Результат обучения:** Понимать связь стадий Spec Kit, отделять обновление инструмента от сопровождения спецификации и оценивать выбранную версию на общем кейсе.

## 1. Инженерная проблема и определения

GitHub Spec Kit — открытый toolkit проекта GitHub для структурированной работы с coding agents. Его задача — сделать intent и evidence явными в ходе разработки. Текущая документация описывает несколько процессов, поэтому исторический tutorial нельзя считать неизменной спецификацией всех нынешних возможностей.

В этом уроке рассматривается SDD-процесс из официального overview на дату чтения, без установки CLI. Это документальный разбор реализации, а не доказательство эффективности SDD.

Связанные первоисточники и границы их применения: [SRC-401](references.md#src-401) · [SRC-403](references.md#src-403). Рабочие модели курса явно отделены от документированных функций продуктов.

## 2. Архитектура и механизм

Overview показывает последовательность Specify → Plan → Tasks → Implement → Converge. Эти стадии отвечают за контракт, технический план, декомпозицию, реализацию и согласование итогового состояния. Человек проверяет смысл артефактов; генерация следующего файла не делает предыдущий правильным.

Сопровождение tooling и эволюция feature artifacts — разные loops. Обновление scripts/templates toolkit не согласует автоматически старую spec с изменившимся кодом. Команда выбирает persistence convention и владельца reconciliation.

## 3. Авторская практическая демонстрация

Возьмём CLOSE-01 Workbench. В spec фиксируются actors, состояния, повтор и audit. Plan выбирает transactional boundary. Tasks связывают изменения и checks с критериями. После implementation convergence review ищет непокрытые требования и расхождения.

```text
spec.md: C1..C4 — согласованное поведение
plan.md: компоненты, ограничения и проверяемые решения
tasks.md: работа со ссылками на criteria
evidence: diff/checks на итоговом commit
```

Имена основных артефактов соответствуют документации, но эта раскладка — учебная адаптация. Если C3 о повторе меняется, нужно пересмотреть plan/tasks/tests, а не просто перезапустить последний prompt. Converge не следует трактовать как независимое доказательство полной корректности.

Для реального trial сначала закрепляют release/commit, host, model, baseline, права и разрешённые scripts. Installer не исполнялся; выводов о текущем setup на Windows или других ОС здесь нет.

**Среда и статус:** Engineering Workbench — кандидат сквозного проекта; здесь использованы синтетические входы. Схемы, псевдокод и JSON иллюстрируют договорённости. Продукты, агентные процессы, команды и приложение в рамках урока не запускались. Ожидаемые свойства не являются фактическими результатами.

## 4. Production, отказы и сопровождение

В legacy сохраняйте существующие contracts и выбирайте достаточно лёгкий процесс. В monorepo определите feature scope и владельцев общих файлов. Обновления toolkit проверяются как dependency, generated instructions — как будущая policy. Считайте setup, токены, review, reconciliation и rework; количество integrations в overview не доказывает переносимость вашего проекта.

В существующем проекте фиксируют исходный commit и совместимость потребителей; в команде — владельца решения и reviewer. Автоматические tests/CI дают evidence в охваченном scope, а человеческий review оценивает намерение и исключения. Полная стоимость включает обучение, настройку, usage, задержку, review, rework и дальнейшие обновления. Secrets и чувствительные payload не помещают в открытые artifacts. Условия остановки и восстановления выбирают до расширения полномочий.

## 5. Trade-offs и альтернативы

| Подход | Когда уместен | Освоение, внедрение и сопровождение / цена компромисса |
|---|---|---|
| Ручной spec-anchored | Один понятный процесс | Низкий tooling overhead, больше ручной дисциплины |
| Spec Kit SDD | Нужны стадийные artifacts и шаблоны | Среднее освоение, поддержка версий toolkit и specs |
| Собственный workflow | Особые corporate constraints | Максимальный контроль и собственная цена сопровождения |

Сравнение качественное, без результатов benchmark. Проверяемость оценивают по связи критериев с независимыми checks; безопасность — по реальным границам действий и bypass paths. Перед выбором сопоставляют цену внедрения и поддержки с ценой ручного baseline. Большая автономность и больше артефактов не получают преимущества автоматически.

## 6. Проверка знаний с объяснёнными ответами

### 1. Кто поддерживает Spec Kit?

Проект GitHub с публичным repo и документацией. Release-specific детали проверяются именно для выбранной версии.

### 2. Какой SDD-путь показан в overview?

Specify, Plan, Tasks, Implement и Converge. Дополнительные операции и варианты процесса нужно проверять в документации версии, а не объявлять неизменными.

### 3. Обязателен ли полный процесс для любой правки?

Нет универсального требования. Выбирают подходящий процесс по риску и scope, иначе формальность может превысить цену самой задачи.

### 4. Кто выбирает, как сопровождать specs после выпуска?

Команда выбирает persistence convention и владельцев. Обновление toolkit files не согласует feature artifacts автоматически.

### 5. Что не проверено в уроке?

Установка, совместимость реального host, запуск стадий, timings и качество итогового кода. Документальная карта не заменяет trial.
