Р4.11 — Паттерн 11. Narrow API surface

Статус: Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

Уровень: Middle–Senior/Tech Lead. Время: 30–45 минут, предварительная оценка без пилота.

Предварительные знания: Р4.03; tool contracts, validation, errors and MCP boundary (GAP-08).

Результат обучения: Ограничивать capability на trusted boundary, одновременно сохраняя пригодность tool для реальной задачи.

1. Инженерная проблема и определения

Narrow API surface — принцип предоставлять минимальную предметную возможность, нужную задаче. Вместо произвольного SQL или shell агент получает, например, операцию закрытия заявки с ограниченными аргументами. Это не отдельный протокол и не гарантия безопасности только от красивого имени tool.

Связанные первоисточники и границы их применения: SRC-422 · SRC-410. Рабочие модели курса явно отделены от документированных функций продуктов.

2. Архитектура и механизм

Схема проверяет форму входа; trusted code проверяет identity, tenant, право, состояние и бизнес-предусловия. Возвращаемый результат должен быть достаточным для следующего шага без лишних чувствительных данных. Ошибки различают: invalid input, denied, conflict, temporary failure и unknown outcome.

tool args → schema → authentication/authorization → domain rule
          → atomic effect → minimal result + audit

Описание tool помогает модели выбрать действие. Оно не заменяет access control. OpenAPI описывает параметры и payload интерфейса, но schema не доказывает правильность политики доступа.

3. Авторская практическая демонстрация

Сравним execute_sql(query) и предметный close_request. Второй принимает request ID, expected version и idempotency key; tenant и actor берутся из trusted identity context, а не безусловно из модельного текста.

{
  "request_id": "REQ-17",
  "expected_version": 4,
  "idempotency_key": "close-req17-attempt1"
}

Иллюстративный payload не является готовой API-schema. Если version уже 5, возвращается conflict без скрытого перезаписывания. Если actor не имеет права, запрос отклоняется независимо от пояснений агента. При timeout исход проверяется по idempotency key прежде повтора. Широкий admin tool может оставаться для инженера в отдельном контролируемом контуре, но не нужен агенту этой задачи.

Среда и статус: Engineering Workbench — кандидат сквозного проекта; здесь использованы синтетические входы. Схемы, псевдокод и JSON иллюстрируют договорённости. Продукты, агентные процессы, команды и приложение в рамках урока не запускались. Ожидаемые свойства не являются фактическими результатами.

4. Production, отказы и сопровождение

Слишком узкий API тоже имеет цену: придётся добавлять операции и версионировать контракты. Измеряйте долю задач, завершённых без escape hatch, false denials и работу по сопровождению. Проверяйте rate limits, tenant isolation, transport security и audits; не доверяйте только аргументам, прошедшим JSON validation.

В существующем проекте фиксируют исходный commit и совместимость потребителей; в команде — владельца решения и reviewer. Автоматические tests/CI дают evidence в охваченном scope, а человеческий review оценивает намерение и исключения. Полная стоимость включает обучение, настройку, usage, задержку, review, rework и дальнейшие обновления. Secrets и чувствительные payload не помещают в открытые artifacts. Условия остановки и восстановления выбирают до расширения полномочий.

5. Trade-offs и альтернативы

ПодходКогда уместенОсвоение, внедрение и сопровождение / цена компромисса
Shell/admin SQLИсследование широкого окруженияГибко, максимальная поверхность полномочий
Generic CRUD toolsСтандартные сущностиУмеренная интеграция; бизнес-правила легко обойти
Domain-specific toolsПовторяемая предметная задачаЛучше ограничение эффекта, выше цена API design

Сравнение качественное, без результатов benchmark. Проверяемость оценивают по связи критериев с независимыми checks; безопасность — по реальным границам действий и bypass paths. Перед выбором сопоставляют цену внедрения и поддержки с ценой ручного baseline. Большая автономность и больше артефактов не получают преимущества автоматически.

6. Проверка знаний с объяснёнными ответами

1. Почему узкий API полезен агенту?

Он ограничивает доступные действия и возможный ущерб ошибочного выбора. При этом API должен сохранять способность решить реальную задачу.

2. Является ли JSON-schema авторизацией?

Нет: она проверяет форму. Сервер отдельно проверяет identity, tenant, доступ к объекту и бизнес-правило.

3. Как задавать повтор для side-effecting tool?

Определить идемпотентность, классы ошибок, лимит и выяснение неизвестного исхода. Иначе повтор может создать второй эффект.

4. Когда оправдан широкий shell?

Для инженерной работы в изолированной среде с минимальными правами и review. Он не должен становиться default интерфейсом к production данным.

5. Что нужно для review tool?

Контракт, schema, отрицательные authorization cases, поведение timeout/retry, аудит и реальный permission boundary. Названия tool недостаточно.

7. Итоги и следующий шаг

Ограничивать capability на trusted boundary, одновременно сохраняя пригодность tool для реальной задачи.
