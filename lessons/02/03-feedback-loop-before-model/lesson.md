# Р2.03 — Сначала цикл обратной связи, потом модель

**Статус:** Final; авторский технический и методический self-review. Независимое рецензирование не проводилось.

**Уровень:** Middle–Senior. **Время:** 35–50 минут, оценка без пилота.

**Предварительные знания:** Р1.08, Р2.02.

**Результат обучения:** Спроектировать проверяемый цикл задачи и отделить дефект процесса от ограничения модели.

## 1. Почему смена модели может не помочь

Если команда принимает изменение по сообщению «готово», она не видит, исправлена ли ошибка. Более сильная модель может дать лучший patch, но процесс не различит успешный и неуспешный результат. Поэтому сначала полезно построить наблюдаемый цикл проверки, а затем измерять влияние модели. Это инженерная рекомендация курса, а не универсальный закон порядка внедрения.

## 2. Компоненты обратной связи

**Oracle** — основание, по которому определяют правильность результата. Оно может быть тестом с ожидаемыми значениями, спецификацией, проверкой состояния БД или решением уполномоченного эксперта. Самооценка агента без внешнего основания слабее независимой проверки.

**Baseline** — исходное состояние и его результаты. **Observation** — наблюдение конкретного запуска: exit code, stdout/stderr, diff, ответ API. **Grader** — механизм оценки определённого свойства. В агентной оценке важно различать текст отчёта и итоговое состояние среды. [SRC-103](references.md#src-103)

```text
зафиксировать требование и baseline
          ↓
получить минимальную правку → выполнить неизменный check
          ↑                         ↓
  ошибка реализации ← диагностировать причину
                                    ↓
                       принять / остановить / эскалировать
```

Цикл должен уметь остановиться. Бесконечный retry превращает устойчивый дефект в большой счёт и потерю диагностической информации.

## 3. Разобранная демонстрация

Вход: функция, принимающая пробельный заголовок. Контракт TITLE-01: принимать только строки, у которых после `trim()` остаётся хотя бы один символ. Сохранение исходного текста — отдельное решение.

```javascript
const cases = [
  ['', false], ['   ', false], ['Bug', true],
  ['  Bug  ', true], [null, false], [42, false]
];
function baseline(v) {
  return typeof v === 'string' && v.length > 0;
}
function candidate(v) {
  return typeof v === 'string' && v.trim().length > 0;
}
for (const [input, expected] of cases) {
  console.log({input, expected,
    baseline: baseline(input), candidate: candidate(input)});
}
```

Это иллюстративный JavaScript без зависимостей; для воспроизведения подойдёт современный Node.js с поддержкой `const` и `for…of`. Здесь пример не исполнялся. Ожидаемое различие: baseline принимает `'   '`, candidate отклоняет его. Остальные перечисленные случаи должны сохранить ожидаемый результат. Конечный набор случаев не доказывает корректность для всех возможных значений.

Сначала проверяется, что baseline действительно воспроизводит дефект. Затем применяется минимальная правка. После неё выполняется тот же check и regression suite. Если агент изменил expected на `true`, чтобы получить зелёный результат, исправлен критерий, а не дефект. Изменять oracle допустимо при обнаруженной ошибке требования/теста с отдельным согласованным объяснением.

## 4. Диагностика неудачи

| Наблюдение | Возможная причина | Следующий шаг |
|---|---|---|
| Runner не запускается | Окружение или зависимости | Зафиксировать версию/ошибку; не трактовать как провал алгоритма |
| Тест проходит до правки | Не воспроизводится дефект или слаб oracle | Проверить вход, версию, вызванную функцию |
| Unit test проходит, API принимает пробелы | Проверяется не тот путь | Проследить integration boundary |
| Новое поведение работает, regression падает | Несовместимость изменения | Проверить контракт потребителей |
| Агент пишет «всё прошло», вывода нет | Отчёт без evidence | Запросить реально выполненный check либо отметить отсутствие |

## 5. Когда сравнивать модели

После фиксации задач, oracle, tools, permissions и бюджета меняют одну экспериментальную переменную. Нужны несколько попыток: стохастический результат одной задачи недостаточен для стабильного рейтинга. Метрики включают долю принятых решений, нарушения scope, время, расход, review и rework. При несовпадающих лимитах сравнивается весь процесс, а не только модель.

| Проверка | Освоение / внедрение | Сопровождение | Безопасность / проверяемость | Стоимость и применимость |
|---|---|---|---|---|
| Кодовый тест | Нужен чёткий expected | Поддержка fixtures и oracle | Повторяемая оценка выбранного свойства | Дёшевы повторы; подходит формализуемому поведению |
| Модельный grader | Нужна rubric и калибровка | Дрейф модели и критериев | Возможны bias и ложное согласие | Usage и задержка; полезен текстовым свойствам |
| Human review | Нужна доменная экспертиза | Согласованность reviewer | Видит контекст, подвержен усталости | Дороже и медленнее; нужен неоднозначным решениям |

## 6. Production-контур

В legacy characterization tests отделяют существующее поведение от желаемого изменения. В monorepo проверяют downstream consumers. В CI воспроизводят зафиксированную конфигурацию и сохраняют evidence конкретного commit; результат старой ветки не подтверждает новый merge.

Tests и evals имеют разные границы. Функциональный тест проверяет поведение приложения, agent eval может дополнительно оценивать соблюдение scope и последовательность действий. Необходимо учитывать приватность logs, стоимость повторов и владельца неавтоматизируемого решения. Хороший цикл сообщает, чего он не проверил, и останавливается при нехватке данных или полномочий.

## 7. Проверка знаний с ответами

### 1. Что такое feedback loop здесь?

Цель → действие → наблюдение → проверка → корректировка. Тест должен различать исходный дефект и исправление; иначе зелёный статус не сообщает о решении задачи.


### 2. Почему сначала oracle?

Без критерия невозможно отличить правдоподобный ответ от успеха. Строка «всё прошло» не заменяет exit code, конкретную версию кода и проверенные случаи.


### 3. Какие graders применимы?

Кодовые, model-based и человеческие; выбираются по виду результата. Без исходной точки можно случайно сравнивать разные состояния приложения и приписать эффект модели.


### 4. Когда менять модель?

Когда задача, контекст и средства проверки уже адекватны, а eval показывает ограничение. Например, ошибка PATH говорит о среде, а неправильное значение boolean — о логике или самом expected.


### 5. Что сравнивать?

Pass@1/качество по oracle, latency, usage, review, rework. Установите лимит попыток, времени и расхода; при повторении одной ошибки сохраните evidence и передайте её владельцу.


### 6. Как избежать подгонки?

Зафиксировать eval cases и не менять критерий после результата. Сохраняйте тестовый набор и остальные условия; при изменении oracle объясняйте это отдельным решением.


### 7. Что делать при провале?

Локализовать вход, prompt/context, tools, oracle либо модель. Учитывайте также запрещённые действия и остаточные дефекты: корректный результат с нарушением scope не проходит приёмку.

## 8. Что запомнить

Зафиксируйте oracle, baseline и условия остановки; проверяйте состояние среды. После этого сравнение моделей получает измеримый смысл. Далее разберём границы делегирования.
