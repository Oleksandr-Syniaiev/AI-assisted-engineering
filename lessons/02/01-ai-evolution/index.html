Р2.01 — Эволюция работы с AI: девять уровней

Статус: Final; авторский технический и методический self-review. Независимое рецензирование не проводилось.

Уровень: Middle–Senior. Время: 35–50 минут, оценка без пилота.

Предварительные знания: Раздел 1; понимание diff, тестов и ограниченного изменения.

Результат обучения: Критически оценивать зрелость рабочего процесса AI по наблюдаемым свойствам, а не по числу уровней.

1. Зачем оценивать рабочий процесс

Два инженера используют одну модель. Первый копирует ответ в редактор и оценивает его по внешнему виду. Второй ограничивает изменение модулем, воспроизводит дефект, смотрит diff и повторяет независимую проверку. Модель одинакова, а основания доверять результату различаются. Поэтому полезнее классифицировать процесс по доступным наблюдениям, контролю и воспроизводимости, чем по названию инструмента.

«Девять уровней» ниже — редакционная карта курса. Исходная авторская таксономия и её валидация не установлены. Ступени не являются рейтингом инженеров: для разовой консультации первый вариант может быть достаточен.

У этих строк нет строгого отношения «всё предыдущее включено». Workflow может быть воспроизводимым и при этом полностью последовательным. Несколько агентов могут работать хуже одного при общем mutable state. Карта помогает находить недостающий контроль, а не обосновывать обязательный переход к максимальной автономности.

Anthropic различает заранее заданные пути workflow и системы, где модель динамически определяет дальнейшие действия. Это документированная классификация конкретного автора; она не подтверждает нашу девятиступенчатую таблицу. SRC-101

3. Механизм перехода от ответа к результату

Процесс можно представить цепочкой:

цель → входное состояние → разрешённое действие → наблюдение
     → сравнение с критерием → исправление / приёмка / остановка

Входное состояние включает версию кода и известные ограничения. Действие меняет ограниченную часть среды. Наблюдение сообщает, что произошло. Критерий определяет, достаточно ли этого для приёмки. Обрыв любой связи создаёт неопределённость: например, успешный запуск на другой версии кода не подтверждает текущий diff.

Для развития процесса нужно назвать конкретный разрыв. Если агент не видит файл, дополнительный reviewer не восстанавливает отсутствующие данные автоматически. Если всё время уходит на ручной запуск тестов, разумным следующим шагом может стать обычный script.

4. Разобранный пример: пробельный заголовок

Engineering Workbench — кандидат сквозного проекта. Здесь используется синтетический фрагмент, а не полное приложение:

// baseline: непустая строка из пробелов проходит проверку
function validTitle(value) {
  return typeof value === 'string' && value.length > 0;
}

На первой ступени ответ «используйте trim» — только рекомендация. На третьей инженер получает diff. На пятой можно наблюдать результат локального check. На шестой заранее фиксируются случаи '', ' ', ' Bug ', null и ожидаемые значения false, false, true, false.

Исправленная функция использует value.trim().length > 0 после проверки типа. Это меняет проверку пустоты, но не утверждает, что значение сохраняется в нормализованном виде: возврат boolean не изменяет строку. Для persistence и Unicode-пробелов понадобятся отдельные требования и проверки.

Ожидаемое свойство демонстрации — отклонение пробельного ввода при сохранении допустимого заголовка. В этом уроке код не запускался; числовых результатов эксперимента нет.

6. Применение в production

В legacy сначала зафиксируйте существующее поведение и владельца требований. Иначе автоматизация быстрее распространит неверное представление о продукте. В monorepo локальный успех нужно связать с потребителями изменённого API: библиотечная функция может использоваться десятками сервисов.

Команда хранит критерии и проверку рядом с изменением; CI повторяет объективные проверки, reviewer принимает архитектурное решение. Credentials и внешние действия ограничиваются средой исполнения. Фраза «работай безопасно» не создаёт sandbox.

При сравнении процессов учитывают успешные принятые изменения, review, rework, задержку, usage и сопровождение. Полезный результат пилота — найденное узкое место и измеримый эффект его устранения. Рост числа шагов, токенов или агентов таким результатом не является.

7. Проверка знаний с ответами

1. Что именно классифицируют уровни?

Рабочий процесс и контроль, не способности модели сами по себе. Одинаковая модель может работать в процессах с разными правами и проверками; поэтому оценка должна относиться к целому контуру.

2. Почему это не универсальная maturity model?

Для чисел и границ ступеней не установлено внешнее авторство или валидация. Рабочая шкала полезна для обсуждения пропусков, но не позволяет присвоить компании объективный балл зрелости.

3. Как сравнить два процесса?

Задать наблюдаемые критерии: вход, действия, проверки, контроль и цена отказа. Например, diff показывает внесённое изменение, а regression test проверяет конкретное свойство; одно свидетельство не заменяет другое.

4. Что улучшать первым?

Узкое место, измеренное на реальных задачах. Если задержка находится в review, дополнительные агенты генерации могут только увеличить очередь.

5. Почему высокий уровень может навредить?

Дополнительная оркестрация повышает стоимость и число отказов. Ошибки между ролями и стоимость интеграции способны перекрыть ускорение отдельных шагов.

6. Как проверить прогресс?

Фиксировать baseline и regression evals. Одинаковые входы и oracle позволяют связать изменение исходов с процессом; один удачный запуск слишком вариативен.

7. Какова связь с разделом 3?

Дальше проектируются readiness и steering. Структура контекста и устойчивые правила репозитория делают описанный здесь контроль поддерживаемым при росте проекта.

8. Что запомнить

Оценивайте процесс по наблюдаемым свойствам и цене ошибки. Девять ступеней — карта курса; следующий урок рассматривает выбор режима управления конкретной задачей.

9. Источники и границы проверки

Проверенные ссылки и ограничения. Авторская демонстрация. Источники описывают принципы; учебные классификации и рекомендации явно обозначены как интерпретации. Локальные JavaScript-примеры и агентные сценарии не исполнялись; ожидаемые результаты не представлены как измерения.
