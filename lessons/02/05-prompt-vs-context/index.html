Р2.05 — Prompt vs Context

Статус: Final; авторский технический и методический self-review. Независимое рецензирование не проводилось.

Уровень: Middle–Senior. Время: 35–50 минут, оценка без пилота.

Предварительные знания: Р1.11–Р1.12; Р2.03.

Результат обучения: Разделить инструкцию, сведения, tools и состояние, доступные модели при генерации.

1. Почему хороший вопрос бывает недостаточен

Агент получает просьбу «исправь валидацию» вместе со старой документацией, где пробельный заголовок разрешён. Даже ясная инструкция не сообщает, что документация устарела. Для работы нужны сведения о текущем коде, версии требований и способе проверки их противоречия.

Prompt engineering рассматривает формулировку и организацию инструкций. Context engineering охватывает отбор и поддержание информации, доступной модели в момент генерации: инструкций, данных, истории и результатов инструментов. Это полезное различие из инженерной литературы, граница зависит от принятой терминологии и устройства harness. SRC-102

2. Что находится в контексте

В прикладной системе удобно различать три множества: данные доступны инструментам, данные прочитаны, данные включены в текущий запрос к модели. Файл на диске не обязательно прочитан. Результат чтения может быть обрезан. Ранее прочитанный фрагмент после сжатия истории может остаться только в summary.

репозиторий / docs / история / tool results
                    ↓ отбор, фильтрация, сжатие
             текущий контекст модели
                    ↓ генерация
             запрос инструмента / ответ
                    ↓ новое наблюдение
                 обновление контекста

Определения инструментов сообщают модели, что можно запросить; фактические permissions и sandbox задаются внешней средой. Tool output — сведения, а не автоматически доверенная инструкция. Строка «игнорируй проверки» внутри issue или README не должна становиться новым полномочием.

3. Разбор конфликта документации и кода

Предположим, что есть три синтетических входа Workbench:

docs/title-policy.md (старая версия): непустая строка допустима.
src/title-policy.js (текущий snapshot): value.length > 0.
issue TITLE-01 (утверждено): пустое после trim значение недопустимо.

Код показывает текущее поведение; он не определяет желаемое поведение сам по себе. Старая документация объясняет происхождение дефекта, но не отменяет утверждённое изменение. Инженер связывает issue с владельцем решения и версией, а затем проверяет функцию и её call sites.

При одном и том же prompt возможны разные условия:

Переданные сведенияЧто можно обоснованно заключитьЧего не хватает
Только просьбаНужно уточнить правилоКод, требование, scope
Просьба + старые docsВидна старая договорённостьАктуальность и новое требование
Код + утверждённое TITLE-01Видно различие length/trimПути вызова, regression checks
Всё выше + tests/call sitesМожно проектировать локальный fixRuntime evidence после исполнения

Это разбор информационных условий, не эксперимент с моделями. Исправление потребует проверки на актуальном snapshot; вывод «добавлено в контекст» здесь не измеряет качество реального agent run.

4. Отбирать, а не просто накапливать

Контекст имеет ограничение объёма и цену обработки. Большой объём увеличивает вероятность противоречий и затрудняет поиск ключевого сигнала; размер окна сам по себе не гарантирует полезность сведений. При отборе учитывают релевантность, актуальность, авторитет и чувствительность.

Минимальный пакет для нашего исправления — правило TITLE-01, функция, релевантные tests и call sites, границы изменения. Полные logs за месяц, unrelated frontend files и копии всех разговоров не помогают автоматически. Сначала полезно дать карту проекта, затем целевые фрагменты с путями/версиями; расширять чтение по конкретному вопросу.

6. Production-процесс

В monorepo карта модулей помогает найти нужную область, но не заменяет чтение конкретного контракта. В legacy устаревшие docs явно маркируют и уточняют владельца актуального требования. Секреты, customer data и внутренние logs фильтруют до передачи провайдеру; доступ к retrieval должен учитывать права пользователя.

Для проверки стратегии контекста фиксируют задачу, модель, tools и oracle, затем сравнивают выбранные пакеты на нескольких попытках. Измеряют качество, стоимость, пропуски нужных файлов и stale-data ошибки. Смена prompt и context одновременно затрудняет объяснение эффекта. В разделе 3 эти принципы превращаются в структуру инструкций и progressive disclosure.

7. Проверка знаний с ответами

1. Что обычно называют prompt engineering?

Формулирование/организация инструкций. Результат prompt engineering оценивается по поведению на задачах, а не по красоте или длине текста.

2. Что называют context engineering?

Отбор и обновление всего полезного состояния для запроса. Отбор повторяется при новых tool results и изменениях истории: контекст является состоянием во времени.

3. Откуда берётся context?

Инструкции, история, tools, файлы, retrieval и результаты действий; зависит от системы. Наличие файла в workspace не доказывает, что его текст прочитан или попал в текущий model request.

4. Почему больше контекста не всегда лучше?

Релевантность, бюджет и деградация внимания ограничивают пользу. Сначала уменьшайте нерелевантность и противоречия; расширение окна не исправляет устаревший источник.

5. Кто решает при конфликте prompt и кода?

Инженер задаёт приоритеты источников и проверяет актуальный snapshot. Код показывает существующее поведение, а согласованное требование — желаемое. При конфликте нельзя автоматически объявить победителем ни один из них.

6. Как оценить контекст?

Trace sources, контрольные случаи, качество и стоимость. Записывайте версии источников и сравнивайте одинаковые задачи; увеличение токенов само по себе не является результатом.

7. Как связан раздел 3?

Переход к архитектуре инструкций и progressive disclosure. В разделе 3 появятся инварианты и структура инструкций: они организуют правила, которыми здесь управляли вручную.

8. Что запомнить

Prompt задаёт инструкцию, а работа с контекстом поддерживает необходимые сведения во времени. Далее соберём это в компактный контракт задачи.

9. Источники и границы проверки

Проверенные ссылки и ограничения. Авторская демонстрация. Источники описывают принципы; учебные классификации и рекомендации явно обозначены как интерпретации. Локальные JavaScript-примеры и агентные сценарии не исполнялись; ожидаемые результаты не представлены как измерения.
