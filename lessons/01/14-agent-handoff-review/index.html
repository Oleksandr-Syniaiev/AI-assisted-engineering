AI-ASSISTED ENGINEERING — Р1.14

Передать задачу другому агенту и получить проверку

Разделить выполнение и review, сохранив общее понимание состояния.

Р1.14 · Основы · 40–55 минут. Нужны Р1.08, Р1.09, Р1.12, Р1.13. Демонстрация — последовательная передача, без одновременной записи и без реальных вызовов второго агента.

01

Результат урока

Вы сможете подготовить задачу для другого исполнителя и отдельный запрос на review, зафиксировать проверяемое состояние и разобрать замечание. Второй агент полезен не числом участников, а отдельной попыткой найти ошибку на понятных входах.

02

Почему «проверь за предыдущим» недостаточно

Получатель не знает исходного контракта, текущего diff и условий проверки. Он может довериться финальному сообщению автора, прочитать только его объяснение и подтвердить вывод без кода. В результате появится второй уверенный текст, но не новое доказательство.

Если два агента одновременно редактируют одни файлы, добавляется другая проблема: reviewer читает состояние, которое меняется во время проверки. Для первого раздела выберем простой маршрут — автор заканчивает правку, состояние фиксируется, затем начинается review. Параллельные worktrees и оркестрация будут отдельной темой курса.

03

Роли и ответственность

Исполнитель предлагает изменение и подтверждает его в доступной среде. Reviewer сопоставляет изменение с контрактом, ищет дефекты и оценивает доказательства. Инженер решает, какие замечания принять, достаточно ли проверок и можно ли объединять изменение.

Новый разговор не гарантирует независимость мышления: модель может быть той же, входы могут повторять ошибочное объяснение автора. Поэтому получателю передают прежде всего контракт, код и результаты, а не просьбу «подтверди, что автор прав». Полная независимая экспертиза здесь не заявляется.

text
Контракт → исполнитель → patch и проверки
                              ↓ фиксированное состояние
                         reviewer → замечания
                              ↓
                         инженер → исправление и перепроверка
04

Что передать исполнителю

Пакет включает цель, входы, ограничения и критерии, как в Р1.13. Дополнительно указывают владельца файлов и исходное состояние. Например:

text
Задача: отклонять пробельный title.
Входы: policy.mjs и контракт четырёх случаев.
Границы: только валидатор, без UI и хранилища.
Инварианты: guard типа и нормализация валидной строки.
Проверка: существующий тест, ожидания не ослаблять.
Остановка: конфликт требований или необходимость расширить область.

В Git-проекте пакет указывает commit и имеющиеся незакоммиченные изменения. Если patch ещё не зафиксирован, его нужно описать отдельно. Отсутствие commit нельзя маскировать вымышленным hash.

05

Отдельное поручение на review

Для reviewer полезен другой запрос:

text
Проверь изменение, не редактируя файлы.
Сопоставь контракт, diff и текущую реализацию.
Проверь пробелы, обычную строку и неправильный тип.
Не принимай отчёт автора за доказательство исполнения.
Для замечания укажи место, вход, ожидаемое и фактическое поведение,
последствие и способ проверки исправления.
Если запуски недоступны, явно отметь статический разбор.

Review читает исходную и новую версии, а не только итоговую функцию. Это позволяет заметить удалённый guard. Проверка одного отчёта не выявит изменение, о котором автор забыл сообщить.

06

Демонстрация: правка решает пробелы, но ломает тип

Смоделированный patch:

javascript
function proposed(value) {
  const title = value.trim();
  return title.length ? { ok: true, title } : { ok: false };
}

Пробелы отклоняются. Но для 7 вызов trim() приводит к ошибке вместо {ok:false}. Это не придирка к стилю: нарушен исходный контракт и поведение вызывающего кода.

Хорошее замечание:

text
MAJOR: перед вызовом trim удалена проверка типа.
Вход 7 должен вернуть {ok:false}, но обращение к trim вызовет ошибку.
Восстановить guard до нормализации.
Проверка: существующий wrong-type case вместе с остальными тремя.

Уровень MAJOR — редакционная шкала этого курса, не универсальный стандарт индустрии. Reviewer объясняет последствие, а не только пишет «добавить typeof». Инженер принимает замечание, исполнитель возвращает guard, затем проверяется итоговая версия.

Для фактического corrected из Р1.01 все четыре случая повторно прошли 03.11.2026. Но показанный proposed разобран статически; отдельная агентная проверка и benchmark согласованности reviewers не выполнялись. Журнал

07

Как связать замечание с состоянием

Результат review относится к конкретному commit или явно сохранённому diff. В Git-проекте перед передачей просматривают:

powershell
git log -1 --oneline
git status --short
git diff -- policy.mjs
git diff --cached -- policy.mjs

Команды просмотра применимы только внутри репозитория. Если после review код изменился, прежнее заключение может не охватывать правку. Необязательно повторять всё исследование: нужно перечитать затронутое изменение и выполнить релевантные проверки.

Если reviewer не нашёл дефектов, это означает отсутствие найденных замечаний в заявленном объёме. Это не гарантия отсутствия ошибок. Список прочитанных файлов и выполненных тестов ограничивает вывод.

В существующем продукте reviewer учитывает публичный API, данные пользователей, совместимость и операционные риски. Дополнительный агент не получает секреты и право публикации только потому, что называется reviewer. При небольшом patch цена передачи может превышать пользу; её оценивают по найденным дефектам и времени, а не числу сообщений.

Типичные отказы: reviewer редактирует во время проверки; два исполнителя перезаписывают файлы; замечания не имеют воспроизводимого входа; автор «исправляет» ожидание вместо поведения. Последовательность, ограниченные права и фиксированное состояние делают эти случаи заметными.

09

Вопросы с объяснёнными ответами

1. Новый агент автоматически независим?

Нет. Он может повторить те же предположения. Независимое чтение входов и воспроизведение важнее номера сессии.

2. Зачем reviewer запрет на редактирование?

Чтобы отделить наблюдение от изменения проверяемого состояния. Исправления выполняются после понятного замечания.

3. Почему удаление guard — серьёзная ошибка?

Неправильный тип теперь вызывает исключение вместо предусмотренного отказа. Решение одного случая сломало другой контракт.

4. Что должно быть в полезном замечании?

Место, конкретный вход, ожидаемое и фактическое поведение, последствие и проверка исправления.

5. «Замечаний нет» означает «ошибок нет»?

Нет. Вывод ограничен прочитанным кодом и выполненными проверками. Это нужно явно назвать.

6. Можно менять файлы во время review?

Лучше завершить отдельный этап. Иначе reviewer должен знать, какое состояние он видел и что после него изменилось.

7. Кто принимает изменение?

Инженер или назначенный процесс команды. Агентное заключение — вход решения, а не автоматическое право на merge.

10

Главное и следующий шаг

Передача работает, когда роли, входы, состояние и доказательства явны. В Р1.15 сохраним эти свойства при переносе исполнения в другую среду.
