# Р1.07 — авторская демонстрация

Материал для чтения. Самостоятельных заданий, обязательных файлов и сдачи нет.

## Разбор: Демонстрация: почему статус бывает `MM`

Исходное состояние: `policy.mjs` сохранён в commit. Автор меняет `// baseline` на `// corrected`, делает `git add -- policy.mjs`, затем дописывает `// later note` и сохраняет файл без повторного add.

Ожидаемый статус:

```text
MM policy.mjs
```

Первый `M` обозначает изменение в index относительно commit, второй — в рабочем дереве относительно index. Поэтому staged diff показывает `corrected`, но ещё не показывает `later note`. Эти две буквы относятся к двум сравнениям, а не к двум файлам. [SRC-015](https://git-scm.com/docs/git-status)

Такой случай возникает и с агентом: он мог отредактировать уже подготовленный файл. Нельзя принять staged diff за полный результат его работы.

Для сохранения выбранного состояния:

```powershell
git add -- policy.mjs
git diff --cached -- policy.mjs
git commit -m "Normalize request title before validation"
git status --short
```

Сначала читается подготовленная правка, затем создаётся commit. Перед фиксацией имени файла недостаточно: нужно понимать, какое его содержимое подготовлено. `git add .` менее прозрачен в незнакомом проекте, потому что область включает все подходящие изменения под текущим каталогом.
