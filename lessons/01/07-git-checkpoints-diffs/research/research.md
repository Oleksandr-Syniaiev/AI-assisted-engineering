## 2. Исследовательские вопросы и ответы

Вопросы раздела сформулированы до сбора источников: проблема, определение, механизм, альтернативы, проверяемость, production-риски и зависимости. Ниже — конкретизация для этой темы. **Ответы являются синтезом и инженерной интерпретацией**, кроме прямо выделенных Verified claims в разделе 7. Ссылка означает опору на указанный механизм/ограничение, а не доказательство эффективности предложенной демонстрации.

### Q1. Что показывает status?

Различия состояний и новые отслеживаемые/неотслеживаемые пути; это отправная точка перед review. [SRC-015](https://git-scm.com/docs/git-status)

### Q2. Почему обычный diff пуст после add?

Изменение может находиться в index; для него нужен staged diff. [SRC-016](https://git-scm.com/docs/git-diff)

### Q3. Что фиксирует add?

Содержимое выбранного файла в момент staging, а не все будущие изменения файла. [SRC-017](https://git-scm.com/docs/git-add)

### Q4. Что сохраняет commit?

Подготовленный snapshot; файлы вне него и внешние данные требуют отдельного обращения. [SRC-018](https://git-scm.com/docs/git-commit)

### Q5. Когда использовать restore?

Для оговорённого восстановления содержимого в учебной копии после проверки несохранённых изменений; эффект зависит от flags. [SRC-019](https://git-scm.com/docs/git-restore)

### Q6. Когда полезен revert?

Когда требуется отменяющий commit с сохранением истории; возможные конфликты нужно разрешить и проверить. [SRC-020](https://git-scm.com/docs/git-revert)

### Q7. Как Git связан с доверием к агенту?

Сравнение baseline и результата делает scope reviewable; история сама по себе не доказывает корректность. [SRC-016](https://git-scm.com/docs/git-diff)

## 3. Терминология

Commit — локальный snapshot подготовленного содержимого. Index — staging area. Restore меняет файлы/index; revert создаёт новую запись истории.

Не считать названия интерфейсов разных продуктов эквивалентными. Общая терминология уточняется перед drafting; отдельного GLOSSARY.md пока нет.

## 4. Механизмы и архитектурный разбор

1. Нарисовать три состояния и переходы edit → add → commit; отдельно вынести remote.
2. На двух последовательных правках одного файла показать, что staged и working tree могут различаться.
3. Разобрать непопавший в diff untracked тест и ignored env; проверить оба до фиксации.

Это план объяснения механизмов на учебном примере, а не утверждение о внутреннем устройстве всех инструментов. Для diagram и demonstrations использовать только наблюдаемые границы и явно обозначенные допущения.

## 5. Альтернативы и trade-offs

Матрица — **Interpretation**, исходные механизмы и доступные интерфейсы см. в sources.md. Оценки относительные; количественных benchmark здесь нет.

| Подход | Зачем выбирать | Издержки / failure modes | Где применим |
|---|---|---|---|
| Файловая копия | Просто для первого знакомства | Трудно анализировать последовательность правок | Временный baseline до Git |
| Commit + targeted diff | История и контролируемый scope | Нужна дисциплина staging | Основной рабочий маршрут |
| Restore / revert | Разные способы отмены | Ошибочный выбор теряет работу или создаёт конфликт | После диагностики состояния |

## 6. Production engineering

Перед правками в существующем проекте выделить пользовательские изменения. Не включать .env и несвязанные файлы в commit. В shared branch предпочитать согласованную политику истории; агент не должен выбирать destructive reset вместо анализа. Git не откатывает миграции или внешние сообщения.

До приёмки результата сопоставить scope, актуальный snapshot, diff и проверки. Отчёт о действиях не подменяет evidence; стоимость включает человеческую проверку. За технические права отвечает конфигурация среды, за решение о выпуске — назначенный владелец.

## 8. Неопределённости и следующая проверка

На подготовленном clone прогнать команды отмены и проверить отсутствие несвязанных изменений; tutorial не должен содержать reset --hard как обычный шаг.



Перед drafting: перепроверить time-sensitive страницы; выбрать фактический snapshot; перед публикацией исполняемого примера выполнить команды и негативный сценарий на заявленной платформе; сохранить входы и результаты. Если неизвестен обязательный контракт, пометить drafting заблокированным для практической части, не изобретать API или successful output.

## 9. Авторская практическая демонстрация

**Сценарий:** **Пример состояния:** один файл изменён, часть правки staged, другая часть осталась unstaged. Команды документированы Git; выполнение на реальном репозитории здесь не заявляется.

```text
git status --short
git diff
git diff --staged
```

Автор объясняет три области: HEAD/последний commit, index/staged snapshot и рабочие файлы. Затем демонстрирует выбор отмены: для незакоммиченного участка после чтения diff — targeted `git restore <path>`; для опубликованного изменения — новый отменяющий commit через `git revert <commit>`. Перед потенциально теряющим данные действием показать исходный diff и назвать, какое состояние будет восстановлено.

**Статус и границы:** это сценарий будущего рассказа/показа. Полное приложение Engineering Workbench остаётся кандидатом; scaffold и end-to-end запуск не подтверждены. Отдельно указанное фактическое evidence относится только к конкретному ограниченному примеру и не переносится на приложение.

**Платформа и prerequisites:** до исполнения демонстрации указать целевую ОС/shell, версии, точный snapshot, необходимые fixtures, доступы, сеть и последствия команд. Продуктовые installer/flags и billing проверять по текущей документации выбранного продукта. Команды в примере с явной пометкой «иллюстративный» требуют выполнения автором до публикации урока.

**Ожидаемое и фактическое:** ожидаемые наблюдения задают учебный сценарий. Фактическим результатом считать только наблюдение из зафиксированного локального verification-отчёта; обзор документации или проектирование сценария не означает исполнение. Демонстрация предназначена для объяснения материала и не требует сдачи работы от читателя.
