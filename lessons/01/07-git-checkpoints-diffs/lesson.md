# Git: сохранить рабочую версию и увидеть изменения

Сохранённый файл, подготовленное изменение и commit — три разных состояния.

**Р1.07 · Основы · 45–65 минут.** Предварительно: [Р1.04](../04-files-editor-terminal/index.html), [Р1.06](../06-run-first-application/index.html). Примеры команд: PowerShell или другой shell с установленным Git. GitHub и сеть не нужны.

## Результат урока

Вы сможете прочитать статус файлов, отличить staged от unstaged diff, сохранить осмысленный снимок и выбрать способ отмены. Цель — понимать границу изменения агента: что было до его работы и что именно предлагается принять.

## Почему копии папок недостаточно

Папки `project-final` и `project-final-2` сохраняют файлы, но не объясняют происхождение различий. Если агент поменял валидатор и заодно настройки запуска, инженер должен увидеть оба изменения до принятия. Git связывает снимки состояния с историей и позволяет сравнить их.

Git не проверяет правильность приложения. Commit с ошибкой — такой же снимок, как commit с исправлением. Поэтому точка восстановления и доказательства тестирования нужны одновременно.

## Три области состояния

**Working tree**, рабочее дерево, — файлы, с которыми сейчас работает редактор. **Index**, или staging area, — подготовленное содержимое будущего commit. **Commit** — сохранённый снимок с метаданными и связью с предшествующей историей. `HEAD` обычно указывает на текущий commit через текущую ветку.

```text
Файл на диске ── git add ──→ index ── git commit ──→ новый commit
     │                        │                        │
     └──── unstaged diff ──────┘                        │
                              └──── staged diff ───────┘
```

`git add` не просто ставит галочку рядом с файлом: он подготавливает его содержимое на этот момент. Если затем снова изменить файл, новая правка не попадёт в index автоматически. Документация `git diff` определяет сравнения отдельно. [SRC-016](https://git-scm.com/docs/git-diff)

## Откуда берётся первый снимок

В демонстрации автора Git создаётся только в отдельной копии учебного стенда. Это важно: вложенный репозиторий в чужом проекте может скрыть файлы от ожидаемого workflow. Следующие команды относятся к корню такой копии, а не к корню курса; вручную эта последовательность не исполнялась, механизм init/add/commit проверен изолированным сценарием ниже.

```powershell
git init --initial-branch=main
git status --short
git add -- .gitignore policy.mjs server.mjs client.html workbench.test.mjs README.md
git diff --cached
git commit -m "Save runnable teaching baseline"
```

Перед первым commit Git должен знать имя и email автора. Если они ещё не настроены, Git сообщит об этом. Команды `git config --local user.name` и `git config --local user.email` с согласованными значениями задают идентичность только этого репозитория; это не вход в GitHub. Реальный email читателя в материалах не задаётся. Файлы данных исключены `.gitignore`, а явный список add помогает заметить состав снимка. Перед commit также выполняется проверка стенда из Р1.06.

Теперь есть исходный commit, с которым можно сравнивать следующее изменение. Исполнитель начинает с просмотра статуса; непустой статус означает, что в рабочем каталоге уже есть работа, которую нельзя молча присвоить или удалить.

## Как прочитать изменение

Предусловия примера: отдельный учебный Git-репозиторий с существующим первым commit и файлом `policy.mjs`. Эти команды не нужно применять к корню курса, если он не является Git-репозиторием.

```powershell
git status --short
git diff -- policy.mjs
git diff --cached -- policy.mjs
git diff HEAD -- policy.mjs
```

Обычный `git diff` сравнивает рабочее дерево с index. `--cached` сравнивает index с `HEAD`. `git diff HEAD` показывает совокупные отличия отслеживаемого файла от текущего commit. Новые неотслеживаемые файлы обычный diff не показывает: для них нужен `status` и чтение содержимого.

Двойной дефис отделяет имена файлов от параметров и ревизий. В unified diff строка с `-` была в старой версии, с `+` появилась в новой. Заголовки `---`, `+++` и `@@` относятся к формату сравнения, а не являются строками программы.

## Демонстрация: почему статус бывает `MM`

Исходное состояние: `policy.mjs` сохранён в commit. Автор меняет `// baseline` на `// corrected`, делает `git add -- policy.mjs`, затем дописывает `// later note` и сохраняет файл без повторного add.

Ожидаемый статус:

```text
MM policy.mjs
```

Первый `M` обозначает изменение в index относительно commit, второй — в рабочем дереве относительно index. Поэтому staged diff показывает `corrected`, но ещё не показывает `later note`. Эти две буквы относятся к двум сравнениям, а не к двум файлам. [SRC-015](https://git-scm.com/docs/git-status)

Такой случай возникает и с агентом: он мог отредактировать уже подготовленный файл. Нельзя принять staged diff за полный результат его работы.

Для сохранения выбранного состояния:

```powershell
git add -- policy.mjs
git diff --cached -- policy.mjs
git commit -m "Normalize request title before validation"
git status --short
```

Сначала читается подготовленная правка, затем создаётся commit. Перед фиксацией имени файла недостаточно: нужно понимать, какое его содержимое подготовлено. `git add .` менее прозрачен в незнакомом проекте, потому что область включает все подходящие изменения под текущим каталогом.

## Как выбрать отмену

| Состояние | Что нужно сделать | Подход |
|---|---|---|
| Ошибочно подготовили файл | Убрать из index, сохранить текст на диске | `git restore --staged -- policy.mjs` |
| Нужна старая версия файла на диске | Отказаться от выбранных несохранённых в commit правок | Сначала сохранить нужное, затем осознанно выбрать restore |
| Ошибка уже опубликована в истории | Добавить обратное изменение без переписывания истории | `git revert` нужного commit |

`restore --staged` и восстановление рабочего файла — разные операции. Первая сохраняет текущий текст на диске. Вторая может уничтожить незакоммиченные правки, поэтому её не применяют вслепую к работе пользователя. [SRC-019](https://git-scm.com/docs/git-restore)

`git revert` создаёт новый commit, отменяющий эффект выбранного. Он может потребовать разрешения конфликтов; это не универсальная кнопка возврата всей среды, БД или внешних действий. [SRC-020](https://git-scm.com/docs/git-revert)

## Production и альтернативы

Перед поручением агенту инженер фиксирует исходный commit и смотрит существующие изменения. Чужая незавершённая работа не становится частью агентного patch автоматически. После работы проверяют все изменённые и новые файлы, а также тесты на том же состоянии.

| Критерий | Копия папки | Локальный commit | Ветка и review |
|---|---|---|---|
| Применение | Разовый ручной снимок | Контролируемое изменение | Совместная работа |
| Освоение | Простое копирование | Index, diff, история | Ветки и интеграция |
| Внедрение | Место для копий | Git-репозиторий | Общие правила команды |
| Сопровождение | Путаница версий | Понятные commits | История и обсуждения |
| Безопасность | Копируются и секреты | Проверять состав commit | Права публикации и защиты |
| Проверяемость | Ручное сравнение | Точный diff | Diff плюс проверка команды |
| Стоимость | Растёт с числом копий | Небольшая дисциплина | Review и интеграция |

Не весь каталог стоит версионировать: локальные данные и секреты не нужны в истории. Стенд содержит `.gitignore` для `data/`. Ignore не удаляет секрет, если он уже попал в commit; публикацию проверяют отдельно.

## Вопросы с объяснёнными ответами

### 1. Сохранение файла в редакторе создаёт commit?

Нет. Оно меняет рабочее дерево. Index и история обновляются отдельными операциями.

### 2. Почему staged diff не показывает последнюю правку?

Она могла появиться после `git add`. Index хранит подготовленное содержимое, а не живую ссылку на файл.

### 3. Обычный diff пуст. Изменений точно нет?

Нет. Могут быть staged или untracked файлы. Нужны `status` и оба вида diff.

### 4. Что означает `MM`?

Файл отличается от commit в index и отдельно отличается от index в рабочем дереве.

### 5. Unstage удаляет текст файла?

`restore --staged` меняет index. Текущий текст остаётся на диске; восстановление рабочего дерева — другая операция.

### 6. Commit означает, что тесты прошли?

Нет. Нужны команда, результат и связь запуска с этим состоянием кода.

### 7. Когда полезен revert?

Для обратного изменения уже разделяемой истории. Он добавляет commit и не отменяет внешние эффекты приложения.
