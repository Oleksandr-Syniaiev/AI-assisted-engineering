# Длинная переписка, сжатие истории и продолжение работы

Сохранить состояние задачи так, чтобы продолжение не зависело от памяти разговора.

**Р1.12 · Основы · 35–50 минут.** Нужны [Р1.07](../07-git-checkpoints-diffs/index.html), [Р1.11](../11-agent-context/index.html). Пример — передача состояния после исправления заголовка. Compaction и продолжение клиента описаны документально, без эксперимента с моделью.

## Результат урока

Вы сможете выбрать между продолжением сессии, сжатием истории и новым разговором; составить передачу состояния; отличить старый результат проверки от актуального. Главное — сохранять факты проекта отдельно от рассказа о них.

## Почему длинный чат становится ненадёжным журналом

В одном разговоре обсуждались три подхода, два были отменены, тест падал из-за пути, затем прошёл, после этого код ещё менялся. Просьба «продолжай» требует восстановить, какое решение действует сейчас. История содержит и полезные факты, и уже неверные намерения.

Проблема не только в размере окна. Даже человек тратит время на чтение старых вариантов. Поэтому передача должна описывать текущее состояние, а не пересказывать все сообщения по порядку.

## Три независимых состояния

**Состояние проекта** — реальные файлы, commits и незавершённые изменения. **Состояние процессов** — запущенный сервер, данные в памяти и внешние ресурсы. **Состояние разговора** — сообщения, инструменты и сохранённые оболочкой сведения. Новая сессия не откатывает файлы; продолжение старой не гарантирует, что прежний сервер ещё работает.

**Compaction** — сжатие старого контекста для продолжения длинной работы. Это термин продукта: например, официальный глоссарий Codex описывает его как суммирование прежнего контекста. Не следует считать summary побитовой копией всей истории. [SRC-040](https://learn.chatgpt.com/docs/glossary)

**Handoff**, передача состояния, — подготовленное описание цели, текущих фактов, решений и следующего шага. В этом уроке это инженерный документ, а не специальная команда или протокол конкретного клиента.

```text
Прошлая работа → файлы и commits → текущее состояние
            └→ handoff: что известно и почему
                                      ↓
Новая сессия → чтение handoff → сверка с проектом → продолжение
```

## Когда продолжать, когда начать заново

Продолжение удобно, пока задача та же и контекст ещё полезен. Compaction позволяет сохранить рабочее направление при росте истории, но после него важные ограничения стоит сверить с устойчивыми документами. Новый разговор полезен при смене задачи, путанице старых решений или необходимости отдельной проверки.

Начинать заново без передачи — значит потерять основания, а не получить «свежую память бесплатно». Продолжать бесконечно без фиксации состояния — значит накапливать противоречия. Решение выбирают по содержанию задачи, а не фиксированному числу сообщений.

## Демонстрация: хорошая передача после дефекта

Плохая запись:

```text
Всё почти готово. Пробелы исправили. Тесты зелёные, продолжи.
```

Неизвестны файл, контракт, команда, ревизия и остаток работы. Получатель может принять старый прогон за новый или исправить уже исправленную функцию.

Разобранный handoff для ситуации Р1.08:

```text
Цель: отклонять пустой после trim заголовок.
Контракт: только string; нормализация до проверки;
" Fix CI " → "Fix CI"; 7 → отказ.
Код-пример: lessons/01/01-agent-basics/practice/title-policy.mjs.
Baseline и corrected сохранены раздельно, первый намеренно ошибочный.
Проверка автора 03.11.2026, Node.js v24.22.1:
baseline 3/4, exit 1; corrected 4/4, exit 0.
Это проверка функции, не браузера и не сохранения.
Следующий шаг: проверить подключение правила в HTTP-стенде.
Ограничение: файлы Р1.01 не переписывать.
```

Это пример передачи существующих фактов, а не отчёт отдельного агента. В рабочем Git-проекте добавляют текущий commit и вывод `git status`. Если изменения не закоммичены, перечисляют их явно: commit не описывает рабочее дерево целиком.

Полезно сохранить ещё нерешённый вопрос и условие остановки: например, «если контракт API расходится с правилом, не менять ожидания без решения». Иначе получатель будет вынужден заново угадывать границы полномочий.

## Сверка перед продолжением

Получатель читает handoff как карту, а не как абсолютную истину. Проверяет, существуют ли файлы, совпадает ли текущая ревизия, не изменились ли незавершённые правки. Затем перечитывает нужные строки кода и выбирает следующий узкий шаг.

В Git-проекте из корня используются команды просмотра:

```powershell
git log -1 --oneline
git status --short
git diff --stat
```

Эти команды применимы только при наличии Git-репозитория. Они не запускались в корне курса, который не является таким репозиторием. Текущий сервер проверяется отдельно: факт его запуска в старом чате не доказывает доступность сейчас.

Если summary утверждает «тесты прошли», а diff показывает последующие изменения, запись остаётся историческим наблюдением. Её нельзя стирать, но для приёмки нужно выполнить релевантную проверку заново. Сжатие не обновляет факты проекта.

## Production и альтернативы

| Критерий | Продолжить разговор | Compaction | Новый разговор с handoff |
|---|---|---|---|
| Применение | Та же короткая задача | Длинная связная работа | Новый этап или проверка |
| Освоение | Минимальное | Понять ограничения summary | Уметь передавать факты |
| Внедрение | Продолжение в клиенте | Поддержка продукта | Документ и чтение входов |
| Сопровождение | Следить за старыми решениями | Сверять важные ограничения | Поддерживать свежесть handoff |
| Безопасность | История содержит прежние данные | Секреты могут попасть в summary | Передавать только нужное |
| Проверяемость | История длинная | Детали могли сократиться | Явные пути, ревизии, доказательства |
| Стоимость | Растущий контекст | Расход на сжатие зависит от продукта | Подготовка и повторное чтение |

Для команды handoff особенно полезен при смене исполнителя и после перерыва. Он уменьшает повторное исследование, но требует поддержки: документ со вчерашним состоянием не должен выглядеть как текущая истина. Лучше короткая датированная передача с ограничениями, чем длинный рассказ «как всё происходило».

Типичные отказы: перенос отвергнутого решения как действующего; потеря запрета на внешние действия; забытые незакоммиченные файлы; прежние тесты, приписанные новой ревизии. Их предотвращают конкретные поля состояния, а не фраза «ничего не забудь».

## Вопросы с объяснёнными ответами

### 1. Новый чат возвращает файлы в исходное состояние?

Нет. Файловая система независима от истории разговора. Состояние проекта нужно проверить отдельно.

### 2. Compaction гарантирует сохранение каждой детали?

Нет. Это сокращённое представление. Критичные правила и доказательства должны быть доступны в устойчивых артефактах.

### 3. Почему недостаточно написать «тесты зелёные»?

Неизвестны тест, ревизия и последующие изменения. Нужно привязать наблюдение к конкретному состоянию.

### 4. Следует пересказывать весь чат в handoff?

Нет. Нужны действующая цель, факты, решения, ограничения и следующий шаг. Отменённые варианты отмечают только при необходимости.

### 5. Получатель может доверять summary без чтения кода?

Для важного решения — нет. Summary помогает найти входы; текущее состояние может уже отличаться.

### 6. Что делать с незакоммиченными правками?

Перечислить их и сохранить факт их наличия. Один commit не представляет рабочее дерево с такими изменениями.

### 7. Зачем указывать, что не проверено?

Чтобы продолжение закрывало реальные пробелы и не принимало отсутствие наблюдений за успех.

## Главное и следующий шаг

Разговор помогает работать, но файлы и проверенные артефакты удерживают состояние. Далее [Р1.13](../13-reusable-prompt/index.html) превратит удачное поручение в переносимый шаблон без старых фактов и секретов.
