# Р1.13 — исследование

Сохранить удачный запрос в репозиторий

## 1. Паспорт и границы

Статус: исследование и план, не готовый урок. Дата проверки источников: 02.11.2026. Продуктовые факты подтверждены чтением указанных разделов документации, но доступность на аккаунте и конкретная версия клиента не проверялись. Полная демонстрация, установка клиентов и облачное исполнение не выполнялись.

Проблема: Удачный одноразовый запрос трудно повторить, а копирование всей переписки переносит случайные пути, устаревшие решения и лишний scope.

Prerequisites: [Р1.07](../../07-git-checkpoints-diffs/research/outline.md), [Р1.08](../../08-change-verify-fix/research/outline.md), [Р1.11](../../11-agent-context/research/outline.md)

Ориентировочное время будущего урока: 60–90 минут; оценка автора плана, без пилотирования.

Целевые результаты:

- Превратить запрос в параметризуемый и проверяемый repo artifact
- Различить prompt template, постоянные инструкции и исполняемую автоматизацию

Граница: один аспект раздела 1; SDD, сложные hooks, worktrees, параллельная оркестрация и production deployment остаются в последующих разделах. Сквозной пример — предложенный в COURSE_OVERVIEW.md **Engineering Workbench**, пока кандидат, а не утверждённая реализация.

## 2. Исследовательские вопросы и ответы

Вопросы раздела сформулированы до сбора источников: проблема, определение, механизм, альтернативы, проверяемость, production-риски и зависимости. Ниже — конкретизация для этой темы. **Ответы являются синтезом и инженерной интерпретацией**, кроме прямо выделенных Verified claims в разделе 7. Ссылка означает опору на указанный механизм/ограничение, а не доказательство эффективности предложенной демонстрации.

### Q1. Что сохранять из удачного запроса?

Цель, входы, placeholders, ограничения, критерии проверки результата и формат evidence; случайный контекст одной попытки исключить. [SRC-023](https://code.claude.com/docs/en/best-practices)

### Q2. Почему файл не применяется сам?

Произвольный Markdown не означает подключённую автоматизацию; нужен явный вызов или documented loader. [SRC-027](https://code.visualstudio.com/docs/agent-customization/prompt-files)

### Q3. Что относится к AGENTS.md?

Постоянные ожидания проекта в рамках documented discovery, а не все разовые задания. [SRC-026](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

### Q4. Как отличаются инструкции и memory?

Они имеют разное происхождение и назначение; автор запроса должен управлять источником постоянных правил. [SRC-025](https://code.claude.com/docs/en/memory)

### Q5. Как проверить переносимость шаблона?

В новой сессии заполнить placeholders для другой ограниченной задачи и проверить, что не остались прежние paths/IDs. [SRC-027](https://code.visualstudio.com/docs/agent-customization/prompt-files)

### Q6. Как версионировать?

Хранить template с причиной изменения и контрольным примером; менять через diff review как иной repo artifact. [SRC-023](https://code.claude.com/docs/en/best-practices)

### Q7. Когда шаблон не лучший путь?

Для полностью формализованной операции нужен script, для проекта — instructions, для процедур с tools позже — workflow/skill. [SRC-027](https://code.visualstudio.com/docs/agent-customization/prompt-files)

## 3. Терминология

Файл prompts/change-request.md ниже — переносимый рабочий формат курса, который нужно явно прочитать. .prompt.md в поддерживаемом VS Code Local harness — отдельный механизм вызова.

Не считать названия интерфейсов разных продуктов эквивалентными. Общая терминология уточняется перед drafting; отдельного GLOSSARY.md пока нет.

## 4. Механизмы и архитектурный разбор

1. Запрос разделяется на стабильный контракт и параметры конкретной задачи.
2. Шаблон читается и заполняется; если неизвестно обязательное поле, выполнение останавливается для уточнения.
3. Версия template связывается с примером использования и результатом; один успех не делает шаблон универсальным.

Это план объяснения механизмов на учебном примере, а не утверждение о внутреннем устройстве всех инструментов. Для diagram и demonstrations использовать только наблюдаемые границы и явно обозначенные допущения.

## 5. Альтернативы и trade-offs

Матрица — **Interpretation**, исходные механизмы и доступные интерфейсы см. в sources.md. Оценки относительные; количественных benchmark здесь нет.

| Подход | Зачем выбирать | Издержки / failure modes | Где применим |
|---|---|---|---|
| Обычный Markdown + явное чтение | Переносим между file-aware агентами | Нет автоматической загрузки | Основной маршрут раздела 1 |
| VS Code prompt file | Удобный документированный вызов | Зависит от Local harness и версии | Дополнительный IDE маршрут |
| Project instructions | Постоянный контекст | Может засоряться разовыми задачами | Только общие правила проекта |

## 6. Production engineering

Шаблоны должны обновляться вместе с API и commands; устаревший prompt способен массово повторять дефект. В monorepo проверять относительные paths и область инструкций. Secrets не являются параметрами для сохранения в Git. Code review включает scope и oracle шаблона.

До приёмки результата сопоставить scope, актуальный snapshot, diff и проверки. Отчёт о действиях не подменяет evidence; стоимость включает человеческую проверку. За технические права отвечает конфигурация среды, за решение о выпуске — назначенный владелец.

## 8. Неопределённости и следующая проверка

Сверить правила loader выбранного клиента; native .prompt.md не объявлять универсальным форматом.



Перед drafting: перепроверить time-sensitive страницы; выбрать фактический snapshot; перед публикацией исполняемого примера выполнить команды и негативный сценарий на заявленной платформе; сохранить входы и результаты. Если неизвестен обязательный контракт, пометить drafting заблокированным для практической части, не изобретать API или successful output.

## 9. Авторская практическая демонстрация

**Сценарий:** **Разбираемый переносимый шаблон:**

```markdown
# Change request
Goal: {{observable_behavior}}
Inputs: {{paths_and_examples}}
Scope: {{allowed_paths}}
Constraints: preserve {{invariants}}; do not {{forbidden_actions}}
Verification: run {{existing_check}} and report exact command/result
Uncertainty: ask before changing {{ambiguous_contract}}
```

Автор отдельно показывает: файл-шаблон вызывается явно/поддерживаемым loader; постоянные требования проекта живут в project instructions вроде документированного `AGENTS.md`; разовый параметр не стоит превращать в глобальное правило. Сопоставить этот template с platform-specific prompt files и отметить, что plain Markdown сам не загружается автоматически.

**Статус и границы:** это сценарий будущего рассказа/показа. Полное приложение Engineering Workbench остаётся кандидатом; scaffold и end-to-end запуск не подтверждены. Отдельно указанное фактическое evidence относится только к конкретному ограниченному примеру и не переносится на приложение.

**Платформа и prerequisites:** до исполнения демонстрации указать целевую ОС/shell, версии, точный snapshot, необходимые fixtures, доступы, сеть и последствия команд. Продуктовые installer/flags и billing проверять по текущей документации выбранного продукта. Команды в примере с явной пометкой «иллюстративный» требуют выполнения автором до публикации урока.

**Ожидаемое и фактическое:** ожидаемые наблюдения задают учебный сценарий. Фактическим результатом считать только наблюдение из зафиксированного локального verification-отчёта; обзор документации или проектирование сценария не означает исполнение. Демонстрация предназначена для объяснения материала и не требует сдачи работы от читателя.
