# Сохранить удачный запрос в репозиторий

Сохранить способ работы, убрав случайные факты прошлой задачи.

**Р1.13 · Основы · 35–50 минут.** Нужны [Р1.08](../08-change-verify-fix/index.html), [Р1.11](../11-agent-context/index.html), [Р1.12](../12-long-session-handoff/index.html). Пример — обычный Markdown-шаблон, а не автоматически исполняемая команда.

## Результат урока

Вы сможете выделить повторяемую часть поручения, определить переменные и проверить переносимость шаблона. Также сможете отличить шаблон задачи от постоянных инструкций проекта, handoff и skill.

## Почему копирование старого сообщения не всегда работает

Удачный запрос содержал правильный путь, актуальную ошибку, точный тест и ограничение области. Через неделю другой дефект находится в другом модуле. Если скопировать сообщение целиком, агент может исправить прежнюю функцию или объявить чужой результат проверки своим.

Сохранять нужно структуру работы: входы, цель, контракт, границы, доказательства. Исторические факты остаются в отчёте прошлой задачи. Их перенос в шаблон превращает удобство в источник устаревшего контекста.

## Четыре разных артефакта

**Шаблон запроса** описывает тип повторяемой задачи и места для текущих значений. **Постоянные инструкции** описывают устойчивые правила проекта: соглашения и обязательные проверки. **Handoff** фиксирует конкретное текущее состояние. **Skill** в поддерживающем его клиенте может поставлять инструкции и вспомогательные ресурсы для определённого workflow. Формат и загрузка skill зависят от экосистемы; обычный файл сам по себе им не становится.

```text
Правила проекта → действуют для многих задач
Шаблон         → создаёт текущее поручение
Handoff        → объясняет состояние одной работы
Отчёт          → сохраняет её фактические результаты
```

Codex имеет документированный загрузчик `AGENTS.md`. VS Code отдельно поддерживает prompt files. Это разные механизмы, и их соглашения о путях и запуске нельзя переносить между клиентами без проверки. [SRC-026](https://learn.chatgpt.com/docs/agent-configuration/agents-md) [SRC-027](https://code.visualstudio.com/docs/agent-customization/prompt-files)

## Из разового запроса в шаблон

Исходное удачное поручение:

```text
В policy.mjs исправь принятие пробельного title.
Сохрани guard типа и нормализацию. Проверь четыре случая.
Не меняй ожидания ради зелёного результата.
```

Что здесь повторяемо? Требование сначала понять контракт, сохранить инварианты, сделать узкую правку и проверить. Что переменно? Файл, дефект, случаи и команда. Что нельзя обобщать бездумно? `trim()` — часть конкретного правила заголовка. Для пароля или исходного текста пробелы могут быть значимыми.

Полный авторский шаблон:

```markdown
# Исправление локального дефекта
Цель: {{наблюдаемое неверное поведение}}.
Входы: {{пути к коду, контракту и проверкам}}.
Исходное состояние: {{commit и существующие изменения}}.
Ожидаемое поведение: {{входы и правильные результаты}}.
Границы: {{разрешённые файлы и запрещённые действия}}.

Сначала свяжи дефект с кодом и воспроизведи его.
Если требования противоречат, покажи конфликт до изменения поведения.
Предложи минимальную достаточную правку.
Сохрани перечисленные инварианты: {{что не должно измениться}}.
Проверка: {{команда, рабочий каталог, предусловия}}.
Не меняй ожидания только ради прохождения тестов.

Отчёт: причина, изменённые файлы, команды и фактические результаты;
непроверенные свойства и препятствия.
Остановка: {{когда нужны новые данные или решение инженера}}.
```

Двойные фигурные скобки — условные обозначения автора. Это не API и не гарантированная подстановка клиента. В простом Markdown их заменяет человек до отправки.

## Разобранное заполнение для Workbench

Цель — отказ для `"   "`. Входы — `policy.mjs` и соответствующие тесты. Контракт — только строка, `trim()` до проверки непустоты. Инвариант — число отклоняется, валидный заголовок нормализуется. Границы — не трогать UI и хранилище, не устанавливать зависимости. Проверка — локальный тест контракта в документированном каталоге.

Теперь заменим задачу на ошибку сохранения. Хороший шаблон остаётся полезен, но значения полей меняются: входы включают сервер и файл данных, проверка — перезапуск и GET, инвариант — не терять существующие записи. Если в шаблоне осталось «четыре случая title», переносимость не достигнута.

Эта проверка выполнена как редакционный разбор двух сценариев. Модель не запускалась, улучшение скорости не измерялось. Фактические тесты валидатора и стенда находятся в отдельном журнале, а не являются результатом самого шаблона.

## Где хранить и как использовать

Например, в отдельном проекте файл `prompts/fix-local-defect.md` можно версионировать рядом с README. Это предложенный путь, не существующая автоматическая точка загрузки. Перед использованием читают текущий файл, заполняют поля и передают текст клиенту выбранным способом.

Сохранение в Git полезно потому, что изменения шаблона видны в diff. Если новая редакция убрала проверку guard или границы записи, команда это заметит. Но наличие файла в commit не доказывает, что агент его прочитал: способ использования должен быть явным.

Полезный критерий качества — другой инженер понимает, какие поля заменить, по какой команде проверить и когда остановиться. «Ты лучший эксперт, сделай идеально» этих сведений не добавляет.

## Production и альтернативы

| Критерий | Копия из чата | Markdown-шаблон | Клиентский prompt file |
|---|---|---|---|
| Применимость | Разовая похожая задача | Командный переносимый маршрут | Частое использование в одном клиенте |
| Освоение | Минимальное | Поля и контракт | Синтаксис и вызов продукта |
| Внедрение | Ручной поиск истории | Файл и инструкция применения | Настройка поддерживаемого пути |
| Сопровождение | Старые факты незаметны | Diff и версии | Формат плюс совместимость клиента |
| Безопасность | Риск скопировать секрет | Не включать личные данные | Проверить scope и подстановки |
| Проверяемость | Нет устойчивой версии | Можно связать запуск с редакцией | Версия файла и клиентский вызов |
| Стоимость | Мало setup, больше ошибок переноса | Поддержка небольшого документа | Удобство за цену привязки к продукту |

В production не делают один огромный шаблон на все задачи. Поля должны соответствовать процессу и позволять остановиться при конфликте. Правила безопасности живут в технических ограничениях и политиках проекта; шаблон не даёт новых полномочий.

При обновлении проверяют несколько разных задач. Успех на одном примере не доказывает универсальность. Избыточные пункты увеличивают чтение и стоимость контекста, а слишком общие скрывают важные предусловия.

## Вопросы с объяснёнными ответами

### 1. Что сохранять из удачного поручения?

Повторяемые цель, структуру входов, ограничения, проверку и отчёт. Конкретные пути и факты делают переменными.

### 2. Почему не оставить `trim()` во всех исправлениях ввода?

Это правило конкретного поля. Для других данных оно может изменить смысл и создать дефект.

### 3. Шаблон загружается автоматически из любой папки?

Нет. Обычный Markdown используют явно. Автоматическая загрузка требует документированного механизма клиента.

### 4. Чем шаблон отличается от handoff?

Шаблон описывает тип задачи, handoff — состояние конкретной работы. Подмешивание старых результатов в шаблон создаёт ложные факты.

### 5. Зачем версия шаблона?

Чтобы видеть изменения процесса и связывать наблюдения с конкретной редакцией. Сам номер версии не доказывает эффективность.

### 6. Фигурные скобки гарантируют подстановку?

Нет. Здесь это авторская нотация. Подстановку делает человек или отдельно реализованный механизм.

### 7. Как проверить переносимость без AI-вызова?

Заполнить шаблон для двух различных дефектов и проверить, не осталось ли прежних путей, правил и результатов. Это редакционная проверка, не benchmark.

## Главное и следующий шаг

Переносимый запрос сохраняет способ принятия решения и требует свежих фактов. Далее [Р1.14](../14-agent-handoff-review/index.html) используем эту дисциплину при передаче работы другому агенту.
