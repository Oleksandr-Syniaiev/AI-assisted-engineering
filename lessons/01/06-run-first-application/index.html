Р1.06 · Основы · 45–65 минут. Предварительно: Р1.03, Р1.04, Р1.05. Демонстрация: Windows, PowerShell, Node.js v24.22.1. Установка пакетов и платный AI-доступ не нужны.

01

Результат урока

Вы сможете запустить учебное приложение, отличить доступность страницы от исправного сохранения, проверить отрицательный сценарий и прочитать ошибку окружения. Все действия ниже — разобранная авторская демонстрация, без обязательной самостоятельной работы.

02

Что именно запускаем

В разделе появился учебный стенд: браузерная форма, Node.js-сервер и JSON-файл. Он использует стандартную библиотеку Node.js. Здесь нет сборщика, npm-зависимостей, учётных записей и production-развёртывания. Engineering Workbench остаётся кандидатом полного сквозного проекта; этот стенд реализует только создание и чтение заявок.

text
Редактор и файлы
      ↓ node server.mjs
Процесс на 127.0.0.1:4317
      ↕ HTTP
Браузер → форма → API → data/requests.json

127.0.0.1 — локальный адрес текущего компьютера. 4317 — выбранный номер порта, по которому процесс принимает соединения. Адрес на другом компьютере не указывает на наш сервер. Запуск процесса не публикует приложение в интернете.

03

Подготовка и запуск

Исходные условия: терминал PowerShell открыт в корне курса, файлы стенда присутствуют, Node.js установлен. Проверка версии выполняется до запуска приложения:

powershell
node --version
Get-ChildItem -LiteralPath 'lessons/01/demo-workbench'
node lessons/01/demo-workbench/server.mjs

Ожидаемый вывод сервера:

text
Workbench: http://127.0.0.1:4317 (Ctrl+C — остановить)

Терминал не возвращает приглашение: сервер продолжает работать. Это нормальное поведение длительного процесса. Для следующей команды нужен второй терминал; первый остаётся занят сервером.

Страницу приложения открывают по http://127.0.0.1:4317, а не двойным щелчком по client.html. Через HTTP клиент обращается к API на том же адресе. При открытии через file:// серверного API по этому пути нет. HTML-страницы самих уроков, напротив, предназначены для чтения с диска.

Точка входа команды проверена чтением кода; сам HTTP-сервер проверен интеграционным тестом. Конкретные результаты и ограничения приведены в журнале.

04

Проверка по слоям

Во втором PowerShell проверяется ответ процесса:

powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:4317/health'

Ожидается поле status со значением ok. Пока доказано только то, что процесс отвечает на этот маршрут. Затем читается список:

powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:4317/api/requests'

Если файл ещё не создан, API возвращает пустой массив. Вид вывода PowerShell зависит от форматирования объектов; отсутствие печатных строк не следует автоматически считать отсутствием HTTP-ответа.

Создание заявки:

powershell
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:4317/api/requests' -ContentType 'application/json' -Body '{"title":" Fix CI "}'

Ожидается объект с новым id и title: Fix CI. Пробелы по краям убраны. Каждый новый POST создаёт отдельную запись, поэтому повторение не должно ожидать тот же идентификатор.

После этого проверяется файл:

powershell
Get-Content -LiteralPath 'lessons/01/demo-workbench/data/requests.json'

Путь дан из корня курса. На первом терминале Ctrl+C останавливает сервер. После повторного запуска GET должен вернуть уже сохранённую запись. Так проверяется сохранение между процессами, а не только память одной сессии.

05

Отрицательный сценарий не менее важен

Запрос с {"title":" "} должен получить HTTP 422 и не добавить запись. Запрос со сломанным JSON — 400. В PowerShell неуспешный HTTP-статус может оформляться как ошибка команды; это ожидаемая реакция клиента на отказ API, а не обязательно падение сервера.

В браузере текст ошибки выводится рядом с формой. Значения заявок вставляются через textContent, поэтому введённый текст не интерпретируется как HTML. Но одна такая мера не превращает стенд в безопасный публичный сервис: авторизации и прочих защит здесь нет.

Разобранный запрос агенту:

text
Проверь существующий стенд без изменения кода.
Среда: Node.js; запуск из корня курса.
Нужны: доступность страницы, создание нормализованной заявки,
отклонение пробельного title и чтение после перезапуска.
Не объявляй /health проверкой сохранения.
Укажи команды, результаты и границы проверки.

Этот запрос — образец постановки. Агентное выполнение не проводилось; тесты запускал автор материалов.

06

Автоматическая проверка и фактический результат

Из корня курса:

powershell
node --test lessons/01/demo-workbench/workbench.test.mjs

Набор создаёт временную папку, выбирает свободный локальный порт и удаляет только собственные временные данные. Он не использует пользовательский data/requests.json. Первый тест проверяет контракт заголовка. Второй обращается к настоящему HTTP-серверу, проверяет статусы, файл, перезапуск и отказ при повреждённом JSON.

Фактически: 03.11.2026, Windows, Node.js v24.22.1: 2 теста пройдены, 0 неудачных, exit code 0. Первый запуск в ограниченной среде не прошёл из-за EACCES при соединении с localhost; после разрешения локального HTTP повторный запуск прошёл. Отказ доступа не был исправлением приложения. Журнал

Эти тесты не подтверждают нагрузку, аварийную сохранность, браузерное поведение и безопасность публичного сервиса. Состав доказательств должен быть уже формулировки «всё работает».

Для существующего production-кода читают его README и скрипты, а не заменяют setup командами стенда. npm install здесь не нужен; в другом проекте установка может быть обязательна. Принцип — выяснить реальную точку запуска и реальные гарантии тестов.

09

Вопросы с объяснёнными ответами

1. Почему терминал не возвращает приглашение?

Сервер продолжает обслуживать запросы. Для новых команд используют второй терминал или останавливают процесс.

2. Почему нельзя открыть клиент как обычный HTML-файл?

Его относительные запросы должны попасть в HTTP API сервера. file:// не предоставляет этот серверный маршрут.

3. Успешный /health подтверждает сохранение?

Нет. Нужны POST, независимое чтение и проверка после перезапуска.

4. Что означает 422 для пробельного заголовка?

API отклонил недопустимое значение по контракту. Это ожидаемый отрицательный результат, а не авария процесса.

5. Что доказывает перезапуск?

Новый процесс смог прочитать запись из файла. Он не доказывает устойчивость к аварии питания и совместную запись.

6. Почему тесты не трогают основной файл данных?

Изоляция делает их повторяемыми и предотвращает смешивание демонстрационных записей с результатами проверки.

7. Что делать при EACCES к localhost?

Разобрать запрет среды и запросить нужное разрешение. Не менять валидатор в попытке исправить сетевую политику.

10

Главное и следующий шаг

Результат запуска — цепочка наблюдений от процесса до сохранённых данных. Следующий Р1.07 покажет, как сохранить исходную версию и увидеть, что изменил агент.
