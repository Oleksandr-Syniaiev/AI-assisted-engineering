## 1. Паспорт и границы

## 2. Исследовательские вопросы и ответы

Вопросы раздела сформулированы до сбора источников: проблема, определение, механизм, альтернативы, проверяемость, production-риски и зависимости. Ниже — конкретизация для этой темы. **Ответы являются синтезом и инженерной интерпретацией**, кроме прямо выделенных Verified claims в разделе 7. Ссылка означает опору на указанный механизм/ограничение, а не доказательство эффективности предложенной демонстрации.

### Q1. Что требуется до запуска?

Предоставленный baseline, README, версии runtime/package manager, lockfile, тестовые данные и ограниченный доступ. [SRC-013](https://docs.npmjs.com/cli/v11/commands/npm-ci/)

### Q2. Почему не устанавливать всё наугад?

Команды установки зависят от manifest; npm ci применим только к совместимому npm-проекту с lockfile. [SRC-013](https://docs.npmjs.com/cli/v11/commands/npm-ci/)

### Q3. Что проверяет HTTP smoke?

Оговорённый контракт запроса/ответа и observable effect; просто открытая страница недостаточна. [SRC-012](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)

### Q4. Как проверить persistence?

Создать запись, прочитать заново и повторить после оговорённого перезапуска; reset fixtures не должен скрывать результат. [SRC-011](https://developer.mozilla.org/en-US/docs/Learn_web_development/Getting_started/Web_standards/How_the_web_works)

### Q5. Как разделять классы ошибок?

Сопоставлять фазу сбоя: установка, старт, HTTP, business rule, storage. Гипотезу подтверждать наблюдением. [SRC-012](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)

### Q6. Почему зелёного отчёта мало?

Проверить, что нужные тесты реально исполнялись, не были пропущены и завершились в нужном snapshot. [SRC-014](https://nodejs.org/api/test.html)

### Q7. Что передавать в Git-урок?

Состояние файлов, run manifest, известные ошибки и реально исполненные checks; генерацию кода не считать проверкой. [SRC-015](https://git-scm.com/docs/git-status)

## 3. Терминология

Smoke check проверяет основную работоспособность выбранного пути; это не полное regression testing. Reproducible setup включает версии, зависимости и исходные данные.

Не считать названия интерфейсов разных продуктов эквивалентными. Общая терминология уточняется перед drafting; отдельного GLOSSARY.md пока нет.

## 4. Механизмы и архитектурный разбор

1. Runbook: prerequisites → dependencies → env → storage/fixtures → server/client → readiness → smoke → stop.
2. Для сбоя сохранять точную команду, cwd, версию, exit code и релевантный log без credentials.
3. Проверять одинаковую операцию через UI и напрямую через согласованный API, затем readback; не подменять backend моками без пометки.

Это план объяснения механизмов на учебном примере, а не утверждение о внутреннем устройстве всех инструментов. Для diagram и demonstrations использовать только наблюдаемые границы и явно обозначенные допущения.

## 5. Альтернативы и trade-offs

Матрица — **Interpretation**, исходные механизмы и доступные интерфейсы см. в sources.md. Оценки относительные; количественных benchmark здесь нет.

| Подход | Зачем выбирать | Издержки / failure modes | Где применим |
|---|---|---|---|
| Готовый scaffold | Контролируемое окружение | Меньше свободы выбора stack | Первый воспроизводимый урок |
| Генерация приложения с нуля | Показывает делегирование | Дополнительная вариативность и setup debt | Продвинутая ветка после smoke baseline |
| Контейнерное окружение | Упрощает унификацию зависимостей | Нужен runtime и знание mount/ports | Команда с подготовленным dev environment |

Если значение зависит от продукта, плана или команды, пометить как непроверенное до сверки актуального источника.

## 6. Production engineering

Для production не переносить dev server и учебные credentials. В legacy сохранять lockfile и documented baseline; в CI воспроизводить тот же check. Изменение окружения во время диагностики фиксировать отдельно от изменения приложения.

До приёмки результата сопоставить scope, актуальный snapshot, diff и проверки. Отчёт о действиях не подменяет evidence; стоимость включает человеческую проверку. За технические права отвечает конфигурация среды, за решение о выпуске — назначенный владелец.

## 8. Неопределённости и следующая проверка

Блокер для final tutorial: нет runnable scaffold и smoke-script; контракт и версии необходимо реализовать и прогнать на целевых ОС.



Перед drafting: перепроверить time-sensitive страницы; выбрать фактический snapshot; перед публикацией исполняемого примера выполнить команды и негативный сценарий на заявленной платформе; сохранить входы и результаты. Если неизвестен обязательный контракт, пометить drafting заблокированным для практической части, не изобретать API или successful output.

## 9. Авторская практическая демонстрация

**Сценарий:** **Диагностическая демонстрация:** один readme/manifest/lockfile snapshot и три заранее подготовленные трассы ошибок. Команды зависят от фактического manifest и не исполняются в этом исследовании.

| Фаза | Наблюдаемый симптом | Следующее различающее наблюдение |
|---|---|---|
| Setup/runtime | Процесс не стартует | версия runtime, lockfile, error log; не менять зависимости наугад |
| API | UI открылся, request завершается ошибкой | HTTP method/status/body и server log |
| Storage | Запись показалась, но исчезла после повторного read | persistence adapter и запрос/fixture после refresh |

Если manifest — совместимый npm проект с lockfile, документационный пример может показывать `npm ci` (SRC-013); запуск команды в будущей демонстрации требует изолированной копии и проверки последствий для `node_modules`. Затем автор показывает smoke request и точно сообщает, что реально проверил.

**Статус и границы:** это сценарий будущего рассказа/показа. Полное приложение Engineering Workbench остаётся кандидатом; scaffold и end-to-end запуск не подтверждены. Отдельно указанное фактическое evidence относится только к конкретному ограниченному примеру и не переносится на приложение.

**Платформа и prerequisites:** до исполнения демонстрации указать целевую ОС/shell, версии, точный snapshot, необходимые fixtures, доступы, сеть и последствия команд. Продуктовые installer/flags и billing проверять по текущей документации выбранного продукта. Команды в примере с явной пометкой «иллюстративный» требуют выполнения автором до публикации урока.

**Ожидаемое и фактическое:** ожидаемые наблюдения задают учебный сценарий. Фактическим результатом считать только наблюдение из зафиксированного локального verification-отчёта; обзор документации или проектирование сценария не означает исполнение. Демонстрация предназначена для объяснения материала и не требует сдачи работы от читателя.
