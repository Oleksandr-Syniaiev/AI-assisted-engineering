# Передать задачу на выполнение в облако (дополнительно)

Удалённая среда должна получить всё необходимое, но только необходимое.

**Р1.15 · Основы, дополнительный урок · 40–55 минут.** Нужны [Р1.06](../06-run-first-application/index.html), [Р1.09](../09-github-pull-request/index.html), [Р1.12](../12-long-session-handoff/index.html), [Р1.14](../14-agent-handoff-review/index.html). Облачная часть — документальный разбор. Доступ не покупался, репозиторий не подключался, удалённая задача не запускалась.

## Результат урока

Вы сможете подготовить переносимую задачу, найти различия окружений и проверить возвращённый patch локально. Облачное исполнение — дополнительный маршрут. Оно не является обязательным условием обучения или автоматическим повышением качества.

## Почему «у меня работает» не переносится вместе с запросом

На компьютере автора есть незакоммиченный файл, локальные данные, установленный runtime и переменная окружения. В удалённом checkout может не быть ничего из этого. Агент получает задачу, но не получает компьютер автора целиком.

Обратная ситуация: облачный тест прошёл на Linux, а локальный импорт ошибается на Windows или в другом окружении. Результат удалённой проверки полезен, но относится к её версии кода, ОС, инструментам и условиям. Он не заменяет проверку целевой среды.

## Что означает облачное выполнение

Нужно отличать место обработки модели от места запуска инструментов. При локальном агенте модель уже может работать удалённо, а команды — на компьютере инженера. **Облачное исполнение задачи** в этом уроке означает, что файлы и команды находятся в выделенной удалённой рабочей среде.

Для конкретного примера Codex Cloud документирует настройку окружения, подключение репозиториев и инструментов, запуск задачи и последующий просмотр изменений. Наличие этих возможностей в документации не доказывает доступ в любой учётной записи. [SRC-028](https://learn.chatgpt.com/docs/cloud)

```text
Репозиторий и закреплённая ревизия
        ↓ подготовка удалённой среды
Runtime + зависимости + ограниченный доступ
        ↓ задача и проверки
Patch + журнал исполнения
        ↓ получение на локальную ветку
Просмотр diff + релевантные локальные проверки
```

Удалённая среда не является резервной копией всех локальных данных. Сроки жизни файлов, сохранение состояния и повторное использование setup зависят от сервиса: эти свойства уточняют до передачи задачи.

## Пакет задачи для Workbench

Для нашего стенда входы невелики: `server.mjs`, `client.html`, `policy.mjs`, `workbench.test.mjs` и README. `data/requests.json` не нужен: тест создаёт собственное временное хранилище. Нет внешних npm-зависимостей и секретов. Это позволяет отделить перенос окружения от установки большого стека.

В реальном Git-проекте сначала фиксируют исходную ревизию и проверяют, что все необходимые исходники в ней есть. Untracked и незакоммиченные локальные правки не появятся в удалённой копии по факту их существования на диске. Локальные результаты тестов тоже не становятся результатами облачного запуска.

Документальный setup для Linux/macOS с доступным Node.js, из корня репозитория:

```sh
node --version
node --test lessons/01/demo-workbench/workbench.test.mjs
```

Синтаксис этих команд переносим, но исполнение в облаке не проверялось. Среда должна разрешать локальный HTTP для интеграционного теста и запись во временный каталог. Runtime следует закрепить на проверенной версии либо явно проверить другую; автоматический выбор «самой новой» версии ухудшает сопоставимость.

## Разобранное облачное поручение

```text
Проверь правило title и подключение к POST /api/requests.
Исходное состояние: конкретная ревизия учебного репозитория.
Контракт: только string; trim до проверки непустоты.
Не трогай UI, не добавляй зависимости и внешние сервисы.
Проверка: node --test lessons/01/demo-workbench/workbench.test.mjs.
Используй только синтетические данные и временное хранилище теста.
Верни diff, версии среды, команды, exit codes и ограничения.
Не публикуй, не объединяй и не развёртывай результат.
```

«Конкретная ревизия» заменяется реальным идентификатором перед запуском; вымышленный hash здесь не приводится. Для задачи на исправление также нужен воспроизводимый дефект. Текущий стенд уже содержит корректный валидатор: отправить его с просьбой «исправить пробелы» без проверки состояния означало бы поручить несуществующую правку.

Условия остановки: не удаётся получить нужную ревизию, недоступен runtime, нет разрешения на локальный тест, конфликтует контракт. Агент сообщает ограничение; отсутствие запуска не оформляется как успешная проверка.

## Как разобрать возвращённый результат

Сначала проверяют исходный и итоговый commit или точный patch. Затем читают изменённые и новые файлы: не появились ли зависимости, сетевые обращения и изменения ожиданий? После этого проверяют журнал: версия Node.js, ОС, рабочий каталог, команда, exit code и состав тестов.

Наконец, результат применяют к отдельной локальной ветке и повторяют относящиеся к изменению проверки. Если локальная base ушла вперёд, возможны конфликты и новые несовместимости. Старый зелёный лог относится к прежнему сочетанию файлов.

Пример отказа уже встречался локально при подготовке стенда: тест получил `EACCES` на соединении с `127.0.0.1`. После разрешения среды он прошёл. Это показывает роль политики исполнения, но **не является облачным экспериментом**. [Журнал](../demo-workbench/verification.md)

## Что обычно различается между средами

| Различие | Возможный симптом | Проверка |
|---|---|---|
| Версия runtime | Иной API или синтаксическая ошибка | Зафиксированные версии и команда |
| Регистр путей | Импорт работает только на одной файловой системе | Реальные имена файлов и импорты |
| Незакоммиченный файл | Модуль отсутствует удалённо | Состав исходной ревизии |
| Секреты и сеть | Сервис недоступен | Разрешённые назначения и отдельный setup |
| Фоновый процесс | Тест ждёт несуществующий сервер | Явное управление жизненным циклом |
| Временные данные | После задачи состояние исчезло | Правила хранения и отдельное получение артефактов |

Нельзя решать каждый такой отказ выдачей полного доступа. Разрешение расширяют до конкретного действия, если оно действительно требуется и авторизовано.

## Production и альтернативы

| Критерий | Локальный агент | Облачный агент | Обычный CI |
|---|---|---|---|
| Применение | Работа рядом с инженером | Делегированная удалённая задача | Заранее заданные проверки |
| Освоение | Клиент и локальная среда | Setup и передача состояния | Pipeline и runner |
| Внедрение | Уже доступный проект | Репозиторий, runtime, политики | Конфигурация workflow |
| Сопровождение | Версии на машине | Образы и удалённые зависимости | Скрипты и runners |
| Безопасность | Локальные файлы и команды | Удалённый доступ и секреты | Права workflow и supply chain |
| Проверяемость | Diff и локальный лог | Diff плюс журнал среды | Повторяемый набор команд |
| Стоимость | Время машины и review | Доступ, ресурсы, setup, review | Ресурсы запуска и поддержка |

CI исполняет описанную последовательность; агент выбирает действия в рамках задачи. Их можно сочетать, но они не взаимозаменяемы. Облачная среда полезна при воспроизводимом setup и достаточном выигрыше в организации работы. Для маленького исправления стоимость настройки и review может превышать пользу.

В production отдельно контролируют происхождение артефактов, доступ к приватному коду, секреты, сетевые направления и право публикации. Допуск к исследованию не означает допуск к deploy. Неподтверждённых заявлений об ускорении или безопасности облака по сравнению с локальной средой здесь нет.

## Вопросы с объяснёнными ответами

### 1. Удалённая модель означает облачное выполнение команд?

Нет. Модель может быть удалённой, а инструменты работать локально. Это разные границы архитектуры.

### 2. Что случится с незакоммиченным локальным файлом?

Он не появится автоматически в удалённом checkout. Нужны явный состав входов и способ передачи.

### 3. Зачем указывать версию runtime?

Чтобы результат можно было сопоставить с локальной и целевой средой. Имя команды не описывает её версию.

### 4. Облачный зелёный тест снимает необходимость локального review?

Нет. Нужны просмотр patch и проверка применимости результата к текущей базе и целевой среде.

### 5. Можно ли переносить пользовательский JSON-файл ради теста?

Для нашего сценария не нужно. Тест использует синтетические данные во временном каталоге, что упрощает безопасность и повторяемость.

### 6. Агент в облаке заменяет CI?

Нет. Агент может выбирать действия и писать код, CI выполняет закреплённые проверки. Они решают разные задачи.

### 7. Что подтверждено в этом уроке?

Документальные возможности и локальные примеры с указанными границами. Реального облачного запуска и сравнений стоимости не было.
