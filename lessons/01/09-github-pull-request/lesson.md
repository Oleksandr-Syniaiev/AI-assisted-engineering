# GitHub: разместить проект и подготовить изменение к проверке

Передать команде изменение вместе с причиной и доказательствами.

**Р1.09 · Основы · 40–60 минут.** Нужны [Р1.07](../07-git-checkpoints-diffs/index.html), [Р1.08](../08-change-verify-fix/index.html). Локальные команды требуют Git и существующий репозиторий. Публикация требует отдельного доступа к GitHub; в этом уроке она разобрана документально, без реального push и создания PR.

## Результат урока

Вы сможете различить Git и GitHub, локальную ветку и remote, выбрать head/base pull request и составить описание изменения. Главное — передать проверяемый patch, а не только сообщить «агент всё сделал».

## Почему локального commit недостаточно команде

После исправления заголовка у автора есть commit и результаты тестов. Другой инженер ещё не знает, какую проблему решает правка, какие варианты рассматривались и на каком коде запускались проверки. Пересылка ZIP лишает его удобной связи с историей.

GitHub хранит удалённый репозиторий и предоставляет обсуждение изменений. Pull request, или PR, — предложение объединить изменения ветки с целевой веткой проекта. PR объединяет описание, commits, diff и checks; это не команда развёртывания приложения. [SRC-037](https://docs.github.com/en/pull-requests/reference/pull-requests)

## Репозиторий, remote и ветки

**Репозиторий Git** хранит историю. **Remote** — именованная ссылка на другой репозиторий, обычно `origin`. Имя `origin` условное: оно не гарантирует правильного адреса или права записи. **Ветка** — перемещаемый указатель на commit. Локальная `fix/title-validation` и удалённая ветка с таким именем существуют в разных репозиториях.

`commit` сохраняет снимок локально. `push` передаёт необходимые объекты и обновляет ссылки на удалённой стороне в рамках разрешений. `fetch` получает сведения и объекты с удалённой стороны, не объединяя их автоматически с рабочими файлами.

```text
Локальная ветка fix/title-validation
        │ commit, локальные тесты
        │ push
        ▼
GitHub: ветка fix/title-validation  ← head
        │ PR и review
        ▼
GitHub: main                       ← base
```

**Head** содержит предлагаемую работу, **base** принимает её при объединении. Если выбрать base неправильно, diff может включить чужие изменения или оказаться пустым. По умолчанию проект часто использует основную ветку, но её имя нужно проверить. [SRC-038](https://docs.github.com/en/pull-requests/reference/branches)

## До публикации: проверить состав и адрес

Предусловия: отдельный учебный проект уже является Git-репозиторием с baseline commit. Корень этого курса не нужно инициализировать ради чтения урока. В PowerShell из корня такого проекта:

```powershell
git status --short
git remote -v
git branch --show-current
git log -1 --oneline
```

Проверяют незавершённые изменения, адреса fetch/push и текущую ветку. До первого push читают состав истории и файлов: `.env`, токены, рабочие данные и личные документы не должны отправляться случайно. Добавление файла в `.gitignore` не удаляет его из существующей истории.

Если remote отсутствует, сначала создаётся пустой репозиторий в нужной учётной записи или организации с выбранной видимостью. Существующий remote не заменяют вслепую. Ссылка и метод авторизации должны соответствовать политике команды.

Документальный пример добавления адреса:

```powershell
# OWNER и REPOSITORY — заменяемые обозначения, не готовый URL.
git remote add origin https://github.com/OWNER/REPOSITORY.git
git remote -v
```

Команда применяется только при отсутствии `origin`. Если серверный репозиторий уже содержит отдельную историю, нельзя принуждать push: сначала выясняют расхождение. Для пустого удалённого репозитория и проверенной локальной ветки `main` первая публикация выглядит как `git push -u origin main`. Это внешнее действие: до него нужны выбранная видимость, доступ и просмотр состава истории. Здесь оно не выполнялось. Если ветка называется иначе, её имя сначала проверяют, а не переименовывают случайно. Первую публикацию отдельно описывает [GitHub Docs](https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github).

## Разбор исправления через PR

Для ветки изменения исходная общая версия уже должна быть доступна в целевом репозитории. Локально создают ветку, вносят проверенную правку, подготавливают и фиксируют выбранные файлы:

```powershell
git switch -c fix/title-validation
# Здесь находится разобранное изменение из Р1.08 и его проверка.
git add -- policy.mjs
git diff --cached -- policy.mjs
git commit -m "Reject whitespace-only request titles"
git push -u origin fix/title-validation
```

Это документальная последовательность, не отчёт о выполнении. `-u` связывает локальную ветку с upstream для дальнейшей работы. Push требует доступа и является внешним действием; агент не должен выводить разрешение на публикацию из разрешения редактировать файл.

На GitHub выбирают head `fix/title-validation` и правильную base, например `main`. В Files changed проверяют, что PR содержит именно нужную правку. Описание:

```text
Проблема: заголовок из пробелов принимался как пустая заявка.
Изменение: trim выполняется до проверки длины;
проверка типа сохранена.
Проверка: четыре случая контракта Р1.08, corrected 4/4.
Ограничение: этот прогон проверяет функцию, не UI и не БД.
```

В реальном PR к проверке добавляют команду, среду и commit. Исторический результат Р1.08 нельзя автоматически приписать новому patch, даже если код выглядит похожим: новый итоговый commit нужно проверить.

## Что читает reviewer

Reviewer сопоставляет требование с diff, проверяет тесты и границы изменения. Вкладка Checks показывает автоматические проверки, но зелёный статус полезен только при понимании их состава и проверенной ревизии. Новые commits могут сделать прежние комментарии и результаты устаревшими.

Если reviewer просит уточнение, ответ должен указывать факты: «guard типа сохранён; случай 7 отклоняется таким тестом», а не «модель уверена». Найденное замечание исправляют и перепроверяют на текущем состоянии. Merge, то есть объединение, и deploy, то есть развёртывание, остаются отдельными этапами, если процесс команды не связывает их автоматикой.

## Production и альтернативы

| Критерий | ZIP или сообщение | Прямой push в основную ветку | Ветка и PR |
|---|---|---|---|
| Применение | Разовая передача снимка | Разрешённые простые процессы | Обсуждаемая командная работа |
| Освоение | Минимальное | Git и общий доступ | Head/base, review, checks |
| Внедрение | Ручное сравнение | Правила записи | Политики PR и CI |
| Сопровождение | Слабая связь с историей | Меньше промежуточных этапов | Контекст обсуждений сохраняется |
| Безопасность | Риск лишних файлов | Сразу меняет общую ветку | Права и защита веток |
| Проверяемость | Ограниченная | Проверки после или до push по процессу | Diff, обсуждение и checks |
| Стоимость | Ручная интеграция | Меньше координации, выше цена ошибки | Время review и интеграции |

PR не гарантирует качество сам по себе. Маленькое изменение с точным контрактом проще проверить, чем массовую правку без объяснений. Для существующего продукта дополнительно нужны совместимость, миграции, rollback и контроль секретов. Стоимость review — часть цены агентного изменения.

## Вопросы с объяснёнными ответами

### 1. Git и GitHub — одно и то же?

Нет. Git управляет историей; GitHub предоставляет удалённый сервис и совместный workflow. Локальный commit не требует GitHub.

### 2. `origin` гарантированно указывает на нужную организацию?

Нет. Это имя настройки. Адрес проверяют через `git remote -v` до публикации.

### 3. Где head, а где base?

Head содержит предлагаемое изменение, base — целевая ветка объединения. Проверяют обе, а не только имя своей ветки.

### 4. Push создаёт PR автоматически?

Не обязательно. Он передаёт ветку. PR создаётся отдельным действием сервиса или настроенной автоматизации.

### 5. Почему нельзя написать просто «тесты прошли»?

Неизвестны команда, состав, среда и ревизия. Точный результат позволяет reviewer оценить реальные границы доказательства.

### 6. Merge означает приложение уже запущено у пользователей?

Только если это предусмотрено конкретным pipeline. Изменение истории и развёртывание — разные действия.

### 7. Что было выполнено здесь?

Локальные Git-состояния проверены отдельной демонстрацией Р1.07. Удалённый репозиторий, push, PR и CI не создавались.
