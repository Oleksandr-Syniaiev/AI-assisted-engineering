## 2. Исследовательские вопросы и ответы

Вопросы раздела сформулированы до сбора источников: проблема, определение, механизм, альтернативы, проверяемость, production-риски и зависимости. Ниже — конкретизация для этой темы. **Ответы являются синтезом и инженерной интерпретацией**, кроме прямо выделенных Verified claims в разделе 7. Ссылка означает опору на указанный механизм/ограничение, а не доказательство эффективности предложенной демонстрации.

### Q1. Что выбрать до публикации?

Учебный репозиторий, владельца, видимость, права и отсутствие секретов; это отдельное решение от commit. [SRC-021](https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github)

### Q2. Можно ли использовать GUI?

Да: официальный маршрут допускает GitHub Desktop, CLI и Git; важна семантика состояния, а не один интерфейс. [SRC-021](https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github)

### Q3. Что такое head и base?

Источник изменений и ветка назначения; перепутанная base меняет состав предлагаемого diff. [SRC-022](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request)

### Q4. Какие доказательства дать reviewer?

Причина изменения, поведение до/после, scope и фактические проверки на commit; это предлагаемая PR rubric. [SRC-016](https://git-scm.com/docs/git-diff)

### Q5. Как продолжить PR?

Новые commits в head branch обновляют предложение; после них результаты старой проверки могут устареть. [SRC-022](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request)

### Q6. Что не доказывает создание PR?

Что change проверен, одобрен или разрешён к выпуску; это отдельные этапы командного процесса. [SRC-022](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request)

### Q7. Что проверить при неожиданном diff?

Remote, head/base, baseline и включённые commits; не скрывать лишнее только сокращением описания. [SRC-016](https://git-scm.com/docs/git-diff)

## 3. Терминология

Git — VCS; GitHub — сервис совместной работы. Push публикует объекты и refs на remote; PR предлагает интеграцию изменений между ветками.

Не считать названия интерфейсов разных продуктов эквивалентными. Общая терминология уточняется перед drafting; отдельного GLOSSARY.md пока нет.

## 4. Механизмы и архитектурный разбор

1. Локальный commit → выбранный remote → опубликованная ветка → PR head/base → review → решение.
2. Развести authentication к GitHub и author identity локального commit.
3. Показать, как изменение base или новый commit меняют состав review и актуальность тестов.

Это план объяснения механизмов на учебном примере, а не утверждение о внутреннем устройстве всех инструментов. Для diagram и demonstrations использовать только наблюдаемые границы и явно обозначенные допущения.

## 5. Альтернативы и trade-offs

Матрица — **Interpretation**, исходные механизмы и доступные интерфейсы см. в sources.md. Оценки относительные; количественных benchmark здесь нет.

| Подход | Зачем выбирать | Издержки / failure modes | Где применим |
|---|---|---|---|
| Git CLI + GitHub web | Явные remote/branch и привычный PR UI | Нужно понимать две среды | Основной универсальный путь |
| GitHub Desktop | Визуальный diff и публикация | Скрывает часть командной механики | Новичок с GUI |
| GitHub CLI | Удобен для повторяемых операций | Нужны отдельные auth/flags | Опытный terminal workflow |

## 6. Production engineering

В организации учитывать branch rules и обязательные checks, не предполагать одинаковые политики. Не делать auto-merge частью первого урока. PR должен быть обозримым, объяснять миграции и риски, если они есть; приватность репозитория не оправдывает хранение credentials.

До приёмки результата сопоставить scope, актуальный snapshot, diff и проверки. Отчёт о действиях не подменяет evidence; стоимость включает человеческую проверку. За технические права отвечает конфигурация среды, за решение о выпуске — назначенный владелец.

## 8. Неопределённости и следующая проверка

Для запуска выбрать отдельный учебный repository; внешние публикации не выполнялись в текущем исследовании.



Перед drafting: перепроверить time-sensitive страницы; выбрать фактический snapshot; перед публикацией исполняемого примера выполнить команды и негативный сценарий на заявленной платформе; сохранить входы и результаты. Если неизвестен обязательный контракт, пометить drafting заблокированным для практической части, не изобретать API или successful output.

## 9. Авторская практическая демонстрация

**Сценарий:** **Показ по read-only учебному репозиторию:** отделить локальный repository, remote URL и GitHub-hosted repository. До публикации автор показывает проверку видимости репозитория и секретов; отправка внешнего PR не требуется для объяснения.

На схеме PR отметить head branch как источник change и base branch как цель. Сопоставить PR diff с локальным commit и статусом checks; после нового commit старый check не следует считать относящимся к новой ревизии без проверки commit SHA. Сравнить GitHub web, GitHub CLI и Desktop как интерфейсы к общей branch/head/base семантике, не приписывая интерфейсам одинаковые capabilities.

**Статус и границы:** это сценарий будущего рассказа/показа. Полное приложение Engineering Workbench остаётся кандидатом; scaffold и end-to-end запуск не подтверждены. Отдельно указанное фактическое evidence относится только к конкретному ограниченному примеру и не переносится на приложение.

**Платформа и prerequisites:** до исполнения демонстрации указать целевую ОС/shell, версии, точный snapshot, необходимые fixtures, доступы, сеть и последствия команд. Продуктовые installer/flags и billing проверять по текущей документации выбранного продукта. Команды в примере с явной пометкой «иллюстративный» требуют выполнения автором до публикации урока.

**Ожидаемое и фактическое:** ожидаемые наблюдения задают учебный сценарий. Фактическим результатом считать только наблюдение из зафиксированного локального verification-отчёта; обзор документации или проектирование сценария не означает исполнение. Демонстрация предназначена для объяснения материала и не требует сдачи работы от читателя.
