# Из чего состоит приложение: клиент, сервер, данные

Проследить заявку от кнопки до сохранённой записи.

**Р1.05 · Основы · 40–55 минут.** Предварительно: [Р1.04](../04-files-editor-terminal/index.html). Пример — [локальный стенд](../demo-workbench/README.md), а не полная production-версия Engineering Workbench.

## Результат урока

Вы сможете объяснить роли браузера, API и хранилища, прочитать путь запроса и выбрать место проверки дефекта. Главная граница: то, что показано на экране, не обязательно сохранено.

## Проблема: запись исчезла после обновления

Пользователь вводит «Fix CI», нажимает кнопку и видит заявку в списке. Кажется, функция готова. Но после обновления страницы запись исчезает. Возможные причины разные: интерфейс добавил строку только в память браузера; запрос не дошёл до сервера; сервер вернул ошибку; запись хранилась только в памяти процесса.

Нельзя исправить этот класс проблем одной просьбой «сделай сохранение». Нужно понять, где находится состояние и каким наблюдением подтверждается переход между слоями. Клиент-серверный обмен устроен как запрос и ответ; динамические приложения используют данные при формировании ответа. [SRC-034](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Server-side/First_steps/Client-Server_overview)

## Три ответственности

**Клиент** — часть приложения, с которой взаимодействует пользователь. Здесь браузер показывает HTML-форму и выполняет JavaScript. Его оперативное состояние — содержимое DOM, то есть дерева элементов страницы. Изменение DOM может никак не затронуть сервер.

**Сервер** — работающий процесс, который принимает запросы. В стенде Node.js раздаёт HTML и обрабатывает API. **API** — договорённость о способах обращения: адресах, методах, данных и ответах. Для клиента важен контракт, а не внутреннее устройство обработчика.

**Хранилище** переживает отдельные запросы. У нас это JSON-файл на диске. JSON — текстовый формат данных, а не самостоятельная база данных. Выбор файла позволяет увидеть запись буквально, но не даёт транзакций, резервного копирования или безопасной совместной работы нескольких серверов.

```text
Браузер: client.html
   │ POST /api/requests  {"title":" Fix CI "}
   ▼
Сервер: server.mjs → policy.mjs: validateTitle
   │ только допустимый нормализованный title
   ▼
Файл: data/requests.json
   │ успешная запись
   ▼
HTTP 201 → браузер запрашивает список → показывает запись
```

## Что именно передаётся

HTTP-запрос содержит метод, путь, заголовки и иногда тело. `GET /api/requests` читает список. `POST /api/requests` в нашем контракте создаёт заявку. `Content-Type: application/json` сообщает формат тела. Ответ содержит статус и данные. Эти свойства реализованы в обработчике Node.js. [SRC-035](https://nodejs.org/docs/latest-v24.x/api/http.html)

```http
POST /api/requests
Content-Type: application/json

{"title":" Fix CI "}
```

Ожидаемое тело ответа при успехе:

```json
{"id":"идентификатор, созданный сервером","title":"Fix CI"}
```

Идентификатор здесь описательный, не настоящий результат запуска. Статус `201` выбран контрактом стенда для созданной записи; `422` — для недопустимого заголовка, `400` — для сломанного JSON. Клиент обязан посмотреть статус: получение HTTP-ответа само по себе не означает успех операции.

## Путь через реальный код

В `client.html` обработчик `submit` отменяет обычную отправку формы через `preventDefault()`. Затем `fetch` отправляет JSON. После успешного ответа функция `show()` заново читает список с сервера. Поэтому список строится по серверному состоянию, а не только по введённому тексту.

В `server.mjs` обработчик читает тело с ограничением размера, разбирает JSON и вызывает `validateTitle(input?.title)`. Если значение не строка или после `trim()` пусто, запись не создаётся. Принятый заголовок помещается в объект с `id`, список записывается в файл, затем отправляется ответ.

Серверная проверка нужна даже при наличии клиентской. Любой другой клиент может обратиться к API без нашей формы. Проверка в браузере помогает пользователю раньше увидеть ошибку, но не защищает серверный контракт.

Функция `save(rows)` использует файловый API Node.js. В демонстрации запись синхронная: пока она выполняется, процесс не обслуживает другие обработчики JavaScript. Это упрощает объяснение последовательности, но блокирует обслуживание на время записи. Файл всё равно может повредиться при аварии. [SRC-036](https://nodejs.org/docs/latest-v24.x/api/fs.html)

## Как отличить отображение от сохранения

Авторская демонстрация состоит из четырёх наблюдений. Сначала успешный `POST` возвращает нормализованную запись. Затем независимый `GET` видит её. Далее проверяется содержимое файла. Наконец, новый процесс сервера читает ту же запись после перезапуска. Только последнее отделяет сохранение на диске от состояния памяти старого процесса.

В [автоматизированном разборе](../demo-workbench/verification.md) эти переходы выполнены через HTTP на временном файле. Визуальное нажатие кнопки не подменяется этим результатом: оно проверяет ещё и работу браузерного обработчика.

| Симптом | Где искать доказательство |
|---|---|
| Кнопка не вызывает запрос | Обработчик формы и вкладка Network браузера |
| API отвечает `422` | Отправленное тело и `validateTitle` |
| API отвечает `500` | Лог сервера и состояние файла |
| После перезапуска нет записи | Фактический путь файла и запись на диск |
| `/health` успешен, список сломан | Процесс жив, но хранилище может быть неисправно |

## Production и альтернативы

В рабочей системе к этому пути добавляются аутентификация, проверка полномочий, ограничения входа, конкурентная запись, наблюдаемость и восстановление. При повторной отправке нашего `POST` появятся две записи: идемпотентность, то есть защита от повторного выполнения одной операции, не реализована. Блокировка кнопки помогает только одному окну браузера.

| Критерий | Память процесса | JSON-файл стенда | База данных |
|---|---|---|---|
| Применимость | Краткая демонстрация | Малый локальный набор | Общие рабочие данные |
| Освоение | Простая структура | Чтение и запись файла | Модель данных и запросы |
| Внедрение | Почти без настройки | Путь и права записи | Схема и окружение |
| Сопровождение | Перезапуск теряет данные | Копии и восстановление вручную | Миграции, backup, мониторинг |
| Безопасность | Доступ к процессу | Права файловой системы | Учётные записи и роли |
| Проверяемость | Проверка в одном процессе | Чтение после перезапуска | Интеграционные и отказные проверки |
| Стоимость | Мало setup, потеря состояния | Мало setup, много ограничений | Больше эксплуатации, богаче гарантии |

Это выбор по требованиям, а не правило «БД всегда лучше». Для вводного чтения файл прозрачен; для совместной записи нужны гарантии, которых у него здесь нет. Агент должен знать выбранную границу, иначе легко предложит интерфейс без настоящего сохранения.

## Вопросы с объяснёнными ответами

### 1. Запись видна в списке. Она сохранена?

Не доказано. Список мог измениться только в DOM. Нужны чтение из API и проверка после перезапуска.

### 2. API — отдельная программа?

Не обязательно. Здесь API и раздача страницы находятся в одном серверном процессе. API обозначает интерфейс взаимодействия.

### 3. Зачем проверять заголовок на сервере?

Форму можно обойти. Сервер должен защищать свой контракт для всех клиентов, а не доверять конкретной странице.

### 4. Почему `/health` недостаточно?

Он подтверждает ответ процесса. В стенде этот маршрут не читает хранилище, поэтому повреждённый файл не мешает ему отвечать.

### 5. JSON-файл равен базе данных?

Нет. Формат хранения не предоставляет сам по себе транзакций и конкурентного доступа. Эти свойства проектируют отдельно.

### 6. Что произойдёт при повторном POST?

Будет создана ещё одна запись. Защиты от повторов в стенде нет; это явная граница примера.

### 7. С чего начать диагностику исчезнувшей заявки?

Проследить фактические переходы: запрос, ответ, независимое чтение, файл и перезапуск. Это локализует потерю состояния.

## Главное и следующий шаг

Клиент показывает данные, сервер применяет правила, хранилище удерживает состояние. Проверка результата должна пересечь нужные границы. В [Р1.06](../06-run-first-application/index.html) запустим этот путь целиком.
