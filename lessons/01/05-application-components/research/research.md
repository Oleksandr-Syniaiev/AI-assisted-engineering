## 1. Паспорт и границы

Статус: исследование и план, не готовый урок. Дата проверки источников: 02.11.2026. Продуктовые факты подтверждены чтением указанных разделов документации, но доступность на аккаунте и конкретная версия клиента не проверялись. Полная демонстрация, установка клиентов и облачное исполнение не выполнялись.

Проблема: Красивый интерфейс может скрывать отсутствие сервера или сохранения данных; без карты компонентов непонятно, где искать дефект.

Prerequisites: [Р1.04](../../04-files-editor-terminal/research/outline.md)

Ориентировочное время будущего урока: 60–90 минут; оценка автора плана, без пилотирования.

Целевые результаты:

- Проследить создание заявки от UI до хранилища
- Различить клиентский state, серверную обработку и persistence

Граница: один аспект раздела 1; SDD, сложные hooks, worktrees, параллельная оркестрация и production deployment остаются в последующих разделах. Сквозной пример — предложенный в COURSE_OVERVIEW.md **Engineering Workbench**, пока кандидат, а не утверждённая реализация.

## 2. Исследовательские вопросы и ответы

Вопросы раздела сформулированы до сбора источников: проблема, определение, механизм, альтернативы, проверяемость, production-риски и зависимости. Ниже — конкретизация для этой темы. **Ответы являются синтезом и инженерной интерпретацией**, кроме прямо выделенных Verified claims в разделе 7. Ссылка означает опору на указанный механизм/ограничение, а не доказательство эффективности предложенной демонстрации.

### Q1. Кто отправляет запрос?

Клиент; в сценарии это браузерный интерфейс. Сервер принимает запрос и формирует ответ. [SRC-011](https://developer.mozilla.org/en-US/docs/Learn_web_development/Getting_started/Web_standards/How_the_web_works)

### Q2. Что содержит HTTP-обмен?

Метод, URL, headers и при необходимости body, затем status/headers/body ответа; контракт примера проектируется отдельно. [SRC-012](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)

### Q3. Почему UI не доказывает сохранение?

Данные могли остаться только в памяти клиента; persistence проверяется отдельным действием после перезапуска. [SRC-011](https://developer.mozilla.org/en-US/docs/Learn_web_development/Getting_started/Web_standards/How_the_web_works)

### Q4. Где проверять неверный заголовок?

Для кандидата проекта — на API-границе и в соответствующих тестах; клиентская подсказка полезна для UX, но не заменяет проверку входа. [SRC-012](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)

### Q5. Почему одинаковый localhost не означает один компонент?

Разные порты могут обслуживаться разными процессами; схема разработки должна перечислять процессы и адреса. [SRC-011](https://developer.mozilla.org/en-US/docs/Learn_web_development/Getting_started/Web_standards/How_the_web_works)

### Q6. Когда не нужны три deployable сервиса?

Для первого маршрута достаточно модульного приложения с ясными ответственностями; это архитектурная рекомендация курса. [SRC-011](https://developer.mozilla.org/en-US/docs/Learn_web_development/Getting_started/Web_standards/How_the_web_works)

### Q7. Что передать следующему уроку?

Карту компонентов, entrypoints, адреса, storage и smoke-сценарий создания заявки. [SRC-012](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)

## 3. Терминология

Client/server — роли в обмене запросами. Storage — отдельная ответственность учебной архитектуры; не каждый web-сервер обязан иметь БД.

Не считать названия интерфейсов разных продуктов эквивалентными. Общая терминология уточняется перед drafting; отдельного GLOSSARY.md пока нет.

## 4. Механизмы и архитектурный разбор

1. Sequence: submit → HTTP request → parse/validate → repository/storage → response → update UI.
2. Сопоставить каждый переход с наблюдением: DevTools, server log, read endpoint, повторный запуск.
3. Показать точки отказа: сеть, формат запроса, business rule, storage, отображение; HTTP-успех не равен выполнению бизнес-требования.

Это план объяснения механизмов на учебном примере, а не утверждение о внутреннем устройстве всех инструментов. Для diagram и demonstrations использовать только наблюдаемые границы и явно обозначенные допущения.

## 5. Альтернативы и trade-offs

Матрица — **Interpretation**, исходные механизмы и доступные интерфейсы см. в sources.md. Оценки относительные; количественных benchmark здесь нет.

| Подход | Зачем выбирать | Издержки / failure modes | Где применим |
|---|---|---|---|
| Только статический frontend | Простой запуск | Нет общего серверного состояния | UI-прототип |
| Модульный клиент–серверный проект | Ясный поток и умеренный setup | Нужно согласовать API и storage | Основной кандидат курса |
| Несколько микросервисов | Независимые границы deployment | Сеть, контракты и ops усложняют старт | Отдельный production-кейс позже |

## 6. Production engineering

В существующем проекте сначала искать реальные границы компонентов, а не навязывать новую архитектуру. Данные пользователя не должны попадать в учебные logs. API-контракт и правила совместимости важны для командных изменений; deployment и migrations углубляются позже.

До приёмки результата сопоставить scope, актуальный snapshot, diff и проверки. Отчёт о действиях не подменяет evidence; стоимость включает человеческую проверку. За технические права отвечает конфигурация среды, за решение о выпуске — назначенный владелец.

## 9. Авторская практическая демонстрация

**Сценарий:** **Иллюстративный поток:** browser form → HTTP request → server validation → persistence adapter → database; ответ возвращается по обратному пути. Endpoint и JSON ниже — учебный контракт-пример, не готовый Workbench API.

```http
POST /api/tickets
Content-Type: application/json

{"title":"Login issue"}
```

Автор разбирает отдельно: (1) UI показывает введённую строку; (2) сервер получает request и применяет правило; (3) storage подтверждает запись; (4) новый read после refresh/restart подтверждает выбранную семантику persistence. Нарисовать sequence diagram и отметить границы ответственности. Наличие UI-элемента или HTTP 2xx само по себе не подтверждает долговременное хранение.

**Статус и границы:** это сценарий будущего рассказа/показа. Полное приложение Engineering Workbench остаётся кандидатом; scaffold и end-to-end запуск не подтверждены. Отдельно указанное фактическое evidence относится только к конкретному ограниченному примеру и не переносится на приложение.

**Платформа и prerequisites:** до исполнения демонстрации указать целевую ОС/shell, версии, точный snapshot, необходимые fixtures, доступы, сеть и последствия команд. Продуктовые installer/flags и billing проверять по текущей документации выбранного продукта. Команды в примере с явной пометкой «иллюстративный» требуют выполнения автором до публикации урока.

**Ожидаемое и фактическое:** ожидаемые наблюдения задают учебный сценарий. Фактическим результатом считать только наблюдение из зафиксированного локального verification-отчёта; обзор документации или проектирование сценария не означает исполнение. Демонстрация предназначена для объяснения материала и не требует сдачи работы от читателя.
