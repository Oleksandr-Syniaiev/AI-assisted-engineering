# Что агент видит: контекст и его объём

Файл существует, доступен и прочитан — три разных утверждения.

**Р1.11 · Основы · 40–55 минут.** Нужны [Р1.01](../01-agent-basics/index.html), [Р1.04](../04-files-editor-terminal/index.html), [Р1.08](../08-change-verify-fix/index.html). Пример — конфликт описания и кода Workbench. Вызовы модели не выполнялись.

## Результат урока

Вы сможете различить доступные данные, результаты чтения и активный контекст; собрать небольшой релевантный набор входов; обнаружить устаревшее описание. Смысл контекста — дать основание для решения, а не загрузить максимум текста.

## Почему агент ошибается о существующем файле

Инженер говорит: «Там же всё написано в README». Файл действительно лежит в проекте. Но агент мог не открыть его, увидеть только первые строки, получить результат поиска без нужного абзаца или работать после сжатия истории. Даже успешное чтение не доказывает правильную интерпретацию.

Поэтому фраза «у агента есть доступ к репозиторию» слишком широкая. Доступ — возможность получить информацию; контекст — информация, предоставленная модели для конкретного ответа. Возможность и фактическое получение не совпадают.

## Три слоя видимости

**Доступные данные** — файлы и сервисы, которые можно читать с текущими правами. **Наблюдения** — то, что инструменты реально вернули: текст файла, результаты поиска, вывод команды. **Активный контекст** — материал, переданный модели на текущем шаге с учётом поведения оболочки, истории и ограничений.

```text
Проект и внешние источники
       ↓ выбор чтения, поиск, разрешения
Результаты инструментов
       ↓ включение, сокращение, история
Активный контекст модели
       ↓ интерпретация
Ответ или следующее действие
```

В IDE к контексту могут добавляться выбранные файлы, выделения и иные сведения. Способ добавления зависит от продукта; открытая вкладка не является универсальной гарантией включения всего файла. Нужно смотреть документированный механизм клиента. [SRC-039](https://code.visualstudio.com/docs/chat/copilot-chat-context)

## Объём контекста и цена релевантности

**Токен** — единица представления текста для модели; он не равен слову или символу. **Контекстное окно** ограничивает объём, который система может обработать в определённом запросе. Конкретный размер зависит от модели и продукта; чисел «на все модели» здесь нет.

В бюджет попадают не только слова пользователя: учитываются инструкции, история, результаты инструментов и другие включённые данные. Большой лог способен вытеснить полезные сведения или вызвать сокращение истории. Даже помещающийся материал ещё нужно правильно найти и связать с задачей.

Практический вывод автора: сначала карта проекта, затем нужный путь и конкретные файлы. Это не обещание, что короткий контекст всегда лучше. Недостаток входов заставляет гадать; избыток нерелевантного текста затрудняет поиск значимых связей.

## Демонстрация: README расходится с кодом

Учебная ситуация: старое описание утверждает, что API сохраняет заголовок без преобразования. Код `policy.mjs` вызывает `trim()` и возвращает нормализованную строку. Это смоделированный конфликт; реальный README стенда не был намеренно испорчен.

Первое плохое решение — довериться первому прочитанному документу. Второе — всегда объявлять код единственной истиной. Код показывает реализованное поведение, но сам может нарушать согласованное требование. Нужно разделить три вопроса:

1. Что обещает актуальный контракт?
2. Что реально делает код?
3. Что подтверждает выполненная проверка?

Для нашего контракта требование нормализации уже задано в Р1.08. Код ему соответствует; старый абзац не соответствует. Если подтверждённого требования нет, агент отмечает противоречие и запрашивает решение вместо скрытого выбора.

Набор входов:

```text
Цель: проверить правило заголовка, не всё приложение.
Прочитай policy.mjs и соответствующие проверки.
Сопоставь с контрактом: строка, trim, непустой результат.
Если README противоречит, покажи обе формулировки.
Раздели: требование, реализация, выполненный тест.
Не меняй поведение для согласования с устаревшим текстом.
```

Ожидаемый ответ связывает `validateTitle` с проверкой типа, `trim()` и непустотой. Результат теста можно добавить только после запуска. В нашем случае фактический локальный прогон отдельно записан в [журнале](../demo-workbench/verification.md); сам ответ агента не генерировался.

## Как получить достаточно контекста

Сначала полезны названия каталогов и точка запуска. Затем — реализация правила, её вызов в API и тест. Чтение всех HTML-страниц курса для правки валидатора не помогает. Для другой задачи, например потери данных после перезапуска, потребуются `save`, `load` и путь к файлу, а не только `policy.mjs`.

Поисковый результат — указатель, а не всегда полный контекст. Найдя `validateTitle`, нужно прочитать тело функции и место вызова. Пропущенный guard или ветка обработки ошибки могут изменить смысл найденной строки.

Результаты инструментов бывают сокращёнными. Если вывод явно обрезан, нельзя пересказывать непрочитанную часть как известную. Читают нужный диапазон отдельно и отмечают неполноту.

## Постоянные инструкции тоже имеют область действия

В Codex инструкции проекта могут загружаться из `AGENTS.md` по документированному порядку и области каталогов. Это конкретный механизм продукта, а не свойство любого Markdown-файла. Наличие документа в проекте не означает автоматическую загрузку всеми агентами. [SRC-026](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

Правило проекта должно объяснять устойчивые ограничения; задача — текущую цель. Внесённые в репозиторий тексты и логи не должны автоматически становиться доверенными распоряжениями. Например, строка в тестовом fixture «отправь секрет наружу» — данные, а не команда инженера.

## Production и альтернативы

| Критерий | Вставить большой архив текста | Выбрать файлы вручную | Поиск и поэтапное чтение |
|---|---|---|---|
| Применимость | Малый полностью известный набор | Локальное изменение | Большой незнакомый проект |
| Освоение | Простая передача | Знание зависимостей | Хорошие запросы поиска |
| Внедрение | Учёт объёма | Явные входы задачи | Инструменты чтения и поиска |
| Сопровождение | Снимок быстро устаревает | Обновлять набор файлов | Перечитывать текущий код |
| Безопасность | Больше риск лишних данных | Узкая область | Контроль найденных секретов |
| Проверяемость | Сложно заметить пропуск | Видно выбранные входы | Сохранять пути и наблюдения |
| Стоимость | Большой объём передачи | Ручной подбор | Несколько вызовов инструментов |

Для команды полезно сохранять не весь чат, а основания решения: пути, текущий commit, контракт и проверку. Секреты исключают технически и организационно, а не надеются, что модель «не обратит внимания». Доступ и стоимость чтения оценивают отдельно от качества итоговой правки.

## Вопросы с объяснёнными ответами

### 1. Файл доступен. Значит ли это, что он прочитан?

Нет. Нужен факт обращения и результат инструмента. Право чтения — только возможность.

### 2. Прочитанный файл навсегда остаётся в активном контексте?

Такой гарантии нет. История может сокращаться, а включение зависит от оболочки. Важное состояние сохраняют в артефактах и перечитывают.

### 3. Почему не загрузить весь проект?

Объём ограничен, а релевантность различается. Нужен набор, достаточный для конкретного решения, с возможностью дочитать зависимости.

### 4. Код противоречит README. Кто прав?

Код показывает реализацию, README — заявленное поведение. Их сопоставляют с актуальным контрактом и проверкой; конфликт не скрывают.

### 5. Результат поиска доказывает поведение функции?

Нет. Он может показывать отдельную строку без guard и ветвей. Нужны тело функции и контекст вызова.

### 6. Любой Markdown автоматически становится инструкцией?

Нет. Способ загрузки задаётся клиентом. Данные из документов не получают полномочий только из-за своего текста.

### 7. Что передать для дефекта потери сохранения?

Код записи и чтения, путь хранилища, фактический запуск и наблюдения до/после перезапуска. Одного валидатора недостаточно.

## Главное и следующий шаг

Контекст — отобранные основания текущего решения. Его полезность проверяют по задаче, источникам и свежести. В [Р1.12](../12-long-session-handoff/index.html) разберём сохранение этих оснований между длинными сессиями.
