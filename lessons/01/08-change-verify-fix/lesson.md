# Поручить изменение, получить проверку, исправить ошибку

Один дефект, неизменное правило и доказательство исправления.

**Р1.08 · Основы · 45–65 минут.** Нужны [Р1.01](../01-agent-basics/index.html), [Р1.06](../06-run-first-application/index.html), [Р1.07](../07-git-checkpoints-diffs/index.html). Пример: JavaScript, Node.js v24.22.1. Используем сохранённые baseline и corrected из первого урока, не изменяя их.

## Результат урока

Вы сможете сформулировать небольшое изменение, воспроизвести дефект, проверить минимальную правку и отделить неудачное исполнение от неверного требования. Ключевой навык — не позволить проверке приспособиться к ошибочному коду.

## Почему «исправь валидацию» слишком расплывчато

В Workbench заявка не должна иметь пустой заголовок. Но что считать пустым: только `""`, пробелы, `null`, число? Нужно ли сохранять пробелы по краям? Без ответа агент может предложить любое из нескольких разумных поведений, и спор о готовности станет спором о неявном требовании.

Фиксируем контракт: принимаются только строки с непустым содержимым после JavaScript `trim()`. Сохраняется нормализованный заголовок. Число не превращается в строку автоматически. Это локальное правило примера, не универсальное требование к любому пользовательскому вводу.

## Контракт и test oracle

**Test oracle** — основание, по которому определяется правильный результат теста. Здесь им служат явные пары входа и ожидаемого выхода:

| Вход | Ожидаемый результат | Причина |
|---|---|---|
| `""` | `{ok:false}` | Нет содержимого |
| `"   "` | `{ok:false}` | После trim строка пуста |
| `" Fix CI "` | `{ok:true,title:"Fix CI"}` | Валидный нормализованный заголовок |
| `7` | `{ok:false}` | Нарушен тип входа |

Проверка не является доказательством только потому, что она зелёная. Если агент поменял ожидаемый результат для пробелов на `ok:true`, тест перестал проверять исходный контракт.

**Регрессия** — поломка поведения, которое уже работало. После исправления пробелов нужно сохранить проверку типа и нормализацию валидной строки. Минимальная правка означает минимальную достаточную область изменения, а не минимальное количество символов любой ценой.

## Причина дефекта в порядке операций

Исходная функция:

```javascript
function baseline(value) {
  if (typeof value !== 'string') return { ok: false };
  if (value.length === 0) return { ok: false };
  return { ok: true, title: value.trim() };
}
```

Для `"   "` исходная длина равна трём, условие пустоты ложно. `trim()` выполняется только при создании успешного результата и превращает заголовок в пустой. Проверка и сохранение работают с разными представлениями одного значения.

Исправленная последовательность:

```javascript
function corrected(value) {
  if (typeof value !== 'string') return { ok: false };
  const title = value.trim();
  if (title.length === 0) return { ok: false };
  return { ok: true, title };
}
```

Теперь и проверка, и выход используют `title`. Проверка типа остаётся первой: иначе вызов `trim()` на числе завершится ошибкой. Изменение не добавляет ограничений длины, HTML-фильтрации или уникальности: этих требований в контракте нет.

## Как поставить задачу агенту

```text
Дефект: baseline принимает title из пробелов.
Контракт: только string; trim до проверки пустоты;
валидный title возвращается нормализованным.
Разбери четыре случая таблицы и воспроизведи проблему.
Предложи минимальное исправление, сохрани проверку типа.
Не меняй ожидаемые результаты ради прохождения теста.
Отчёт: причина, patch, команда, результат, что не проверено.
```

В реальном репозитории добавляют путь к функции, разрешённую область изменения и исходный commit. Если агент обнаружил противоречие между тестом и согласованным требованием, он должен вынести его на обсуждение, а не молча выбрать удобный вариант.

## Проверка автора: красный результат, затем зелёный

Команды из корня курса:

```powershell
node --test lessons/01/01-agent-basics/practice/baseline.test.mjs
node --test lessons/01/01-agent-basics/practice/corrected.test.mjs
```

Два entrypoint используют общий набор проверок. Baseline намеренно оставлен ошибочным: ожидается ненулевой exit code. Вторая команда проверяет исправленную реализацию. Node test runner запускает тесты через `--test`; это стандартный механизм Node.js. [SRC-014](https://nodejs.org/api/test.html)

**Повторно выполнено 03.11.2026:** baseline — 3 passed, 1 failed, exit 1; corrected — 4 passed, 0 failed, exit 0. Падающий случай:

```text
input:    "   "
expected: {"ok":false}
actual:   {"ok":true,"title":""}
```

Это подтверждает конкретную ошибку и её исправление на четырёх случаях. Оно не доказывает правильность API, браузера или БД. Для пути HTTP используется отдельный набор [стенда](../demo-workbench/verification.md). Исходные файлы Р1.01 не переписаны.

## Что делать, если первая попытка не прошла

Если исправление вызывает ошибку на числе, проверяют порядок `typeof` и `trim()`. Если пробелы ещё принимаются, проверяют, по какой переменной измеряется длина. Если тестовый файл не найден, исправляют путь запуска. Если тесты не содержат пробельного случая, добавляют проверку исходного требования, а не объявляют отсутствие падения успехом.

Затем читают diff: не пропала ли проверка типа, не изменились ли ожидания, не добавлена ли ненужная зависимость? Финальный прогон относится к окончательной правке. Изменения после него требуют повторить затронутые проверки.

## Production и альтернативы

В существующем коде валидатор может вызываться из нескольких API. Минимальное исправление сопровождают поиском вызовов, оценкой совместимости и тестом на нужном уровне. Новые правила нельзя добавлять под видом исправления старого дефекта: это меняет поведение для пользователей.

| Критерий | Только ручной пример | Unit-тест функции | Интеграционный HTTP-тест |
|---|---|---|---|
| Применение | Быстро понять дефект | Проверить правило | Проверить подключение правила |
| Освоение | Вход и выход | Assertions и test runner | Сервер и изоляция данных |
| Внедрение | Почти без setup | Небольшой test entrypoint | Запуск среды и cleanup |
| Сопровождение | Повторять вручную | Обновлять контракт осознанно | Поддерживать API и fixtures |
| Безопасность | Не брать реальные данные | Синтетические входы | Временные файлы и локальная сеть |
| Проверяемость | Легко забыть случай | Точный детерминированный результат | Проверка границ компонентов |
| Стоимость | Дёшево разово | Дёшево повторять | Больше setup и времени |

Ни один уровень не заменяет остальные автоматически. Зелёный unit-тест бесполезен для маршрута, который вообще не вызывает эту функцию. Командная проверка связывает требование, код и доказательства одного состояния.

## Вопросы с объяснёнными ответами

### 1. Где именно дефект baseline?

Пустота проверяется до нормализации, а возвращается значение после неё. Для пробелов эти представления различаются.

### 2. Почему нельзя просто вызвать `value.trim()` первой строкой?

Контракт допускает неправильный тип как вход, который нужно отклонить. Число не имеет нужного строкового метода.

### 3. Зачем сохранять падающий baseline?

Он подтверждает, что проверка ловит исходную ошибку. Это намеренный отрицательный контроль.

### 4. Можно менять тесты при исправлении?

Можно, если меняется или уточняется согласованный контракт. Нельзя незаметно ослаблять ожидания ради зелёного результата.

### 5. Четыре теста доказывают работу приложения?

Они проверяют четыре случая одной функции. Другие слои требуют собственных наблюдений.

### 6. Что делать после новой правки в уже проверенном файле?

Повторить относящиеся к ней проверки. Старый результат описывает предыдущее состояние.

### 7. Почему не добавить сразу проверку длины и уникальности?

Это отдельные требования и риски совместимости. Они расширят область изменения и затруднят оценку конкретного исправления.

## Главное и следующий шаг

Устойчивый цикл: контракт → воспроизведение → минимальная правка → неизменные ожидания → diff и проверки. В [Р1.09](../09-github-pull-request/index.html) этот результат станет предложением изменения для команды.
