# Р3.04 — Паттерн 2. Two-pass AGENTS.md (живой артефакт)

**Статус:** Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

**Уровень:** Middle–Senior. **Время:** 35–50 минут, без пилотирования.

**Предварительные знания:** Р3.03, Р3.05; смысл двух проходов не определён как внешний стандарт.

**Результат:** объяснить механизм, разобрать демонстрацию, сравнить альтернативы и выбрать проверку с явными границами доказательности.

## 1. Почему сгенерированный guide бывает бесполезен

Агент просмотрел package scripts и записал в AGENTS.md команду, которая требует закрытый сервис. Или скопировал generic советы «пиши чистый код», забыв правило о запрещённых прямых записях в БД. Формально файл существует, но следующая задача выполняется хуже из-за неверных указаний.

Two-pass AGENTS.md — **рабочий процесс курса**: сначала собрать guide из свидетельств, затем проверить его на ограниченной задаче. Это не специальный формат файла и не найденная общепринятая методология. «Живой» означает поддерживаемый владельцами в version control, а не самостоятельно обновляющийся без review.

## 2. Первый проход: извлечение правил

Инженер определяет аудиторию и scope guide. Из README, scripts, CI, архитектурных решений и действующих инструкций собираются факты. Для каждого кандидата записываются источник, степень уверенности и владелец. Название package script не подтверждает успешный запуск; найденная convention не всегда является обязательной политикой.

```text
Источник → кандидат правила → подтверждение owner → компактный guide
```

Полезны неочевидные указания: где проходит boundary домена, какие checks обязательны, как подготовить тестовую среду, что требует согласования. Не нужно дублировать lint config или переносить целиком все docs. Инструкции должны направлять следующую задачу, а не пересказывать репозиторий.

В разных клиентах отличаются discovery, scope и способы подключения инструкций. VS Code описывает эти механизмы применительно к своим harness. Перед практическим использованием файла нужно проверить целевой клиент; существование AGENTS.md не доказывает, что он будет прочитан. [SRC-202](references.md#src-202)

## 3. Синтетический первый вариант

Для Workbench выбраны следующие правила. Paths и команда ниже иллюстративны; они не утверждают существование такого scaffold в курсе:

```markdown
# Project guide
Область: изменение backend поведения заявок.
Карта: domain — правила статусов; adapters — API и persistence.
Перед изменением: прочитать утверждённый контракт перехода.
Проверка: использовать script check после подтверждения окружения.
Сохранять: public API и согласованность статуса с audit event.
Не добавлять dependencies без решения владельца.
Если runner недоступен: записать ошибку; не заявлять проверку.
```

Фраза про `check` пока недостаточна: следующий исполнитель не знает prerequisites и охват. На первом проходе это допустимый отмеченный пробел, но не готовая команда для production.

## 4. Второй проход: проверка применимости

Выбирается задача малого риска: разобрать `closed → open` без изменения данных. На зафиксированном snapshot проверяется discovery: какие правила нашёл клиент и куда они применены. Затем оценивается результат по независимому контракту, а не по уверенности агента.

```text
guide → безопасная задача → trace/diff/checks → finding → правка guide
```

Если ответ пропустил audit consistency, выясняют причину. Правило могло не загрузиться, быть неясным, конфликтовать с другим источником или быть проигнорированным. Решения различны: изменить scope, формулировку, согласовать конфликт или вынести критичную проверку в CI. Добавление ещё одной строки «обязательно соблюдай» не заменяет диагностику.

Ожидаемый артефакт второго прохода — reviewed diff guide с причинами изменений и известными пробелами. В этом уроке клиент и команды не запускались; trace описан как способ проверки, а не показан как фактический результат.

## 5. Альтернативы подготовки

| Подход | Применимость | Освоение / внедрение | Сопровождение | Безопасность / проверка | Цена |
|---|---|---|---|---|---|
| Ручной шаблон | Малый стабильный проект | Низкие | Ревизии владельца | Прозрачный текст, возможны пропуски | Дёшево начать |
| One-pass генерация | Быстрый черновик | Низкие | Непроверенные правила накапливаются | Нужно подтверждение каждого факта | Экономия автора, возможный rework |
| Two-pass | Повторяющиеся задачи команды | Средние; нужна контрольная задача | Ревизия после дрейфа | Evidence discovery и выполнения | Выше старт, полезнее при повторении |
| Генератор из configs | Машинные факты, команды, paths | Выше; нужен generator | Поддержка schema и шаблонов | Меньше ручных устареваний, смысл policy всё равно review | Оправдан при масштабе |

## 6. Production и жизненный цикл

Guide пересматривается при смене runtime, команды tests, границы модуля или политики зависимостей. Изменение инструкции проходит обычный review: оно влияет на будущие действия агентов. В monorepo корневой guide даёт общую карту, scoped материалы — различия; поддерживать десятки копий одной политики дорого.

Секреты и внутренние данные в guide не помещают. Ссылки должны быть доступны целевому исполнителю, а автономные действия ограничиваются средой. Полезность оценивают по повторяющимся нарушениям, времени поиска, review и rework на сопоставимых задачах. Этот цикл связан с progressive disclosure: компактный guide должен вести к подробностям, когда они нужны.

## 7. Проверка знаний с ответами

### 1. Что здесь означают два прохода?

В этом пакете это предложенная рабочая модель: discovery/draft, затем проверка/переработка. Происхождение названия не найдено; не следует представлять его как общепринятый паттерн.
### 2. Что должно войти в AGENTS.md?

Краткие цели репозитория, проектные соглашения, способы проверки, важные границы и ссылки на необходимый контекст — если это поддерживается выбранным агентом.
### 3. Почему не копировать все правила из linter?

Дублирование создаёт два источника истины и может устареть. В guide лучше указать, что автоматически проверяет tooling, и объяснить только существенные проектные решения.
### 4. Как проверить, что файл был загружен?

Использовать диагностику/References конкретного harness, если она доступна; сделать контролируемую задачу и сверить diff и checks. Не выводить факт загрузки только из наличия файла.
### 5. Что значит «живой артефакт»?

Версионируемый, с понятной областью действия и владельцем; он обновляется при смене тестов, архитектуры и инструментов. Это не означает автоматическую синхронизацию.
### 6. Как поступить с конфликтом org и repo?

Не рассчитывать на универсальный приоритет; согласовать исходники правила с владельцами, проверять отображённые effective instructions и использовать платформенные controls для enforced policy.
### 7. Как измерить ценность Two-pass процесса?

Сопоставить число пропущенных project rules, ошибочных изменений, review/rework и стоимость поддержки до/после на одинаковом сценарии; небольшая демонстрация не доказывает общую эффективность.

## 8. Итоги и источники

Полезное правило связывает намерение, область действия, владельца и проверяемое свидетельство. Источник документации подтверждает механизм в своём продукте; рекомендации курса не являются доказанной универсальной методологией.
