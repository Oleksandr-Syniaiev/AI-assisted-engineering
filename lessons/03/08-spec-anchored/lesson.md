# Р3.08 — Методология 1. Spec-anchored

**Статус:** Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

**Уровень:** Middle–Senior. **Время:** 35–50 минут, без пилотирования.

**Предварительные знания:** Р3.06–Р3.07; короткий мостик: requirement → specification → acceptance check.

**Результат:** объяснить механизм, разобрать демонстрацию, сравнить альтернативы и выбрать проверку с явными границами доказательности.

## 1. Спецификация как точка согласования

Два агента реализуют закрытие заявки. Один возвращает успешный ответ при повторном запросе, второй считает повтор ошибкой. Оба решения могут выглядеть разумно, пока нет согласованного контракта. Спецификация делает выбор явным до того, как он разойдётся по API, tests и данным.

Spec-anchored здесь — **рабочее название курса**, без подтверждённого универсального автора или стандартизованного набора файлов. Оно означает процесс, в котором спецификация связывает намерение, изменение и проверку. Полная SDD-методология будет рассмотрена в разделе 4.

## 2. Механизм трассировки

Для каждого требования фиксируют идентификатор, границу и наблюдаемый критерий. Затем указывают компонент реализации, вид проверки и владельца. Можно идти от требования к evidence и обратно — выяснять, какое требование проверяет конкретный test.

```text
потребность → требование → критерий → компонент → check → review
                  ↑                                ↓
                  согласованное изменение решения / найденный drift
```

Traceability облегчает обнаружение пропусков; сама ссылка не доказывает достаточность проверки. Один happy-path test не подтверждает authorization, конкурентность и восстановление после отказа. NASA описывает требования и их verification в системной инженерии; рабочий процесс для AI-кода — наша адаптация принципа. [SRC-206](references.md#src-206)

## 3. Минимальная спецификация Workbench

Следующий контракт синтетический; бизнес-решения выбраны для учебного примера, а не извлечены из действующего продукта:

```text
CLOSE-01: только назначенный исполнитель может закрыть in_progress.
CLOSE-02: open → closed напрямую запрещён.
CLOSE-03: статус closed и событие Closed фиксируются согласованно.
CLOSE-04: повтор с тем же request key не создаёт второго события.
CLOSE-05: ошибка проверки не меняет состояние заявки.
Не входит: переоткрытие, массовое закрытие, миграция старых событий.
```

Последовательность: проверить identity и роль; проверить request key; оценить текущее состояние; выполнить согласованную запись; вернуть ответ по API-контракту. Детальный порядок idempotency lookup и authorization требует security review: повтор не должен раскрывать чужие данные. Для атомарности потребуется transaction/outbox-подобное решение по архитектуре системы; наличие пункта CLOSE-03 его не реализует.

## 4. Карта проверок

| Критерий | Компонент | Вид evidence | Негативный случай |
|---|---|---|---|
| CLOSE-01 | Application authorization | Role integration test | Чужой исполнитель |
| CLOSE-02 | Domain transition | Unit/property test | Прямое закрытие open |
| CLOSE-03 | Persistence boundary | Transaction/failure integration test | Сбой записи события |
| CLOSE-04 | Request deduplication | Повтор/конкурентный запрос | Два одновременных вызова |
| CLOSE-05 | API + persistence | Снимок до/после ошибки | Некорректная роль или состояние |

Таблица показывает, какую проверку нужно построить. Она не является фактическим отчётом: приложение, tests и агент не запускались. Ожидаемый результат авторского разбора — каждый критерий имеет подходящий вид evidence, а непроверенное отмечено.

Допустим, продукт разрешает администратору закрывать заявку. Меняется CLOSE-01 и role matrix; reviewer проверяет implementation и негативные cases, а остальные свойства должны сохраниться. Старый test нельзя просто удалить ради зелёного CI. Решение записывается с причиной, владельцем и версией, после чего обновляется traceability.

## 5. Альтернативы глубины процесса

| Вариант | Применимость | Освоение / внедрение | Поддержка | Проверяемость / безопасность | Цена |
|---|---|---|---|---|---|
| Ticket + review | Малый обратимый fix | Низкие | Риск потерять детали | Зависит от reviewer и tests | Низкая церемония |
| Test-first / TDD | Поведение хорошо выражается oracle | Средние | Tests и fixtures | Исполняемая обратная связь в своём scope | Быстрый повтор, не охватывает все требования |
| Лёгкий spec-anchored контракт | API, handoff, сложное правило | Средние | Specs, links, owners | Видны пробелы и решения; permissions отдельно | Больше review, меньше скрытых интерпретаций |
| Полный SDD lifecycle | Большая функция и несколько команд | Высокие | Стадии и артефакты | Богатая traceability, риск формальной бюрократии | Высокий setup и поддержка |

## 6. Production и drift

Spec drift появляется, когда код, tests, API schema и текст больше не описывают одно поведение. Причины — срочные fixes, неактуальные ссылки и разные владельцы. Проверка drift должна смотреть содержимое, а не только наличие файла. Иногда код отражает исправленную реальность, иногда нарушает договорённость; решение принимает owner по истории и evidence.

Для legacy сначала описывают текущие контракты и characterization tests, затем согласуют desired change. В monorepo перечисляют потребителей API и порядок миграции. Specs не хранят secrets; CI обеспечивает автоматизируемые свойства, review — смысл и исключения. Стоимость процесса оправдана, когда уменьшение неоднозначности и rework превышает поддержку документов. Следующий раздел расширяет этот baseline до SDD, stages, loops и сравнения конкретных tooling.

## 7. Проверка знаний с ответами

### 1. Что в этом курсе значит Spec-anchored?

Рабочая интерпретация: спецификация связывает согласованное намерение с реализацией и проверкой. Внешнее происхождение точного термина не подтверждено.
### 2. Чем это отличается от полного SDD?

Spec-anchored — минимальная концептуальная база и источник сравнения; полный SDD в разделе 4 раскрывает стадии, артефакты, gates и lifecycle. Это педагогическое разграничение, а не общепринятый стандарт терминов.
### 3. Какая связь нужна между requirement и test?

Проверяемый критерий должен указывать ожидаемое наблюдаемое поведение и способ проверки; traceability помогает увидеть пропущенные и осиротевшие проверки, но не гарантирует качество oracle.
### 4. Кто утверждает конфликт спецификации с production behavior?

Назначенный product/domain owner совместно с техническим владельцем; агент не должен сам решать изменение публичного или бизнес-контракта.
### 5. Когда хватит лёгкого task contract?

Для локального, обратимого и низкорискового изменения с ясными границами и тестом. Если затронуты API, data migration, permissions или compliance, формализация должна усилиться.
### 6. Как обнаружить spec drift?

Сопоставлять критерии, links, тесты, runtime/API schema и историю изменений; отмечать непокрытые/неиспользуемые требования и владельца обновления.
### 7. Какой переход в Р4?

Р4.01 вводит SDD и модели зрелости, а Р4.15 использует эту рабочую концепцию как baseline для сравнения методологий; состав уровней нужно отдельно установить.

## 8. Итоги и источники

Полезное правило связывает намерение, область действия, владельца и проверяемое свидетельство. Источник документации подтверждает механизм в своём продукте; рекомендации курса не являются доказанной универсальной методологией.
