# Р3.07 — Как изучать методологии?

**Статус:** Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

**Уровень:** Middle–Senior. **Время:** 35–50 минут, без пилотирования.

**Предварительные знания:** Р3.01, Р3.06.

**Результат:** объяснить механизм, разобрать демонстрацию, сравнить альтернативы и выбрать проверку с явными границами доказательности.

## 1. Название методологии не является доказательством

Одна статья обещает управляемую разработку через спецификации, другая — через роли агентов. Сравнивать лозунги бесполезно: «качество» может означать больше документов, меньше bugs или скорость первого demo. Сначала определяют единицу сравнения, задачу и evidence.

Методология — система принципов и процесса. Инструмент реализует часть процесса. Продуктовая платформа может содержать инструменты, политики и hosted runtime одновременно. Один паттерн уточнения вопросов нельзя корректно оценить как полную замену delivery-платформе без выравнивания scope.

## 2. Порядок исследования

```text
идентификация проекта → pinned версия/дата → цели и артефакты
      → реальный механизм → ограничения → общий кейс → evidence → выбор
```

Фиксируют автора/организацию, официальный repo, лицензию, release/status и выбранный компонент. Документация подтверждает опубликованное описание. Исходный код помогает проверить механизм. Реальный isolated run показывает поведение выбранной конфигурации. Независимое исследование может подтвердить ограниченную эффективность, но не гарантирует локальный ROI.

Для каждого важного утверждения полезны четыре метки: проверено по источнику, поддержано косвенно, интерпретация и не подтверждено. «Официально написано, что инструмент ускоряет разработку» подтверждает существование заявления; само ускорение требует сравнения.

## 3. Документальное сравнение двух подходов

Рассмотрим одну задачу Workbench: закрыть заявку при согласованных условиях и сохранить audit event. В качестве публичных объектов берём GitHub Spec Kit и Fission-AI OpenSpec. Просмотрены официальная документация и README, без установки CLI и запуска workflow.

| Объект | Что подтверждено документально | Что не установлено здесь |
|---|---|---|
| GitHub Spec Kit | Toolkit со структурированным spec-driven процессом; overview показывает Specify → Plan → Tasks → Implement → Converge | Фактическая скорость, качество конкретной интеграции, цена pilot |
| OpenSpec | Репозиторий описывает spec-driven development для AI coding assistants и работу с изменениями/спецификациями | Полный execution trace, функциональная совместимость текущего release с выбранным клиентом |

Источники: [SRC-208](references.md#src-208), [SRC-209](references.md#src-209). Это разные документированные поверхности; таблица не устанавливает победителя и не описывает все актуальные команды. Для executable tutorial потребуются pinned release и повторная сверка инструкций.

## 4. Общий протокол практической оценки

Каждый подход начинает с одной исходной версии проекта. Требование, oracle, доступные инструменты, модельный бюджет и среда должны быть сопоставимы. Артефакты предыдущего подхода не переносятся следующему незаметно: иначе сравнивается накопленная подготовка.

Пример evidence table для одного trial:

```text
Задача/commit: Workbench close request, исходный SHA.
Реализация: выбранный framework и зафиксированная версия.
Требования: роли, предусловия, повтор, audit consistency.
Результат: artifact paths, diff, checks на итоговом commit.
Риски: scope violations, неразрешённые вопросы, непроверенное.
Затраты: setup + usage + ожидание + review + rework.
```

Числовые показатели здесь отсутствуют: это шаблон измерений, а не проведённый эксперимент. Несколько задач/попыток и описание ограничений необходимы для более устойчивого решения. Качество оценивается по неизменным критериям, а не числу созданных Markdown-файлов.

## 5. Единая rubric и альтернативы выбора

| Измерение | Что сравнить | Как не исказить |
|---|---|---|
| Применимость | Тип задач, brownfield, командный размер | Не сравнивать весь продукт с одним паттерном |
| Освоение | Понятность терминов, нужные навыки | Не считать знакомый автору подход автоматически проще |
| Внедрение | Setup, доступы, интеграции | Включить первоначальные расходы |
| Сопровождение | Updates, drift, владельцы | Учитывать цену после demo |
| Безопасность | Permissions, secrets, dependencies | Не принимать prompt за enforcement |
| Проверяемость | Traceability, tests, негативные сценарии | Не менять oracle под результат |
| Стоимость | Runtime, люди, инфраструктура | Считать принятое изменение, включая rework |

Можно ограничиться документальным обзором, провести небольшой pilot или строить собственный workflow. Первый дешевле и объясняет устройство, но не измеряет эффективность. Pilot дороже, зато даёт локальное evidence. Собственный процесс обеспечивает контроль, но переносит поддержку на команду. Иногда достаточно обычного issue, tests и review.

## 6. Production-решение

Проверяют лицензию, доверие к dependencies, совместимость с policy, возможность отключения/экспорта и поддержку legacy. В monorepo оценивают влияние общих инструкций и generated config на чужие команды. Секреты и customer data не должны попадать в публичный benchmark dataset.

Результат исследования — объяснимое решение: принять ограниченный компонент, провести дополнительный trial или отказаться при конкретных ограничениях. В следующем уроке Spec-anchored станет рабочим baseline, относительно которого проще оценивать дополнительные процессы раздела 4.

## 7. Проверка знаний с ответами

### 1. Почему начинать с версии и происхождения?

Название может обозначать изменяемый продукт, метод, workflow или сообщество. Без автора, версии и даты неясно, какое утверждение проверяется.
### 2. Чем vendor claim отличается от verified behavior?

Vendor claim — заявление источника о своём продукте. Verified behavior требует наблюдаемого подходящего свидетельства: документированного механизма или воспроизводимой проверки в описанном scope.
### 3. Что сравнивать на общем кейсе?

Полноту/изменение требований, traceability, работу с существующим кодом, quality checks, review/rework, время и стоимость, настройку/сопровождение, безопасность, переносимость.
### 4. Почему сравнивать один прогон недостаточно?

Результат зависит от задачи, случайности генерации, версии, модели и reviewer. Один пример показывает возможность/проблему, но не устойчивую частоту или причинный эффект.
### 5. Как использовать продукт без доступа?

Указать document-only, фиксировать claims и видимые ограничения; не приписывать установку/исполнение. Если критична практика, отложить hands-on вывод до доступной среды.
### 6. Как строить source log?

Для каждого ID записать название, организацию, URL, дату/версию, дату просмотра, тип, поддерживаемые тезисы и ограничения; отдельно перечислить источники, которые пока не открывались.
### 7. Как связан раздел с Р4?

Р3.07 задаёт методы чтения и rubric; Р4.16–Р4.20 применяют общий кейс к конкретным вариантам и накапливают сопоставимые данные.

## 8. Итоги и источники

Полезное правило связывает намерение, область действия, владельца и проверяемое свидетельство. Источник документации подтверждает механизм в своём продукте; рекомендации курса не являются доказанной универсальной методологией.
