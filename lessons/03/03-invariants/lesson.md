# Р3.03 — Паттерн 1. Инварианты

**Статус:** Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

**Уровень:** Middle–Senior. **Время:** 35–50 минут, без пилотирования.

**Предварительные знания:** Р3.02; основы permissions, sandbox, секретов и проверки из GAP-02.

**Результат:** объяснить механизм, разобрать демонстрацию, сравнить альтернативы и выбрать проверку с явными границами доказательности.

## 1. От пожелания к проверяемому свойству

«Не ломай архитектуру» не сообщает, какая зависимость запрещена. «Закрытую заявку нельзя открыть обычным запросом смены статуса» уже задаёт наблюдаемое ограничение. Инвариант — свойство, сохраняемое при всех допустимых состояниях или переходах внутри явно указанной границы.

Область важна. Статусный инвариант приложения не означает, что администратор никогда не сможет исправить запись напрямую. Если такое исправление допустимо, оно должно иметь отдельный процесс и аудит. Если запрещено, техническая граница должна охватывать и этот путь.

## 2. Виды инвариантов

| Вид | Пример | Подходящая проверка | Основной пробел |
|---|---|---|---|
| Доменный | `closed` не переходит в `open` обычным API | Unit/property/integration tests, транзакция | Конкурентные и обходные пути |
| Архитектурный | Domain не импортирует DB adapter | Анализ dependency graph | Динамические связи вне модели |
| Данных | Статус и audit event фиксируются согласованно | Transaction/integration checks | Поведение при частичном отказе |
| Организационный | Production deploy требует approval | Identity и deployment gate | Bypass и усталость reviewer |
| Доступа | Агент не читает production secrets | Ограничение среды и credentials | Сетевые/побочные каналы |

Документирование ограничений помогает reasoning. Для критичных рисков нужен независимый от текста контроль; OWASP рекомендует уменьшать полномочия и учитывать недоверенные данные. Это guidance по угрозам, а не доказательство полной защиты. [SRC-204](references.md#src-204)

## 3. Механизм проектирования

Сначала формулируют множество допустимых состояний и действия. Затем записывают property, выбирают enforcement point и проверку. Последними назначают owner, обработку нарушения и порядок изменения самого правила.

```text
граница → свойство → действие, способное нарушить его
        → место предотвращения → независимая проверка → owner
```

Unit test проверяет логику функции, но не доказывает атомарность двух записей. Проверка БД защищает своё ограничение, но не знает смысл пользовательского требования. Review нужен там, где свойство нельзя полностью выразить автоматическим правилом. Источник требования и связь с verification должны сохраняться. [SRC-206](references.md#src-206)

## 4. Демонстрация перехода статуса

Для синтетического Workbench примем правило: закрытая заявка не возвращается в open через обычную операцию. Разрешённые переходы определены явно:

```javascript
const allowed = {
  open: new Set(['in_progress']),
  in_progress: new Set(['closed']),
  closed: new Set()
};
function canTransition(from, to) {
  return Object.hasOwn(allowed, from) && allowed[from].has(to);
}
```

Иллюстративный JavaScript использует `Object.hasOwn`, доступный в Node.js 16.9+; выполнение здесь не проводилось. Ожидается `true` для `open → in_progress` и `false` для `closed → open`, неизвестного исходного состояния и `open → closed`. Возврат `false` сам по себе не сообщает API-код ошибки: transport contract проектируется отдельно.

Такая функция не решает гонку: два запроса могут прочитать один статус, пройти разные проверки и затем записать несовместимые данные. Для persistence нужны транзакция и условное обновление по версии/ожидаемому состоянию. Audit event должен согласованно отражать принятое изменение; отказ записи журнала не должен оставлять незаметную смену статуса. Это архитектурное требование примера, не проверенная реализация БД.

## 5. Проверки и ограничения

| Средство | Освоение / внедрение | Сопровождение | Проверяемость | Безопасность и цена |
|---|---|---|---|---|
| Инструкция в guide | Низкие | Ревизия текста | Объясняет правило, не блокирует нарушение | Дёшево, слабая гарантия |
| Unit/property tests | Средние | Oracle и генераторы входов | Поведение внутри тестовой модели | Быстрый повтор, не покрывает всю интеграцию |
| БД/API guard | Средние/высокие | Миграции, race/error handling | Ограничивает реальный write path | Сильнее в своей границе, дороже внедрение |
| Ручной review | Нужна экспертиза | Rubric и ответственность | Проверяет смысл и исключения | Время человека и риск пропуска |

## 6. Production-практика

В legacy сначала ищут реальные переходы и потребителей: правило, красивое на диаграмме, может противоречить существующему recovery process. В monorepo проверяют, что второй сервис не пишет те же данные напрямую. CI должен обнаруживать намеренное нарушение правила, иначе его защита не продемонстрирована.

Правило может измениться по решению продукта. Поэтому «инвариант» не означает вечный запрет менять требования. Изменение свойства проходит review, обновляет проверки и миграционный план. Агент не должен снимать check просто потому, что он мешает текущему patch. Результат урока — умение назвать property, границу, enforcement и предел evidence, а не обещание доказать всю систему одним тестом.

## 7. Проверка знаний с ответами

### 1. Чем invariant отличается от обычного требования?

Инвариант формулирует условие, которое должно сохраняться во всём заявленном множестве состояний/операций; требование может задавать отдельную функцию или целевой результат. Граница должна быть названа.
### 2. Достаточно ли добавить правило в AGENTS.md?

Нет. Файл направляет модель, но не обеспечивает неизменность. Для критичного свойства добавляют тест, статический контроль или ограничение полномочий.
### 3. Как проверить статусный инвариант?

Покрыть разрешённые и запрещённые переходы тестами на бизнес-слое и интеграцией с persistence, чтобы конкурентные обновления и транзакции не обходили проверку.
### 4. Что делать с правилом, которое нельзя автоматизировать?

Сделать критерии review наблюдаемыми, назначить владельца/approval и явно описать предел гарантии. Не маркировать документальную проверку как автоматическую.
### 5. Почему минимальный blast radius важен?

Если модель ошибается или получает malicious context, ограниченные права сокращают возможные побочные эффекты; OWASP рекомендует least privilege и human approval для high-risk действий.
### 6. Как доказать, что инвариант выполнен?

Только в пределах свидетельства: тест доказывает покрытый набор сценариев, статический check — заданные паттерны, sandbox — доступ в своём scope. Ни один локальный check сам по себе не доказывает отсутствие всех дефектов.
### 7. Как тема готовит Two-pass AGENTS.md?

Инварианты дают содержание правил; Р3.04 рассматривает, как выводить компактную инструкцию из репозитория и проверять её на реальной задаче.

## 8. Итоги и источники

Полезное правило связывает намерение, область действия, владельца и проверяемое свидетельство. Источник документации подтверждает механизм в своём продукте; рекомендации курса не являются доказанной универсальной методологией.
