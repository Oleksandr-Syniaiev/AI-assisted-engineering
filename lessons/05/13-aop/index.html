Р5.13 — Паттерн 22. Aspect Oriented Programming (AOP)

Статус: Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

Уровень: Middle–Senior/Staff, Tech Lead. Время: 35–50 минут, оценка без пилотирования.

Предварительные знания: Р4.06, Р5.06–Р5.07; уточнить классический AOP и scope паттерна.

Результат обучения: Отделить классический AOP для сквозных concerns от возможной метафоры общих agent policies/hooks.

1. Инженерная проблема и определения

Aspect Oriented Programming выражает сквозные concerns отдельно от базовой функциональности. Классический пример — tracing во многих методах. В AspectJ используются join points, pointcuts, advice и weaving. Это конкретная языковая модель, а не любое правило, применяемое «поперёк» процесса.

В curriculum смысл агентного паттерна AOP не уточнён. Связь с hooks/policies в этом уроке — явно ограниченная аналогия.

Основания и ограничения: SRC-528 · SRC-529. Рабочие модели и инженерные рекомендации не объявляются универсальными стандартами.

2. Архитектура и механизм

Join point — определённая точка выполнения, pointcut выбирает такие точки, advice задаёт дополнительное поведение. Weaving соединяет aspects и базовую программу. Обычный middleware или callback может решать похожую задачу, но не становится эквивалентом AspectJ.

базовая логика + выбранные точки применения + advice
                         → результирующее поведение

В агентной среде lifecycle hook запускает код на событии runtime. Он не обязан выполнять weaving и не получает автоматически семантику классического AOP.

3. Разобранная авторская демонстрация

Для Workbench требуется trace вызовов закрытия. Есть три реализации: явный вызов logger в service, middleware вокруг API и аспект вокруг подходящих service methods. Псевдокод показывает только идею:

выбранные операции: closeRequest
перед вызовом: записать run/task correlation ID без payload
после успеха: записать результат и длительность
после ошибки: записать тип отказа и завершить span

Это не executable AspectJ syntax. При explicit call точка логирования видна в функции, но её легко забыть. Middleware может пропустить внутренний вызов не через HTTP. Aspect pointcut может неожиданно охватить новый метод при rename/рефакторинге.

Отдельно рассмотрим agent before-tool hook: он ограничивает proposed action. Сходство в отделении concern, различие — в event domain и исполнении. Authorization всё равно должен проверяться у trusted domain boundary, чтобы альтернативный путь не обходил правило.

Платформа и проверка: Engineering Workbench — кандидат сквозного проекта, входы синтетические. Конкретные prerequisites приведены рядом с кодом/командами; псевдокод и JSON — учебные форматы. Приложение, тесты, агенты и продукты здесь не запускались. Ожидаемые свойства не являются фактическим результатом.

4. Production, риски и сопровождение

Сквозной механизм может скрывать control flow и порядок нескольких обработчиков. Тестируйте совместное применение, ошибки advice/hook, performance и отладку. Широкий pointcut или глобальный hook способен увеличить blast radius. Для маленькой системы явная композиция часто дешевле специального tooling.

В legacy фиксируют текущие контракты и baseline; в monorepo — затронутых consumers и owners. Приёмка связывается с конкретным состоянием кода и неизменными критериями. Проверяемые автоматические свойства идут в tests/CI, а неоднозначные решения — к назначенному владельцу. Полная стоимость включает setup, обучение, usage, ожидание, review, rework и поддержку версий. Непроверенное указывается явно.

5. Альтернативы и trade-offs

ПодходПрименимостьОсвоение, внедрение, сопровождение и цена компромисса
Явная композицияНемного мест примененияПрозрачно, возможны дубли и пропуски
Middleware/decorator/hooksИзвестные boundariesУмеренный setup, проверять bypass пути
Классический AOPМного cross-cutting join pointsВыше обучение и build/debugging цена

Это качественное сравнение, а не benchmark. Проверяемость зависит от подходящего независимого evidence, безопасность — от фактических boundaries и возможности обхода. Дополнительный tooling оправдан, если польза для принятых outcomes покрывает затраты и новые отказные режимы.

6. Проверка знаний с объяснёнными ответами

1. Что такое pointcut?

Выражение, выбирающее точки выполнения, где к аспекту привязывается advice.

2. Почему hooks не автоматически AOP?

Hook может быть callback на lifecycle event без advice/weaving и не обладать семантикой join point классического AOP.

3. Какое преимущество explicit call?

Путь исполнения очевиднее; цена — возможное дублирование и пропущенные call sites.

4. Когда аспект оправдан?

Когда concern действительно cross-cutting, набор join points понятен и команда умеет диагностировать weaving.

5. Как обнаружить скрытый order bug?

Интеграционные тесты на несколько аспектов/hooks, наблюдаемая трасса вызовов и закреплённый порядок/семантика.

6. Можно ли назвать agent policies аспектами?

Только как оговорённую метафору; нельзя выдавать за стандартную или технически эквивалентную реализацию.

7. Как enforce запрет в обход hooks?

Архитектурными тестами, ограничением API/permissions и интеграционной проверкой всех доступных путей.

7. Итоги и следующий шаг

Отделить классический AOP для сквозных concerns от возможной метафоры общих agent policies/hooks. Главный критерий — объяснимое решение с границами ответственности и доказательности.
