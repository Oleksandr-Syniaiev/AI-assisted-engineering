Р5.07 — Паттерн 16. Архитектурные тесты

Статус: Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

Уровень: Middle–Senior/Staff, Tech Lead. Время: 35–50 минут, оценка без пилотирования.

Предварительные знания: Р3.03, Р5.06; определить границы модулей и зависимости.

Результат обучения: Кодировать один выбранный архитектурный инвариант исполняемой проверкой и понимать пределы такого контроля.

1. Инженерная проблема и определения

Архитектурный тест делает согласованное структурное правило исполняемым. Пример: domain не импортирует web или DB adapters. Он проверяет соответствие правилам выбранной модели зависимостей, но не доказывает, что архитектура выбрана правильно.

ArchUnit анализирует Java bytecode; dependency-cruiser предоставляет правила import graph для JS/TS. Их области обнаружения и ограничения различаются.

Основания и ограничения: SRC-518 · SRC-519 · SRC-520. Рабочие модели и инженерные рекомендации не объявляются универсальными стандартами.

2. Архитектура и механизм

Сначала определяют boundary и rationale, затем строят граф зависимостей и проверяют forbidden/allowed relations. В CI нарушение должно давать понятный сигнал с source/target. Dynamic imports, reflection, generated code и неверный scope анализа могут создавать пропуски или ложные срабатывания.

архитектурное решение → правило → модель графа → violation → owner

Изменение test-rule рассматривают как архитектурный diff. Удаление запрета только ради зелёного CI снимает защиту вместо исправления зависимости.

3. Разобранная авторская демонстрация

Для синтетического TypeScript Workbench установлено: src/domain не зависит от src/adapters. Иллюстративный фрагмент конфигурации dependency-cruiser:

module.exports = {
  forbidden: [{
    name: 'domain-without-adapters',
    severity: 'error',
    from: { path: '^src/domain' },
    to: { path: '^src/adapters' }
  }]
};

Пример требует Node.js, установленной совместимой версии dependency-cruiser и настроенного TS resolution; версия и actual command до исполнения должны быть закреплены. Здесь анализатор не запускался.

Если domain service импортирует DB implementation, ожидается violation. После инверсии зависимости domain использует собственный interface, adapter реализует его. Затем проверяют, что анализ охватывает тестовый нарушающий import: успешный scan пустой папки не подтверждает правило. Пропуск через generated path или alias требует диагностики scope, а не игнорирования отчёта.

Платформа и проверка: Engineering Workbench — кандидат сквозного проекта, входы синтетические. Конкретные prerequisites приведены рядом с кодом/командами; псевдокод и JSON — учебные форматы. Приложение, тесты, агенты и продукты здесь не запускались. Ожидаемые свойства не являются фактическим результатом.

4. Production, риски и сопровождение

В legacy полезны временные waivers с owner, причиной и сроком пересмотра. Тотальный запрет всех текущих циклов может заблокировать любую работу; постепенная стратегия не допускает новых нарушений и уменьшает старые. В monorepo согласуют import conventions и скорость CI, чтобы check оставался используемым.

В legacy фиксируют текущие контракты и baseline; в monorepo — затронутых consumers и owners. Приёмка связывается с конкретным состоянием кода и неизменными критериями. Проверяемые автоматические свойства идут в tests/CI, а неоднозначные решения — к назначенному владельцу. Полная стоимость включает setup, обучение, usage, ожидание, review, rework и поддержку версий. Непроверенное указывается явно.

5. Альтернативы и trade-offs

ПодходПрименимостьОсвоение, внедрение, сопровождение и цена компромисса
Architecture reviewСмысловые границыНизкий tooling setup, высокая повторная работа эксперта
ArchUnitJVM и bytecode modelПовторяемые rules, нужны понимание scope и JVM setup
dependency-cruiserJS/TS import graphБыстрый static feedback, требуется resolution/config maintenance

Это качественное сравнение, а не benchmark. Проверяемость зависит от подходящего независимого evidence, безопасность — от фактических boundaries и возможности обхода. Дополнительный tooling оправдан, если польза для принятых outcomes покрывает затраты и новые отказные режимы.

6. Проверка знаний с объяснёнными ответами

1. Чем архитектурный тест отличается от unit-теста?

Он проверяет структурные отношения модулей/пакетов, тогда как unit-тест обычно проверяет поведение ограниченной единицы.

2. Доказывает ли прохождение теста корректность архитектуры?

Нет. Оно показывает соответствие формализованному правилу на охваченном графе зависимостей.

3. Когда запрет циклов полезен?

Когда цикл затрудняет независимую сборку, тестирование или изменение компонентов; допустимость нужно оценивать для системы, а не объявлять циклы всегда невозможными.

4. Что такое false positive здесь?

Анализатор классифицировал зависимость как нарушение, хотя она не противоречит принятой архитектурной границе; сигнал требует проверки правила и модели анализа.

5. Можно ли enforce архитектуру через prompt?

Prompt может сообщить намерение агенту, но для устойчивого ограничения нужен независимый CI/static check или другой enforcement.

6. Как обновлять архитектурное правило?

Рассматривать его изменение как архитектурное решение, проходящее review с обоснованием, миграцией и тестами, иначе guardrail может быть снят ради зелёного CI.

7. Что сравнить при выборе инструмента?

Язык, тип построенного графа, динамические зависимости, скорость, понятность отчетов, интеграцию в тесты и цену ложных срабатываний.

7. Итоги и следующий шаг

Кодировать один выбранный архитектурный инвариант исполняемой проверкой и понимать пределы такого контроля. Главный критерий — объяснимое решение с границами ответственности и доказательности.
