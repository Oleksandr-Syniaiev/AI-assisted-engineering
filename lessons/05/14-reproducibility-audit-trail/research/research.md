# Исследование Р5.14: Паттерн 23. Reproducibility unit + audit trail

## Метаданные

- Дата исследования и проверки источников: 2026-11-02.
- Зависимости curriculum: Р5.05, Р5.09, Р5.02; GAP-12.
- Статус: Research / Outline; готовый урок не написан.
- Граница: документальное исследование и авторский разбор; установка продукта, benchmarking и запуск примеров не выполнялись.
- Практика: разобранная демонстрация без самостоятельного задания, сдачи или обязательного создания читателем артефакта.

## Исследовательские вопросы и ответы

### 1. Observability и audit trail идентичны?

Нет. Observability помогает понять runtime состояние; audit trail поддерживает доказуемую историю значимых действий и решений. [SRC-512](sources.md#src-512); [SRC-531](sources.md#src-531); [SRC-532](sources.md#src-532)

### 2. Что значит reproducible run?

Повторение процедуры/inputs в контролируемых условиях; идентичность output должна быть отдельно доказана. [SRC-512](sources.md#src-512); [SRC-531](sources.md#src-531); [SRC-532](sources.md#src-532)

### 3. Какие поля важны в manifest?

Task/run ID, source commit, спецификация/конфиги, tool/model/runtime IDs, environment, artifacts и ссылки на checks/decisions. [SRC-512](sources.md#src-512); [SRC-531](sources.md#src-531); [SRC-532](sources.md#src-532)

### 4. Почему хранить весь transcript рискованно?

В нём могут быть секреты, персональные данные и код; минимизация, redaction, retention и access control обязательны. [SRC-512](sources.md#src-512); [SRC-531](sources.md#src-531); [SRC-532](sources.md#src-532)

### 5. Как связывать события между системами?

Стабильными run/task/trace IDs и ссылками на commit, PR, CI run, approval и deployed artifact. [SRC-512](sources.md#src-512); [SRC-531](sources.md#src-531); [SRC-532](sources.md#src-532)

### 6. Что защищает log integrity?

Контроль записи и чтения, append-only/tamper-evident storage, key custody, clock source и аудит доступа; отдельные меры имеют свои границы. [SRC-512](sources.md#src-512); [SRC-531](sources.md#src-531); [SRC-532](sources.md#src-532)

### 7. Как доказать chain-of-custody?

Хэш/подпись артефакта с provenance, известным источником идентичности и проверяемым хранением; SLSA описывает supply-chain provenance, а не весь AI reasoning. [SRC-512](sources.md#src-512); [SRC-531](sources.md#src-531); [SRC-532](sources.md#src-532)

## Определение и границы

«Reproducibility unit» — не установленный стандартный термин curriculum. Рабочая модель: атомарная запись, позволяющая связать цель, входы, версии, действия, environment, outputs и evidence одного agent run.

## Механизм и архитектура

Run manifest ссылается на commit/spec/config digests и runtime/version, trace хранит этапы/инструменты/результаты, audit log фиксирует identity и решения. Пакет должен защищать целостность, связывать причинность и минимизировать чувствительные payload.

## Сравнение альтернатив

Матрица — качественная инженерная оценка, не benchmark. Перед выбором согласовать вес критериев с риском и измерять один и тот же outcome.

| Подход | Применимость | Освоение / внедрение | Сопровождение | Безопасность | Проверяемость | Стоимость |
|---|---|---|---|---|---|---|
| Текстовый лог | Локальная отладка малой системы. | Самый дешёвый старт; схема дрейфует. | Пересматривать при изменении процесса/границ; закрепить владельца и версию. | Секреты могут утечь; причинные связи трудно подтвердить. | Сопоставить с независимым oracle и точным состоянием. | Низкая цена сбора, высокая цена расследования при сложных циклах. |
| Structured traces + события | Диагностика multi-step flow и latency/cost по компонентам. | Нужно внедрить instrumentation, retention и semantic conventions. | Пересматривать при изменении процесса/границ; закрепить владельца и версию. | Доступ гранулируется, но payload может содержать PII/secrets. | Сопоставить с независимым oracle и точным состоянием. | Умеренная стоимость storage/аналитики; хорошая наблюдаемость при консистентном schema. |
| Provenance manifest + signed audit | Compliance, release provenance и воспроизводимая проверка цепочки. | Высокая стоимость интеграции и эксплуатации. | Пересматривать при изменении процесса/границ; закрепить владельца и версию. | Сильнее tamper evidence при правильном key management; лог сам по себе не предотвращает злоупотребление. | Сопоставить с независимым oracle и точным состоянием. | Наибольшая TCO, оправданная высоким риском/регуляторной потребностью. |

## Разобранная авторская демонстрация

Разобрать manifest одного Workbench PR: task ID, commit, config hash, model/provider ID, check run IDs, approval event и итоговый commit. Показать, что при недоступности модели точное повторение может быть невозможным.

Ожидаемые выводы — проектируемые критерии walkthrough, не фактические результаты запуска.

## Применение в production

Определить immutable/append-only storage, подписи/доступ, retention, redaction, clock/identity, correlation IDs, incident export, tamper threat model и процедуру воспроизведения в безопасном sandbox.

Для любой демонстрации явно указать платформу/harness, prerequisites и статус исполнения. Если команда или API не проверялись на выбранной версии, показывать их как иллюстрацию документации, не как воспроизводимую инструкцию.

## Неопределённости и проверка перед написанием урока

Нельзя обещать бит-в-бит повтор model output без доказанного deterministic runtime и неизменных внешних зависимостей; реальный scope воспроизведения надо определить для каждого артефакта.

Перед подготовкой урока заново проверить текущую версию документации, требования доступа, модель безопасности, доступность функций и точные команды выбранной платформы. Независимое сравнение и эксплуатационные измерения в этом пакете не проводились.

## Кандидат демонстрации и критерии

Разобрать manifest одного Workbench PR: task ID, commit, config hash, model/provider ID, check run IDs, approval event и итоговый commit. Показать, что при недоступности модели точное повторение может быть невозможным.

Критерии разбора: цель/контракт определены; альтернативы сопоставлены на одинаковом scope; ожидаемое поведение отделено от наблюдаемого; production-риск и способ независимой проверки названы; отсутствующие данные помечены.
