# План урока Р5.14: Паттерн 23. Reproducibility unit + audit trail

**Статус:** Research / Outline; урок не написан.  **Предпосылки:** Р5.05, Р5.09, Р5.02; GAP-12.

## Результат обучения

Собрать минимальный пакет provenance и аудита, объяснив, что повторяемость не обещает идентичный LLM output.

## План разделов урока

1. **Проблема и мотивация:** инженерная задача и границы применения темы.
2. **Определение и терминология:** «Reproducibility unit» — не установленный стандартный термин curriculum. Рабочая модель: атомарная запись, позволяющая связать цель, входы, версии, действия, environment, outputs и evidence одного agent run.
3. **Механизм:** Run manifest ссылается на commit/spec/config digests и runtime/version, trace хранит этапы/инструменты/результаты, audit log фиксирует identity и решения. Пакет должен защищать целостность, связывать причинность и минимизировать чувствительные payload.
4. **Архитектура:** схема компонентов, состояния, потока данных/управления, владельцев и enforcement boundary; объяснить, где есть nondeterminism.
5. **Практический разбор:** Разобрать manifest одного Workbench PR: task ID, commit, config hash, model/provider ID, check run IDs, approval event и итоговый commit. Показать, что при недоступности модели точное повторение может быть невозможным.
6. **Production:** Определить immutable/append-only storage, подписи/доступ, retention, redaction, clock/identity, correlation IDs, incident export, tamper threat model и процедуру воспроизведения в безопасном sandbox.
7. **Trade-offs:** сравнить с альтернативами по применимости, освоению, внедрению, сопровождению, безопасности, проверяемости и стоимости; не приписывать общий ranking.
8. **Вопросы с ответами:** использовать сценарные вопросы ниже; объяснить ход решения, не только термин.
9. **Итоги и переход:** назвать limitations и связать с зависимой следующей темой.

## Практическая демонстрация и проверяемость

Это разбор автора, не задание читателю. Показать один обычный сценарий и один отказ/negative case. Ожидаемый результат формулировать как критерий; фактическим считать только вывод реально выполненной команды в зафиксированной среде. Сейчас продуктовый запуск/benchmark не заявлен.

## Вопросы для проверки знаний с ответами

### 1. Observability и audit trail идентичны?

Нет. Observability помогает понять runtime состояние; audit trail поддерживает доказуемую историю значимых действий и решений.


### 2. Что значит reproducible run?

Повторение процедуры/inputs в контролируемых условиях; идентичность output должна быть отдельно доказана.


### 3. Какие поля важны в manifest?

Task/run ID, source commit, спецификация/конфиги, tool/model/runtime IDs, environment, artifacts и ссылки на checks/decisions.


### 4. Почему хранить весь transcript рискованно?

В нём могут быть секреты, персональные данные и код; минимизация, redaction, retention и access control обязательны.


### 5. Как связывать события между системами?

Стабильными run/task/trace IDs и ссылками на commit, PR, CI run, approval и deployed artifact.


### 6. Что защищает log integrity?

Контроль записи и чтения, append-only/tamper-evident storage, key custody, clock source и аудит доступа; отдельные меры имеют свои границы.


### 7. Как доказать chain-of-custody?

Хэш/подпись артефакта с provenance, известным источником идентичности и проверяемым хранением; SLSA описывает supply-chain provenance, а не весь AI reasoning.


## Частые ошибки

- Считать название из curriculum стандартизованной методологией без источника. Нельзя обещать бит-в-бит повтор model output без доказанного deterministic runtime и неизменных внешних зависимостей; реальный scope воспроизведения надо определить для каждого артефакта.
- Путать рекомендации/vendor claims с независимыми доказательствами.
- Принимать зелёный check, согласие нескольких агентов или метрику активности за полное доказательство качества.
- Игнорировать scope, безопасность, стоимость эксплуатации и поддержку legacy.

Не добавлять обязательную лабораторию, домашнее задание, сдачу или артефакт читателя. Если урок потребует продуктового walkthrough, сначала закрепить версию, платформу, prerequisites и доступ; иначе оставить пример концептуальным.
