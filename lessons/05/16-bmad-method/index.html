Р5.16 — Методология 8. BMAD-METHOD

Статус: Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

Уровень: Middle–Senior/Staff, Tech Lead. Время: 35–50 минут, оценка без пилотирования.

Предварительные знания: Р4.21, Р5.10, Р5.14.

Результат обучения: Разобрать роли, workflow и артефакты BMAD на том же change case без смешения продуктовой документации и доказательства эффективности.

1. Инженерная проблема и определения

BMAD-METHOD, в текущих документах BMad Method, — набор skills, agents и workflow для обдумывания и разработки изменений с AI. Публичная документация BMad Code описывает planning, build, review, работу с existing codebase и customization.

Это конкретный развивающийся инструментарий, а не отраслевой стандарт. Старые tutorials могут описывать другие имена и организацию процесса.

Основания и ограничения: SRC-534. Рабочие модели и инженерные рекомендации не объявляются универсальными стандартами.

2. Архитектура и механизм

Workflow соотносится с неопределённостью и размером работы: ясная маленькая правка может начать с build, большая идея проходит уточнение intent, исследование, требования, design и decomposition. Названные skills подключаются в выбранном coding host.

intent → подходящий planning path → согласованные artifacts
       → build/review/test → evidence → человек принимает результат

Ролевой prompt не обеспечивает OS isolation. Обсуждение несколькими agents не заменяет независимый oracle. Конкретные commands, files и integrations должны быть привязаны к release.

3. Разобранная авторская демонстрация

На Workbench выбран один кейс — закрытие с role/state/repeat/audit criteria. Сначала фиксируется достаточно полный intent. Затем проектируется transaction boundary и tasks. Build output проверяется тем же acceptance набором, что ручной spec-anchored baseline.

Intent evidence: owner подтвердил C1..C4 и non-goals.
Design evidence: понятен путь отказа и атомарной записи.
Build evidence: diff и проверки на точном commit.
Review evidence: независимые замечания, исправления и остаточный риск.

Если агент создаёт много artifacts, но игнорирует C3 о повторе, процесс не проходит приёмку. Если простая правка тратит больше времени на церемонии, это тоже часть результата сравнения. Установка, commands и multi-agent discussions не запускались.

Платформа и проверка: Engineering Workbench — кандидат сквозного проекта, входы синтетические. Конкретные prerequisites приведены рядом с кодом/командами; псевдокод и JSON — учебные форматы. Приложение, тесты, агенты и продукты здесь не запускались. Ожидаемые свойства не являются фактическим результатом.

4. Production, риски и сопровождение

Аудируйте сторонние modules, instructions, hooks и tool permissions. Версионируйте overrides и проектный context вместе с кодом. Для legacy учитывайте текущие API и ограничения migrations; для команд — владельца финального решения. Сравнение workflow требует нескольких задач и учёта setup/rework, а не только привлекательного design demo.

В legacy фиксируют текущие контракты и baseline; в monorepo — затронутых consumers и owners. Приёмка связывается с конкретным состоянием кода и неизменными критериями. Проверяемые автоматические свойства идут в tests/CI, а неоднозначные решения — к назначенному владельцу. Полная стоимость включает setup, обучение, usage, ожидание, review, rework и поддержку версий. Непроверенное указывается явно.

5. Альтернативы и trade-offs

ПодходПрименимостьОсвоение, внедрение, сопровождение и цена компромисса
Прямой contract + reviewМалый ясный changeНизкий overhead, больше ручной дисциплины
BMad workflowНужны повторяемые planning/build practicesГотовые навыки, learning и upgrade cost
Свой playbookОсобые доменные/корпоративные правилаКонтроль максимален, поддержка на команде

Это качественное сравнение, а не benchmark. Проверяемость зависит от подходящего независимого evidence, безопасность — от фактических boundaries и возможности обхода. Дополнительный tooling оправдан, если польза для принятых outcomes покрывает затраты и новые отказные режимы.

6. Проверка знаний с объяснёнными ответами

1. Кто принимает финальные решения по продукту?

Человек/команда, назначенные владельцами; роли агента предлагают и проверяют артефакты, но не получают автоматически полномочия.

2. Как выбрать путь планирования?

По неоднозначности, размеру, риску и неизвестным требованиям, а не только числу файлов/агентов.

3. Что переносимо между версиями?

Концептуальные артефакты intent, spec, tasks и review; конкретные commands/skills потребуют проверки release.

4. Как проверять результат агента реализации?

Независимыми acceptance checks, tests, static/security checks и review в пределах изменённого scope.

5. Как сравнить BMad с простой схемой?

Один и тот же baseline, входная задача, model/tools, oracle и лимиты; измерять completeness, rework, cost и review time.

6. Какие основные риски сторонних skills?

Недоверенные инструкции, чрезмерные tool permissions, prompt injection, скрытое выполнение и supply chain; проверить содержимое и ограничить полномочия до применения.

7. Запускался ли BMad при подготовке урока?

Нет. Изучена документация и подготовлен авторский разбор; пробного запуска не было.

7. Итоги и следующий шаг

Разобрать роли, workflow и артефакты BMAD на том же change case без смешения продуктовой документации и доказательства эффективности. Главный критерий — объяснимое решение с границами ответственности и доказательности.
