# План урока Р5.16: Методология 8. BMAD-METHOD

**Статус:** Research / Outline; урок не написан.  **Предпосылки:** Р4.21, Р5.10, Р5.14.

## Результат обучения

Разобрать роли, workflow и артефакты BMAD на том же change case без смешения продуктовой документации и доказательства эффективности.

## План разделов урока

1. **Проблема и мотивация:** инженерная задача и границы применения темы.
2. **Определение и терминология:** BMAD-METHOD (актуальная официальная документация использует название BMad Method) — community/vendor-maintained набор skills/agents/workflow для проектирования и разработки с AI. Это методология/инструментарий, не отраслевой стандарт.
3. **Механизм:** Docs описывают пути от idea/research/spec/architecture/story decomposition к build/review/test, а также работу с existing codebases, customization, multi-agent discussions и agents with memory. Текущие prompts, команда установки и структура modules меняются; до практики закрепить release/tag и agent host.
4. **Архитектура:** схема компонентов, состояния, потока данных/управления, владельцев и enforcement boundary; объяснить, где есть nondeterminism.
5. **Практический разбор:** На единичной функции Workbench выбрать подходящую planning path, показать артефакты intent/spec/task, выполнить walkthrough build/review по docs и сопоставить с локальным простым workflow. Инсталляция/исполнение не выполнялись.
6. **Production:** Аудировать scope навыков и tools, доверие внешним modules, доступы, memory, update policy, соблюдение внутренних правил и стоимость церемоний. Измерять outcome на одном baseline, не количеством ролей.
7. **Trade-offs:** сравнить с альтернативами по применимости, освоению, внедрению, сопровождению, безопасности, проверяемости и стоимости; не приписывать общий ranking.
8. **Вопросы с ответами:** использовать сценарные вопросы ниже; объяснить ход решения, не только термин.
9. **Итоги и переход:** назвать limitations и связать с зависимой следующей темой.

## Практическая демонстрация и проверяемость

Это разбор автора, не задание читателю. Показать один обычный сценарий и один отказ/negative case. Ожидаемый результат формулировать как критерий; фактическим считать только вывод реально выполненной команды в зафиксированной среде. Сейчас продуктовый запуск/benchmark не заявлен.

## Вопросы для проверки знаний с ответами

### 1. Кто делает финальные calls по продукту?

Человек/команда, назначенные владельцами; роли агента предлагают и проверяют артефакты, но не получают автоматически полномочия.


### 2. Как выбрать planning path?

По неоднозначности, размеру, риску и неизвестным требованиям, а не только числу файлов/агентов.


### 3. Что переносимо между версиями?

Концептуальные артефакты intent, spec, tasks и review; конкретные commands/skills потребуют проверки release.


### 4. Как проверять результат build agent?

Независимыми acceptance checks, tests, static/security checks и review в пределах изменённого scope.


### 5. Как сравнить BMad с простой схемой?

Один и тот же baseline, входная задача, model/tools, oracle и лимиты; измерять completeness, rework, cost и review time.


### 6. Какие основные риски сторонних skills?

Недоверенные инструкции, чрезмерные tool permissions, prompt injection, скрытое выполнение и supply chain; inspect/limit before use.


### 7. Требует ли этот план запускать BMAD?

Нет; пакет описывает исследование/docs и авторский walkthrough. Functional trial не заявлен.


## Частые ошибки

- Считать название из curriculum стандартизованной методологией без источника. Текущая структура/commands/releases различаются со старыми tutorial; перед будущим уроком использовать pinned release и не переносить фактическое состояние сайта в курс бессрочно.
- Путать рекомендации/vendor claims с независимыми доказательствами.
- Принимать зелёный check, согласие нескольких агентов или метрику активности за полное доказательство качества.
- Игнорировать scope, безопасность, стоимость эксплуатации и поддержку legacy.

## Границы подготовки

Не добавлять обязательную лабораторию, домашнее задание, сдачу или артефакт читателя. Если урок потребует продуктового walkthrough, сначала закрепить версию, платформу, prerequisites и доступ; иначе оставить пример концептуальным.
