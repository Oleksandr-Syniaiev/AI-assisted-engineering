# План урока Р5.18: Методология 10. AI-DLC

**Статус:** Research / Outline; урок не написан.  **Предпосылки:** Р4.21, Р5.12, Р5.14.

## Результат обучения

Сопоставить lifecycle, роли, артефакты и human gates AI-DLC с предыдущими workflow на фиксированном кейсе.

## План разделов урока

1. **Проблема и мотивация:** инженерная задача и границы применения темы.
2. **Определение и терминология:** AI-DLC (AI-Driven Development Life Cycle) в данном curriculum — подход/реализация; первоисточник имени неоднозначен. Текущий публичный кандидат — aws-labs/aidlc-workflows, описывающий adaptive workflow steering rules для coding agents. Не считать это единственным определением AI-DLC.
3. **Механизм:** Репозиторий позиционирует общее ядро и несколько интеграции со средами выполнения. Для учебного анализа разобрать артефакты процесса, steering rules, адаптацию стадий, решения людей, путь тестирования и проверки и версионные различия; конкретный workflow требует чтения зафиксированную версию документации или кода перед написанием урока.
4. **Архитектура:** схема компонентов, состояния, потока данных/управления, владельцев и enforcement boundary; объяснить, где есть nondeterminism.
5. **Практический разбор:** На одной Workbench функции сопоставить стадии требований/дизайна/реализации/проверки из зафиксированного AI-DLC workflow с простым SDD process; отметить обязательные решения человека и где framework может адаптировать детализацию. Прогон не выполнялся.
6. **Production:** Проверить installed instruction scope, prompts/tools/permissions, agent compatibility, injection surface, update chain, supportability, generated artifacts and test evidence. Репозиторий не равен официальному стандарту AWS для всех команд.
7. **Trade-offs:** сравнить с альтернативами по применимости, освоению, внедрению, сопровождению, безопасности, проверяемости и стоимости; не приписывать общий ranking.
8. **Вопросы с ответами:** использовать сценарные вопросы ниже; объяснить ход решения, не только термин.
9. **Итоги и переход:** назвать limitations и связать с зависимой следующей темой.

## Практическая демонстрация и проверяемость

Это разбор автора, не задание читателю. Показать один обычный сценарий и один отказ/negative case. Ожидаемый результат формулировать как критерий; фактическим считать только вывод реально выполненной команды в зафиксированной среде. Сейчас продуктовый запуск/benchmark не заявлен.

## Вопросы для проверки знаний с ответами

### 1. AI-DLC — общепринятый стандарт?

Проверенные материалы подтверждают конкретный проект/workflow, а не универсальный стандарт определения и обязательного lifecycle.


### 2. Что означает adaptive lifecycle?

Детализация и порядок артефактов могут зависеть от сложности/риска; exact criteria надо брать из выбранной версии.


### 3. Чем workflow отличается от методологии?

Workflow — исполняемый набор шагов/правил конкретной реализации; методология шире и может существовать независимо от tooling.


### 4. Какие артефакты сравнить?

Intent/requirements, design, task breakdown, code diff, test evidence, approvals и change history.


### 5. Почему нужна версия?

Prompt/workflow изменения могут менять поведение; pinned commit позволяет связать разбор с известной реализацией.


### 6. Как проверять совместимость с harness?

По docs и automated tests выбранной версии, затем пробным isolated run; текущий пакет не заявляет этот запуск.


### 7. Какие требования production readiness?

Безопасные permissions, независимые checks, review ownership, observability, bounded execution, incident recovery и стоимость.


## Частые ошибки

- Считать название из curriculum стандартизованной методологией без источника. Нужно проверить официальную терминологию/публичный status проекта, pinned release, list supported harnesses, tests и весь lifecycle документации; исходное имя AI-DLC не подтверждает, что это однозначно тот проект, который имел в виду автор curriculum.
- Путать рекомендации/vendor claims с независимыми доказательствами.
- Принимать зелёный check, согласие нескольких агентов или метрику активности за полное доказательство качества.
- Игнорировать scope, безопасность, стоимость эксплуатации и поддержку legacy.

## Границы подготовки

Не добавлять обязательную лабораторию, домашнее задание, сдачу или артефакт читателя. Если урок потребует продуктового walkthrough, сначала закрепить версию, платформу, prerequisites и доступ; иначе оставить пример концептуальным.
