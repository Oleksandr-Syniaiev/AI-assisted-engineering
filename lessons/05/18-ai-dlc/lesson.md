# Р5.18 — Методология 10. AI-DLC

**Статус:** Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

**Уровень:** Middle–Senior/Staff, Tech Lead. **Время:** 35–50 минут, оценка без пилотирования.

**Предварительные знания:** Р4.21, Р5.12, Р5.14.

**Результат обучения:** Сопоставить lifecycle, роли, артефакты и human gates AI-DLC с предыдущими workflow на фиксированном кейсе.

## 1. Инженерная проблема и определения

AI-DLC — неоднозначное название подхода. В этом уроке выбран публичный кандидат AWS Labs `aidlc-workflows`, описывающий adaptive workflow steering rules для coding agents. Совпадение имени не устанавливает единственный общепринятый lifecycle и не доказывает исходный замысел curriculum.

Текущий README позиционирует общее ядро и интеграции с несколькими harness, связанные requirements, decisions, implementation, tests и audit. Это документированное устройство проекта, а не независимый результат сравнения.

Основания и ограничения: [SRC-536](references.md#src-536). Рабочие модели и инженерные рекомендации не объявляются универсальными стандартами.

## 2. Архитектура и механизм

Реализация разделяет core процесса и host-specific подключение. Подходящий workflow выбирается по запросу, недостающие решения уточняются, а переходы могут останавливаться на approval gates. Конкретный профиль и версии важны: один label AI-DLC не фиксирует набор stages и семантику исполнения навсегда.

```text
request → workflow/profile selection → decisions/artifacts
        → implementation и checks → source-bound review → завершение
```

Steering rules и hooks участвуют в управлении, но host permissions и независимая проверка приложения остаются отдельными слоями.

## 3. Разобранная авторская демонстрация

Для Workbench берём те же C1..C4, что у Spec-anchored baseline. Сопоставляются не имена ролей, а функции процесса: где уточняется actor, кто решает повтор, где выбирается transaction boundary и чем подтверждается результат.

```text
Сравнительный dossier:
вход: одинаковый source commit и acceptance cases;
процесс: pinned AI-DLC profile + host/version;
artifacts: intent, решение, план/tasks, diff, checks, review;
cost: setup, model usage, ожидание owner, rework, support;
scope: без production действий и внешних записей.
```

Если framework меняет правила review в новой версии, старая оценка не переносится автоматически. Опубликованная install-команда не исполнялась, generated files не наблюдались. Для будущего trial установку сначала изучают и выполняют в подходящей ограниченной среде с разрешённым доступом.

**Платформа и проверка:** Engineering Workbench — кандидат сквозного проекта, входы синтетические. Конкретные prerequisites приведены рядом с кодом/командами; псевдокод и JSON — учебные форматы. Приложение, тесты, агенты и продукты здесь не запускались. Ожидаемые свойства не являются фактическим результатом.

## 4. Production, риски и сопровождение

При внедрении проверяют license выбранного release, installer/update path, host compatibility, instructions/hooks, secrets, persistent state и recovery. Brownfield требует сохранения существующих contracts и миграций. Не считайте broad support list доказательством того, что одинаковые controls действуют во всех hosts.

В legacy фиксируют текущие контракты и baseline; в monorepo — затронутых consumers и owners. Приёмка связывается с конкретным состоянием кода и неизменными критериями. Проверяемые автоматические свойства идут в tests/CI, а неоднозначные решения — к назначенному владельцу. Полная стоимость включает setup, обучение, usage, ожидание, review, rework и поддержку версий. Непроверенное указывается явно.

## 5. Альтернативы и trade-offs

| Подход | Применимость | Освоение, внедрение, сопровождение и цена компромисса |
|---|---|---|
| Обычный ticket workflow | Зрелая небольшая команда | Мало setup, agent controls добавляются отдельно |
| Generic spec-anchored | Нужна traceability без тяжёлого toolkit | Умеренная формализация и ручная поддержка |
| AWS Labs AI-DLC workflow | Нужна проверка готового lifecycle tooling | Выбранный profile даёт структуру; upgrades и host differences требуют обслуживания |

Это качественное сравнение, а не benchmark. Проверяемость зависит от подходящего независимого evidence, безопасность — от фактических boundaries и возможности обхода. Дополнительный tooling оправдан, если польза для принятых outcomes покрывает затраты и новые отказные режимы.

## 6. Проверка знаний с объяснёнными ответами

### 1. AI-DLC — общепринятый стандарт?

Проверенные материалы подтверждают конкретный проект/workflow, а не универсальный стандарт определения и обязательного lifecycle.

### 2. Что означает adaptive lifecycle?

Детализация и порядок артефактов могут зависеть от сложности/риска; точные критерии надо брать из выбранной версии.

### 3. Чем workflow отличается от методологии?

Workflow — исполняемый набор шагов/правил конкретной реализации; методология шире и может существовать независимо от tooling.

### 4. Какие артефакты сравнить?

Intent/requirements, design, task breakdown, code diff, test evidence, approvals и change history.

### 5. Почему нужна версия?

Prompt/workflow изменения могут менять поведение; зафиксированный commit позволяет связать разбор с известной реализацией.

### 6. Как проверять совместимость с harness?

По docs и automated tests выбранной версии, затем пробным isolated run; текущий пакет не заявляет этот запуск.

### 7. Какие требования production readiness?

Безопасные permissions, независимые checks, review ownership, observability, bounded execution, incident recovery и стоимость.
