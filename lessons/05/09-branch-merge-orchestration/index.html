Р5.09 — Паттерн 18. Branch-and-merge оркестрация

Статус: Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

Уровень: Middle–Senior/Staff, Tech Lead. Время: 35–50 минут, оценка без пилотирования.

Предварительные знания: Р5.08; основы merge и конфликтов.

Результат обучения: Задать порядок интеграции параллельных изменений, разрешить конфликт и перепроверить объединённое состояние.

1. Инженерная проблема и определения

Branch-and-merge оркестрация разделяет подготовку изменений и их включение в общую ветку. Она помогает управлять ownership и review, но не устраняет логическую несовместимость. Отсутствие текстового конфликта означает только, что Git смог объединить строки.

Основания и ограничения: SRC-523. Рабочие модели и инженерные рекомендации не объявляются универсальными стандартами.

2. Архитектура и механизм

Каждая задача имеет base и контракт, PR — конкретный head, а integration — текущую target version. Проверки и approvals должны соответствовать нужному состоянию. Merge queue может проверять candidate с актуальной базой и предшествующими PR по правилам платформы.

base → branch A → checks/review
    → branch B → checks/review
             → интеграционный кандидат → повторные checks → merge

Важны не только порядок merges, но и правила stale approvals, обновления base, failure handling и отмены очереди.

3. Разобранная авторская демонстрация

В Workbench ветка A переименовывает status в API response, ветка B добавляет notification consumer, читающий старое поле. Разные файлы сливаются без текстового конфликта, но уведомления ломаются. Consumer contract test на объединённом дереве должен проявить несовместимость.

Другой случай: оба автора меняют одно условие transition. Git показывает textual conflict, но выбрать строку недостаточно. Owner сопоставляет обе причины с согласованными CLOSE criteria, затем фиксирует решение и запускает проверки на результате.

merge evidence:
- точный кандидат/итоговый commit;
- разрешённый конфликт и rationale;
- проверки API/consumer и regression;
- оставшиеся неизвестные и решение owner.

Это проектируемый разбор. Repository protection, queue и tests здесь не настраивались. Зелёные независимые ветки не представлены как гарантия зелёной интеграции.

Платформа и проверка: Engineering Workbench — кандидат сквозного проекта, входы синтетические. Конкретные prerequisites приведены рядом с кодом/командами; псевдокод и JSON — учебные форматы. Приложение, тесты, агенты и продукты здесь не запускались. Ожидаемые свойства не являются фактическим результатом.

4. Production, риски и сопровождение

Проверяйте права обхода, identity источника checks, возможность изменять workflow и управление emergency paths. В busy main цена повторной CI растёт; queue может уменьшить ручные обновления, но требует согласованных CI events. Нельзя разрешать агенту выключать protection ради собственного merge.

В legacy фиксируют текущие контракты и baseline; в monorepo — затронутых consumers и owners. Приёмка связывается с конкретным состоянием кода и неизменными критериями. Проверяемые автоматические свойства идут в tests/CI, а неоднозначные решения — к назначенному владельцу. Полная стоимость включает setup, обучение, usage, ожидание, review, rework и поддержку версий. Непроверенное указывается явно.

5. Альтернативы и trade-offs

ПодходПрименимостьОсвоение, внедрение, сопровождение и цена компромисса
Прямые commitsМалый низкорисковый потокМало процесса, слабее независимый контроль
PR workflowОбычная командная разработкаЯсные reviews/checks, очередь внимания человека
Merge queueBusy branchБольше integration CI, меньше ручного rebasing при конкуренции

Это качественное сравнение, а не benchmark. Проверяемость зависит от подходящего независимого evidence, безопасность — от фактических boundaries и возможности обхода. Дополнительный tooling оправдан, если польза для принятых outcomes покрывает затраты и новые отказные режимы.

6. Проверка знаний с объяснёнными ответами

1. Что гарантирует отсутствие текстового конфликта?

Только совместимость редактируемых строк, не бизнес-семантику, миграции, API или изменившиеся предположения.

2. Когда повторять CI?

После разрешения конфликтов и на точном кандидате к слиянию/итоговом commit.

3. Какова роль merge queue?

Проверить интеграцию PR с текущей базой/очередью и сериализовать допустимые слияния по правилам платформы.

4. Кто принимает решение при конфликте требований?

Назначенный владелец домена/архитектуры; агент может собрать diff и варианты, но не должен подменять authority.

5. Что делать со stale approval?

Считать policy-specific; настроить повторный review при значимых изменениях и проверить текущую конфигурацию платформы.

6. Как безопасно проверить merge settings?

Сверить source/check identity, permissions, branch protection/rulesets и позитивный/негативный сценарий на тестовой ветке.

7. Какие сигналы улучшения?

Время до устойчивого merge, конфликтные циклы, ошибки проверок после слияния и rework, при этом качество остаётся не ниже baseline.

7. Итоги и следующий шаг

Задать порядок интеграции параллельных изменений, разрешить конфликт и перепроверить объединённое состояние. Главный критерий — объяснимое решение с границами ответственности и доказательности.
