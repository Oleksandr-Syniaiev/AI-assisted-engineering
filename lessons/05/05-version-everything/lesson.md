# Р5.05 — Паттерн 14. Version Every Thing (VET)

**Статус:** Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

**Уровень:** Middle–Senior/Staff, Tech Lead. **Время:** 35–50 минут, оценка без пилотирования.

**Предварительные знания:** Р4.09–Р4.10; определить границы Version Every Thing.

**Результат обучения:** Фиксировать достаточно версий и provenance для объяснимого сравнения/аудита, не сохраняя секреты и лишние данные.

## 1. Инженерная проблема и определения

Version Every Thing (VET) в curriculum — рабочий ярлык, а не универсальный стандарт. Практическое правило: идентифицировать значимые изменяемые входы процесса, чтобы объяснить результат и сравнение. «Всё» не означает сохранять каждый payload, секрет или персональные данные.

Версия prompt полезна, но не фиксирует автоматически toolchain, внешнее состояние и backend модели.

Основания и ограничения: [SRC-513](references.md#src-513) · [SRC-514](references.md#src-514). Рабочие модели и инженерные рекомендации не объявляются универсальными стандартами.

## 2. Архитектура и механизм

Manifest связывает task/run с commit, spec, конфигом, модельным идентификатором, инструментами, окружением и evidence. Для доступных immutable входов используют точные IDs/digests; для недоступных фиксируют неопределённость. SLSA описывает build provenance, а не полную детерминированность LLM.

```text
входы и версии → run manifest → outputs/checks → сравнение/аудит
```

Model alias может меняться. Даже при доступном snapshot внешняя tool-среда способна дать другой результат. Поэтому повторяемость процедуры и идентичность результата — разные требования.

## 3. Разобранная авторская демонстрация

Два Workbench runs используют один task prompt, но второй получил обновлённый tool schema. Без manifest различие ошибочно приписывается модели. Учебная запись:

```json
{
  "task_id": "CLOSE-01",
  "source_commit": "<sha>",
  "spec_digest": "<digest>",
  "prompt_revision": "v2",
  "tool_contract_revision": "v3",
  "model_id": "<available-identifier>",
  "checks": [],
  "execution_status": "not-executed"
}
```

Это собственный формат примера, не SLSA schema. В реальном manifest секрет заменяется контролируемой ссылкой; значение credential не сохраняется. Смена tool schema вызывает review совместимости. Старый manifest позволяет понять входы, но не обещает, что hosted model ещё доступна для replay.

**Платформа и проверка:** Engineering Workbench — кандидат сквозного проекта, входы синтетические. Конкретные prerequisites приведены рядом с кодом/командами; псевдокод и JSON — учебные форматы. Приложение, тесты, агенты и продукты здесь не запускались. Ожидаемые свойства не являются фактическим результатом.

## 4. Production, риски и сопровождение

Определите data classification, доступ, retention, целостность и owners schema. Сохраняйте только необходимые метаданные: хэши чувствительных низкоэнтропийных значений тоже могут раскрывать информацию. Цена VET включает сбор, хранение и миграции схемы; глубина фиксации выбирается по риску и цели аудита.

В legacy фиксируют текущие контракты и baseline; в monorepo — затронутых consumers и owners. Приёмка связывается с конкретным состоянием кода и неизменными критериями. Проверяемые автоматические свойства идут в tests/CI, а неоднозначные решения — к назначенному владельцу. Полная стоимость включает setup, обучение, usage, ожидание, review, rework и поддержку версий. Непроверенное указывается явно.

## 5. Альтернативы и trade-offs

| Подход | Применимость | Освоение, внедрение, сопровождение и цена компромисса |
|---|---|---|
| Git + lockfiles | Код и обычные dependencies | Дёшево, не охватывает весь hosted execution |
| Run manifest | Объяснение конкретной попытки | Умеренная интеграция и schema maintenance |
| Provenance package | Высокий риск и supply chain | Больше integrity controls и эксплуатационной цены |

Это качественное сравнение, а не benchmark. Проверяемость зависит от подходящего независимого evidence, безопасность — от фактических boundaries и возможности обхода. Дополнительный tooling оправдан, если польза для принятых outcomes покрывает затраты и новые отказные режимы.

## 6. Проверка знаний с объяснёнными ответами

### 1. Что следует версионировать?

Все входы, значимо меняющие выполнение, в разумной границе: код/спека, версии инструментов и правил, модельный идентификатор, параметры и окружение.

### 2. VET означает сохранить все данные?

Нет. Нужно сохранять достаточную provenance-метаинформацию, минимизировать персональные/чувствительные payload и исключать секреты.

### 3. Достаточно назвать модель?

Нет, alias и hosted service могут обновляться; зафиксировать доступный immutable ID, дату, параметры и провайдера, а неопределённость указать.

### 4. Версия prompt обеспечивает воспроизводимость?

Она помогает повторить входную конфигурацию, но не гарантирует идентичный output из-за nondeterminism, model updates, tools и внешнего состояния.

### 5. Как хранить секретные параметры?

Хранить ссылку на secret manager и аудит доступа, не значение; очищать логи, артефакты и trace перед публикацией.

### 6. Какова цена VET?

Дополнительные сбор, хранение, обновление схем, приватность и интеграция; объём ограничивают через риск-ориентированный manifest.

### 7. Когда достаточно простого lockfile?

Для dependency graph он фиксирует пакеты, но не описывает полное agent execution, системные зависимости, модель и набор проверок.

## 7. Итоги и следующий шаг

Фиксировать достаточно версий и provenance для объяснимого сравнения/аудита, не сохраняя секреты и лишние данные. Главный критерий — объяснимое решение с границами ответственности и доказательности.
