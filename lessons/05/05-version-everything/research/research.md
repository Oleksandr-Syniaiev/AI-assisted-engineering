# Исследование Р5.05: Паттерн 14. Version Every Thing (VET)

## Метаданные

- Дата исследования и проверки источников: 2026-11-02.
- Зависимости curriculum: Р4.09–Р4.10; определить границы Version Every Thing.
- Статус: Research / Outline; готовый урок не написан.
- Граница: документальное исследование и авторский разбор; установка продукта, benchmarking и запуск примеров не выполнялись.
- Практика: разобранная демонстрация без самостоятельного задания, сдачи или обязательного создания читателем артефакта.

## Исследовательские вопросы и ответы

### 1. Что следует версионировать?

Все входы, значимо меняющие выполнение, в разумной границе: код/спека, версии инструментов и правил, модельный идентификатор, параметры и окружение. [SRC-512](sources.md#src-512); [SRC-513](sources.md#src-513); [SRC-514](sources.md#src-514)

### 2. VET означает сохранить все данные?

Нет. Нужно сохранять достаточную provenance-метаинформацию, минимизировать персональные/чувствительные payload и исключать секреты. [SRC-512](sources.md#src-512); [SRC-513](sources.md#src-513); [SRC-514](sources.md#src-514)

### 3. Достаточно назвать модель?

Нет, alias и hosted service могут обновляться; зафиксировать доступный immutable ID, дату, параметры и провайдера, а неопределённость указать. [SRC-512](sources.md#src-512); [SRC-513](sources.md#src-513); [SRC-514](sources.md#src-514)

### 4. Версия prompt обеспечивает воспроизводимость?

Она помогает повторить входную конфигурацию, но не гарантирует идентичный output из-за nondeterminism, model updates, tools и внешнего состояния. [SRC-512](sources.md#src-512); [SRC-513](sources.md#src-513); [SRC-514](sources.md#src-514)

### 5. Как хранить секретные параметры?

Хранить ссылку на secret manager и аудит доступа, не значение; очищать логи, артефакты и trace перед публикацией. [SRC-512](sources.md#src-512); [SRC-513](sources.md#src-513); [SRC-514](sources.md#src-514)

### 6. Какова цена VET?

Дополнительные сбор, хранение, обновление схем, приватность и интеграция; объём ограничивают через риск-ориентированный manifest. [SRC-512](sources.md#src-512); [SRC-513](sources.md#src-513); [SRC-514](sources.md#src-514)

### 7. Когда достаточно простого lockfile?

Для dependency graph он фиксирует пакеты, но не описывает полное agent execution, системные зависимости, модель и набор проверок. [SRC-512](sources.md#src-512); [SRC-513](sources.md#src-513); [SRC-514](sources.md#src-514)

## Определение и границы

VET здесь — ярлык curriculum, а не найденный универсальный стандарт. Рабочее определение: версионировать или идентифицировать изменяемые входы, влияющие на результат: код, спецификации, prompts, agent/tool config, модели/endpoint, зависимости и среду.

## Механизм и архитектура

Сформировать manifest, связывающий задачу и commit с версиями материалов, разрешениями, окружением, идентификаторами запуска и evidence. Секреты заменять ссылками на контролируемый secret reference; содержимое credentials не сохранять. [SRC-512](sources.md#src-512), [SRC-513](sources.md#src-513)

## Сравнение альтернатив

Матрица — качественная инженерная оценка, не benchmark. Перед выбором согласовать вес критериев с риском и измерять один и тот же outcome.

| Подход | Применимость | Освоение / внедрение | Сопровождение | Безопасность | Проверяемость | Стоимость |
|---|---|---|---|---|---|---|
| Только Git commits и lockfiles | Код, обычные зависимости и документы уже имеют immutable IDs. | Просто и привычно; не описывает все hosted inputs. | Пересматривать при изменении процесса/границ; закрепить владельца и версию. | Надёжно в границах Git, но секреты и external model state не фиксируются. | Сопоставить с независимым oracle и точным состоянием. | Дешёвое основание, ограниченное покрытие provenance. |
| Run manifest | Нужно повторно объяснить конкретный agent run и compare changes. | Среднее внедрение схемы/сборщика. | Пересматривать при изменении процесса/границ; закрепить владельца и версию. | Можно исключить payload/секреты и трассировать версии. | Сопоставить с независимым oracle и точным состоянием. | Низкая/умеренная цена записи; требует maintenance при evolution schema. |

## Разобранная авторская демонстрация

Сравнить два разбора одного изменения Workbench: один без фиксации версии prompt/tool, другой с manifest из commit SHAs, config digest, model identifier и test output hash. Это формат демонстрации, не обещание повторить stochastic output.

Ожидаемые выводы — проектируемые критерии walkthrough, не фактические результаты запуска.

## Применение в production

Применять data classification, signing/integrity, access control, retention и redaction. Model alias может менять backend; запись имени модели не гарантирует, что старый backend доступен.

Для любой демонстрации явно указать платформу/harness, prerequisites и статус исполнения. Если команда или API не проверялись на выбранной версии, показывать их как иллюстрацию документации, не как воспроизводимую инструкцию.

## Неопределённости и проверка перед написанием урока

Репозиторная история и SLSA provenance покрывают разные слои; проектный VET manifest должен уточнить, какие model/tool state реально доступны для pinning.

Перед подготовкой урока заново проверить текущую версию документации, требования доступа, модель безопасности, доступность функций и точные команды выбранной платформы. Независимое сравнение и эксплуатационные измерения в этом пакете не проводились.

## Кандидат демонстрации и критерии

Сравнить два разбора одного изменения Workbench: один без фиксации версии prompt/tool, другой с manifest из commit SHAs, config digest, model identifier и test output hash. Это формат демонстрации, не обещание повторить stochastic output.

Критерии разбора: цель/контракт определены; альтернативы сопоставлены на одинаковом scope; ожидаемое поведение отделено от наблюдаемого; production-риск и способ независимой проверки названы; отсутствующие данные помечены.
