# План урока Р5.08: Паттерн 17. Git worktrees / параллельные субагенты

**Статус:** Research / Outline; урок не написан.  **Предпосылки:** Р5.05–Р5.07, Р5.12; GAP-10–GAP-11.

## Результат обучения

Спроектировать параллельные независимые изменения в отдельных worktrees и изолированных runtime-ресурсах.

## План разделов урока

1. **Проблема и мотивация:** инженерная задача и границы применения темы.
2. **Определение и терминология:** Git worktree — несколько рабочих деревьев, связанных с одним репозиторием и использующих общее repository metadata с отдельными рабочими состояниями. Worktree сам по себе не изолирует процессы, порты, базы, Docker volumes или credentials.
3. **Механизм:** Создать задачу-граф, привязать каждому исполнителю отдельный branch/worktree, определить ownership файлов и API, выделить окружения, затем интегрировать и повторить проверки на итоговом состоянии. [SRC-521](sources.md#src-521), [SRC-501](sources.md#src-501)
4. **Архитектура:** схема компонентов, состояния, потока данных/управления, владельцев и enforcement boundary; объяснить, где есть nondeterminism.
5. **Практический разбор:** Развести фильтр списка и уведомления по отдельным модулям с утверждённым API. Показать в плане: одинаковый base commit, разные ветки/деревья, уникальные порты и тестовые БД, cleanup и post-merge CI. Пример команд — документальный; запуск не выполнялся.
6. **Production:** Контролировать совместное использование Git refs, lockfiles, build caches, migrations, test fixtures, secrets, network и shared services. Ограничивать число одновременных задач по доступным runtime-ресурсам и review bandwidth.
7. **Trade-offs:** сравнить с альтернативами по применимости, освоению, внедрению, сопровождению, безопасности, проверяемости и стоимости; не приписывать общий ranking.
8. **Вопросы с ответами:** использовать сценарные вопросы ниже; объяснить ход решения, не только термин.
9. **Итоги и переход:** назвать limitations и связать с зависимой следующей темой.

## Вопросы для проверки знаний с ответами

### 1. Что именно изолирует Git worktree?

Рабочую копию и индекс/HEAD для отдельного checkout; значительная часть repository metadata остаётся общей.


### 2. Почему двух worktrees недостаточно для безопасности?

Они не дают отдельные OS users, container namespaces, DB, сетевые политики или secret scopes.


### 3. Какой способ разделения задач лучший?

Тот, где у задач мало конфликтующих записей и четкие интерфейсы; независимость важнее числа агентов.


### 4. Зачем фиксировать один baseline commit?

Чтобы отделить различия модели/задач от исходного состояния и не скрыть незапланированные изменения.


### 5. Можно ли одновременно проверить миграции в одной dev DB?

Обычно это создаёт конфликт схемы/данных; использовать отдельные disposable DB или строго сериализовать миграционные проверки.


### 6. Как завершать worktree?

После фиксации результата и проверки состояния ветки удалить только чистое дерево корректной процедурой; несохранённую работу сначала сохранить.


### 7. Какие проверки нужны после интеграции?

Все относящиеся к итоговому дереву tests/build/lint/security/architecture checks, потому что по отдельности зелёные ветки могут конфликтовать после merge.


## Частые ошибки

- Считать название из curriculum стандартизованной методологией без источника. Worktree разделяет файлы/index, но реальная изоляция требует отдельной модели процессов и сервисов; на конкретном стеке Workbench она ещё не закреплена.
- Путать рекомендации/vendor claims с независимыми доказательствами.
- Принимать зелёный check, согласие нескольких агентов или метрику активности за полное доказательство качества.
- Игнорировать scope, безопасность, стоимость эксплуатации и поддержку legacy.
