Р5.08 — Паттерн 17. Git worktrees / параллельные субагенты

Статус: Final; авторский технический и методический self-review. Независимая рецензия не проводилась.

Уровень: Middle–Senior/Staff, Tech Lead. Время: 35–50 минут, оценка без пилотирования.

Предварительные знания: Р5.05–Р5.07, Р5.12; GAP-10–GAP-11.

Результат обучения: Спроектировать параллельные независимые изменения в отдельных worktrees и изолированных runtime-ресурсах.

1. Инженерная проблема и определения

Git worktree позволяет иметь несколько рабочих деревьев одного репозитория. У них отдельные working files, index и HEAD, но существенная часть repository data общая. Это удобная основа для параллельных изменений, а не sandbox выполнения.

Отдельные директории не дают автоматически отдельные порты, базы, caches, сетевые права или учётные записи.

Основания и ограничения: SRC-521 · SRC-522. Рабочие модели и инженерные рекомендации не объявляются универсальными стандартами.

2. Архитектура и механизм

Сначала задачи разделяют по контрактам и общим writes. Каждой дают известный base commit, ветку, worktree и runtime resources. Изменение shared schema требует согласования, даже если файлы лежат отдельно.

согласованный API + baseline
       → task A / worktree A / test resources A
       → task B / worktree B / test resources B
       → integration owner → post-merge checks

Нельзя безопасно параллелить запись двух агентов в одну рабочую копию только на основании разных имён задач. Ownership касается фактических файлов и внешних эффектов.

3. Разобранная авторская демонстрация

В Workbench task A добавляет фильтр списка, task B — независимое уведомление после согласования API. Для учебного shell-примера нужны Git, существующий repository с commit HEAD, свободные paths и ещё не созданные branches. Команды подходят PowerShell и обычному POSIX shell; здесь не исполнялись:

git worktree add -b lesson-filter ../wb-filter HEAD
git worktree add -b lesson-notify ../wb-notify HEAD
git worktree list

Если HEAD между командами меняется, оба дерева могут получить разный baseline; для настоящего trial используют один заранее зафиксированный SHA. Рабочие processes дополнительно получают разные порты и test DB. Migration не применяется конкурентно к общей dev DB.

После сохранения результата и проверки чистоты дерево удаляют через git worktree remove; непереданные changes сначала сохраняют. Force cleanup не входит в демонстрацию. Ожидается локальная изоляция files, а не доказанная isolation всего runtime.

Платформа и проверка: Engineering Workbench — кандидат сквозного проекта, входы синтетические. Конкретные prerequisites приведены рядом с кодом/командами; псевдокод и JSON — учебные форматы. Приложение, тесты, агенты и продукты здесь не запускались. Ожидаемые свойства не являются фактическим результатом.

4. Production, риски и сопровождение

Различайте общие refs и caches, config scopes, DB volumes и секреты. Слишком много параллельных tasks перегружает runners и reviewer. Метрики включают конфликтные cycles и post-merge rework. Иногда последовательная работа в одном tree дешевле полного набора изолированных окружений.

В legacy фиксируют текущие контракты и baseline; в monorepo — затронутых consumers и owners. Приёмка связывается с конкретным состоянием кода и неизменными критериями. Проверяемые автоматические свойства идут в tests/CI, а неоднозначные решения — к назначенному владельцу. Полная стоимость включает setup, обучение, usage, ожидание, review, rework и поддержку версий. Непроверенное указывается явно.

5. Альтернативы и trade-offs

ПодходПрименимостьОсвоение, внедрение, сопровождение и цена компромисса
ПоследовательноСвязанные измененияМало координации, полная elapsed duration
Общее treeНезависимое чтениеДёшево, concurrent writes опасны
Worktree + runtime isolationНезависимые реализацииВыше setup/cleanup, проще локализация изменений

Это качественное сравнение, а не benchmark. Проверяемость зависит от подходящего независимого evidence, безопасность — от фактических boundaries и возможности обхода. Дополнительный tooling оправдан, если польза для принятых outcomes покрывает затраты и новые отказные режимы.

6. Проверка знаний с объяснёнными ответами

1. Что именно изолирует Git worktree?

Рабочую копию и индекс/HEAD для отдельного checkout; значительная часть repository metadata остаётся общей.

2. Почему двух worktrees недостаточно для безопасности?

Они не дают отдельные OS users, container namespaces, DB, сетевые политики или secret scopes.

3. Какой способ разделения задач лучший?

Тот, где у задач мало конфликтующих записей и четкие интерфейсы; независимость важнее числа агентов.

4. Зачем фиксировать один baseline commit?

Чтобы отделить различия модели/задач от исходного состояния и не скрыть незапланированные изменения.

5. Можно ли одновременно проверить миграции в одной dev DB?

Обычно это создаёт конфликт схемы/данных; использовать отдельные disposable DB или строго сериализовать миграционные проверки.

6. Как завершать worktree?

После фиксации результата и проверки состояния ветки удалить только чистое дерево корректной процедурой; несохранённую работу сначала сохранить.

7. Какие проверки нужны после интеграции?

Все относящиеся к итоговому дереву tests/build/lint/security/architecture checks, потому что по отдельности зелёные ветки могут конфликтовать после merge.

7. Итоги и следующий шаг

Спроектировать параллельные независимые изменения в отдельных worktrees и изолированных runtime-ресурсах. Главный критерий — объяснимое решение с границами ответственности и доказательности.
